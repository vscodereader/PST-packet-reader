# 게시큐 "완전 종료(kill)" 설계서

- 작성일: 2026-07-06
- 대상 PR: #324 (`docs/admin-remote-control-design`)
- 범위: **로컬 앱(하위 COM) UI 쓰레기통 버튼** + **Admin 원격 kill 명령** 두 경로로, 실행 중인 게시큐를 고아 프로세스·캡차·중복게시·다음 작업 오염 없이 **칼같이** 종료.
- 상태: **설계 검토 단계** (구현 전). 기존 코드·UI 재사용, "종료 신호" 원시primitive 1개만 신규.

> 이 문서는 4갈래 코드 실측 조사(게시큐 실행 루프 / Chrome 수명 / 게시 흐름·캡차 / Admin·UI 삽입점)를 근거로 한다. 모든 주장에 `file:line`(브랜치 `docs/admin-remote-control-design` 기준) 근거를 붙였다.

---

## 1. 배경 · 목표

**문제**: 게시큐를 실행시키면 그 큐가 끝날 때까지 사용자가 취소할 수 없다. 새 작업을 하려면 기존 작업이 끝날 때까지 대기하는 방법밖에 없다.

**요구(사용자)**:
1. 실행 중인 게시큐 각 행 **우측에 쓰레기통 아이콘** → 누르면 그 큐가 **완전 종료**.
2. Admin에서 "n번 컴퓨터의 ~계정 게시 작업을 kill" 명령을 내려도 종료.
3. 하위 COM 사용자가 직접 제거 버튼을 눌러도 종료.
4. **눈(UI)에서만 사라지고 뒤에서 계속 도는 게 아니라, 하던 작업 자체를 칼같이 중지.**
5. 매크로 로직뿐 아니라 **실행 중이던 Chrome 등 자식 프로세스까지 고아 없이 완전 정리**.
6. 종료 직후 **뒤에 대기하던 게시큐가 즉시 승계**되어 실행.
7. 강제 종료로 생길 수 있는 문제(앞 작업 잔재로 인한 오류·캡차)가 **없도록**.

**수용 기준(Acceptance)**:
- kill 후 그 큐의 게시 API 호출·Chrome이 **더 이상 발생하지 않는다**.
- kill 후 **고아 Chrome(렌더러/GPU/crashpad) 0개**, 임시 프로필 잔여 0.
- kill 후 다음 로그인/게시에서 **잔재로 인한 캡차·오류 0**.
- kill 직후 **다음 Waiting 큐가 자동 승계**.
- **중복게시 0**(3장 안전 경계 준수 시).

## 2. 현재 코드 실측 — 왜 지금은 "칼같이 중지"가 불가능한가

### 2-1. 취소 원시primitive가 **아예 없다**
- `RunnerInner`는 durable 상태로 `is_running`·`active_forum`·`active_comment` **정수 3개만** 보유 — 취소 토큰/플래그/태스크 핸들 레지스트리 전무. `src-tauri/src/ipc/queue_runner.rs:55-66`.
- `src-tauri/src` 전체에 `CancellationToken`·`AtomicBool`(취소용)·`AbortHandle`·`.abort()` 가 **하나도 없다**(조사 grep 결과 0건).

### 2-2. 지금의 "취소/중지"는 **협조적(cooperative)** 이고 **경계에서만** 먹힌다
- `cancel_queue_now`(`src-tauri/src/ipc/queue.rs:471-479`) → `apply_cancel_now`(`queue.rs:282-296`)는 **디스크 큐(JsonStore)에서 항목 id만 filter로 제거**한다. 실행 태스크에 접근하지 못하며 신호도 못 준다.
- 워커는 각 단계 경계에서 `item_present(app, id)`(`queue_runner.rs:446-451`)로 "아직 큐에 있나?"만 본다. 없으면 **다음 단계를 시작 안 할 뿐**, 진행 중인 단계는 끝까지 간다. 코드 주석이 직접 "협조적 취소"라고 명시(`queue_runner.rs:444-445`).
- 우선순위 양보(`should_yield` `queue_runner.rs:1459-1462`, "중지=삭제아님" #232)도 **계정 그룹 경계에서만**, 그것도 더 높은 우선순위 Waiting이 도착했을 때만 자동 발동.
- 협조적 체크포인트(취소가 먹히는 유일한 지점): `queue_runner.rs:506, 513, 600, 646, 729, 763, 800, 839, 1932, 2167, 2355-2367, 2491, 3577-3587`. **이 사이(예: 한 계정의 종목 게시 루프 내부)에는 체크가 하나도 없다.**

### 2-3. 종토 게시는 `spawn_blocking` → tokio가 **abort 자체 불가**
- 계정별 게시는 `tauri::async_runtime::spawn_blocking`(`queue_runner.rs:1966`) 안에서 돈다. 블로킹 클로저는 await 지점이 없어 **tokio가 중간에 끊을 수 없다**. 핸들을 저장해도 소용없다.
- 아이템 단위 병렬 레인 태스크는 `spawn` 후 **JoinHandle을 즉시 drop**(`queue_runner.rs:278, 319`) → 어디에도 저장 안 됨 → 부를 `.abort()` 대상이 없다.

### 2-4. Chrome 종료는 오직 `ChromeHandle::drop`에 묶여 있다
- `ChromeHandle`(`src-tauri/src/auth/chrome.rs:20-24`)이 `child: std::process::Child`·`port`·`user_data_dir`를 보유. `Drop`(`chrome.rs:26-112`)에서 **Windows는 `taskkill /PID <pid> /T /F`(`chrome.rs:49-50`)로 프로세스 트리(헬퍼 자식 포함) 전체를 죽이고** 임시 프로필을 `remove_dir_all`(`chrome.rs:94`)로 지운다.
- 정상 완료 시 `drop(chrome)` 호출: `queue_runner.rs:2053`, `lib.rs:392`, `login.rs:80-81`.
- **PID 레지스트리가 없어**, 특정 큐/계정의 Chrome PID를 밖에서 찾을 방법이 없다(`running_chrome_count`(`chrome.rs:118`)는 마커 `pstmacro-login-`(`chrome.rs:152`) 개수만 셀 뿐 계정 매핑 불가).
- **카페 고정 9222 Chrome**(`lib.rs:494`)은 `Child`를 버려서(`lib.rs:508`) **코드가 아예 안 죽인다**(설계상 사용자가 닫음).

### 2-5. 결론
> 지금은 "실행 중 아이템을 중간에 끊는" 수단이 **전무**하다. kill 기능은 (a) **취소 신호 primitive**(신규)와 (b) **더 촘촘한 협조적 체크포인트**(기존 루프에 삽입)를 넣어, 워커가 스스로 안전 경계에서 멈추고 `drop` 경로로 Chrome을 정상 정리하게 만드는 것이 핵심이다. "프로세스를 난폭하게 죽이는 것"이 아니다(그건 오히려 고아·캡차를 만든다 — 3장).

## 3. ★안전 종료 경계★ — 어디까지 하고 끊어야 문제·캡차가 없나

사용자 핵심 질문에 대한 코드 근거 답. **결론부터**: 끊는 최소 단위는 **글(종목) 1개**다. 진행 중인 종목 1개의 게시 왕복(form POST→add POST→응답)까지는 반드시 끝내고, **다음 종목으로 넘어가기 직전**에 멈춰야 한다.

### 3-1. 단일 종토 글 게시 순서 (영속 write = `(W)`)
| # | 단계 | 위치 |
|---|------|------|
| 6 | `spawn_blocking` per 계정 → `launch_debug_chrome(true)` 격리 Chrome | `queue_runner.rs:1966`, `:2001` |
| 9 | 세션 오픈: Chrome connect → **쿠키 주입(읽기전용)** → in-memory jar 추출 → 로그인확인 GET | `naver_automation.rs:176`, inject `:190` |
| 10 | npay 필수약관 리다이렉트 체인 — Set-Cookie를 **in-memory jar에만** 누적 | `naver_automation.rs:211` → `packet_client.rs:512`, 회전 `:539` |
| 12 | 프로필 보장: status GET → 신규면 **profile-create POST**(멱등) `(W 원격)` | `naver_automation.rs:324` → `packet_client.rs:386`, create `:420` |
| 13 | 글쓰기 **form POST → txId 발급**(세션 내 1회용) | `packet_client.rs:1267` |
| 14 | **★글 게시 add POST★** `/front-api/discussion/add` `(W 원격)` | `packet_client.rs:862`, 성공판정 `:870` |
| 16 | 다음 종목 있으면 **60초 대기** | `discussion_batch.rs:317-320` (루프 `:247`) |
| 17 | 계정 전 종목 끝 → **`drop(chrome)`** = taskkill 트리 + 프로필 삭제 | `queue_runner.rs:2053` → `chrome.rs:26` |
| 18 | 전 계정 outcome 수집 후 **계정 상태 일괄 기록** `(W accounts.json)` | `queue_runner.rs:876`, write `:951` |

**영속 write는 4종뿐**: ⑫⑭(네이버 원격, 우리 디스크 아님), ⑱ `accounts.json`(게시 전부 끝난 뒤 일괄), 알림 로그. **게시 경로는 쿠키 파일을 절대 쓰지 않는다**(읽기만; `cookie_bridge.rs` 전체 write 없음). 쿠키 파일 write는 로그인 `finalize`에서만, **원자적 temp+rename**(`login.rs:217/238`, 실패 시 tmp 제거 `:248`)이라 어느 시점에 죽어도 `cookies/{loginId}.json` **손상 구조적 불가**.

### 3-2. 캡차의 진짜 원인 — 코드가 직접 지목
- **고아 Chrome 헬퍼(렌더러/GPU/crashpad) 누적 = 봇탐지 점수 상승 = 캡차.** `chrome.rs:32-36` 주석이 명시: 고아 누적(15계정 병렬)이 "**캡차(봇탐지 점수 상승)의 유력 원인**". 정상 종료는 `Drop`의 `taskkill /T /F`로 트리 전체를 죽여 잔재를 남기지 않는다.
- 캡차는 **게시 패킷 경로가 아니라 다음 번 로그인 시점**에 뜬다(캡차 로직 전부 `src-tauri/src/auth/login_flow.rs`; 게시 패킷은 `classify_restriction_body`(`packet_client.rs:2272`)로 차단/만료만 가름, 캡차 개념 없음).
- ⇒ 캡차를 안 부르는 유일한 길 = **계정 Chrome을 `drop` 경로로 정상 정리한 상태로 멈추는 것**. 프로세스를 강제로 죽여 `drop`을 건너뛰면 헬퍼 고아가 남아 다음 로그인 캡차 확률↑.

### 3-3. 중복게시
- **영속 dedup 대장이 없다.** "이 종목 이미 게시함" 디스크 마커 없음. 재실행 시 form을 다시 부르면 **새 txId로 또 게시**.
- 지금 중복이 안 나는 이유는 두 가지, 둘 다 "재실행 자체를 안 함"에 의존: (1) 협조적 취소는 add POST 도중엔 절대 발동 못 함(체크가 그룹·배치 경계뿐), (2) 재시작 시 `Running` 아이템은 `pick_next_waiting`(`queue_runner.rs:163-166`)이 안 집음.
- **위험 창**: add POST 전송(`packet_client.rs:862`) 후 ~ outcome 기록(`queue_runner.rs:876`) 전에 **하드 킬**하면 → 글은 네이버에 실렸는데 우리 기록은 비어 있음 → 사용자가 "안 올라간 줄 알고" **수동 재큐잉하면 이중게시**.

### 3-4. 안전 경계 등급 (안전 → 위험)
1. **[가장 안전] 그룹/배치 경계** (`queue_runner.rs:506, 513, 1932`) — 이미 구현된 협조적 취소 지점. 완료 그룹은 잔여 plan에서 빠져 재개해도 중복 0.
2. **[안전] 계정 Chrome `drop` 직후** (`queue_runner.rs:2053` 이후) — 그 계정 프로세스트리·프로필 정리 완료, 다음 배치 전이면 잔재 0.
3. **[안전, 상태 미기록] 세션오픈~add POST 전** (⑨~⑬) — 원격 변경은 프로필 생성(멱등, `packet_client.rs:400` "existent면 통과")까지, 글은 아직 안 나감 → 중복 없음. 단 Chrome 살아있으면 헬퍼 잔재 위험.
4. **[위험] add POST 전송 후 ~ 기록 전** (`packet_client.rs:862` 직후) — 글은 올라갔는데 기록 없는 유일한 창.
5. **[가장 위험] 계정 Chrome 살아있는 전 구간의 하드 프로세스킬** — `drop` 미실행 → 고아 헬퍼 → 다음 로그인 캡차.

> **설계 원칙**: kill은 항상 **①②③에서 멈추도록** 협조적으로 유도하고, **④는 절대 강제로 끊지 않으며**(진행 중 글 1개는 응답까지 받는다), **⑤(하드 프로세스킬)는 협조적 정지가 타임아웃 안에 안 끝날 때의 최후수단으로만**, 그것도 add POST 임계구역이 아닐 때만 발동한다.

## 4. 설계 — 취소 신호 + 2단계 kill

### 4-1. 신규 원시primitive: 큐별 취소 신호
- `RunnerInner`(`queue_runner.rs:55-66`)에 `cancels: HashMap<QueueId, Arc<CancelSignal>>` 추가.
- `CancelSignal { flag: AtomicBool, chrome_pids: Mutex<Vec<u32>>, in_critical: AtomicBool }`
  - `flag`: 협조적 취소 요청.
  - `chrome_pids`: 이 큐가 띄운 Chrome 메인 PID들(강제 에스컬레이션용). `launch_debug_chrome` 성공 직후 등록, `drop` 시 해제.
  - `in_critical`: form POST~add POST 응답까지의 **임계구역** 표시(강제 kill이 이 구간을 건드리지 않게 함).

### 4-2. 협조적 정지(Stage 1, 기본)
- kill 요청 → 해당 큐 `CancelSignal.flag = true` + 디스크 큐에서 항목 제거(`apply_cancel_now` 재사용).
- 워커/게시 루프가 신호를 보는 **체크포인트 추가**(기존 `item_present`와 나란히):
  - `discussion_batch.rs:247` 종목 루프 **매 종목 시작 직전** → 신호 있으면 남은 종목 중단, 현재까지 정상 종료.
  - `discussion_batch.rs:317-320` **60초 대기를 인터럽터블 sleep**(1초 단위로 신호 검사)로 교체 → 대기 중 kill이 near-instant.
  - `execute_item`/`run_forum_targets`/`run_band_targets`/`run_blog_targets`의 기존 `item_present` 지점에서 신호도 함께 검사.
- 루프가 신호를 보고 빠져나오면 `spawn_blocking` 클로저가 정상 리턴 → **`drop(chrome)`(`queue_runner.rs:2053`)이 정상 실행** → taskkill 트리 + 프로필 삭제 → 고아 0.
- `ItemOutcome`에 **`Killed` 변형 추가**(`queue_runner.rs:1430-1439`) → `finish_item`(`:341-366`)에서 `Completed`처럼 항목 제거 + "사용자 종료" 로그.

**정지 지연(latency)**: 최악 = 진행 중 종목 1개의 게시 왕복(수 초) 또는 인터럽터블 대기 1초. 사용자 체감 "칼같이"에 부합하면서 안전.

### 4-3. 강제 에스컬레이션(Stage 2, 최후수단)
- Stage 1 신호 후 **N초(예: 10s) 내 정지 안 되면**(네트워크 홉 hang 등): `CancelSignal.chrome_pids`를 조회해 **`in_critical == false`일 때만** `taskkill /PID <pid> /T /F` 직접 발동.
  - Chrome이 죽으면 블로킹 스레드의 CDP/HTTP 왕복이 즉시 에러 → 클로저가 에러 경로로 리턴 → `drop`은 no-op(이미 죽음)이지만 프로필 정리는 별도 sweep으로 보장.
- `in_critical == true`(add POST 임계구역)면 **강제 kill을 잠깐 보류**하고 임계구역이 풀리면(응답 수신, CDP read/write 타임아웃 `naver_automation.rs:532-537`로 상한) 즉시 실행 → 중복게시·반쪽글 방지.
- CDP 소켓은 read/write 타임아웃이 있어 hang 상한이 존재(`naver_automation.rs:532-537`).

### 4-4. 리소스 정리 체크리스트(kill이 반드시 해제)
| 리소스 | 보유 위치 | 해제 |
|---|---|---|
| Chrome 메인 PID | `ChromeHandle.child` `chrome.rs:21` | `Drop` taskkill `chrome.rs:66/82` (Stage1) / 직접 taskkill (Stage2) |
| Chrome 헬퍼(렌더러/GPU/crashpad) | 개별 추적 안 됨 | Windows `taskkill /T` `chrome.rs:50` |
| 임시 프로필 dir | `ChromeHandle.user_data_dir` | `remove_dir_all` `chrome.rs:94` + Stage2 sweep |
| 디버그 포트(동적 0) | OS | 프로세스 종료 시 해제 |
| CDP 웹소켓/TCP | `CdpClient.socket` `naver_automation.rs:477` | drop 시 OS 회수(타임아웃 상한) |

## 9. 결정 사항 (사용자 확정 2026-07-06)
1. **중복게시 = 경고만.** dedup 자동-skip 대장은 안 만든다. 이번 실행에서 게시 완료한 종목을 종료 로그에 남기고, 같은 plan 재큐잉 시 "이미 N개 게시됨" 경고만 표시.
2. **카페 9222 Chrome = 건드리지 않음.** 카페 게시는 저장 쿠키로 HTTP 통신(`client.rs:59`)이라 그 Chrome을 쓰지 않는다. kill = HTTP 루프 협조취소로 즉시 정지, 9222 공유 인스턴스는 그대로 둔다(같이 죽이면 다른 카페 작업 손상).
3. **ADB 비행기모드 = 토글 원자성 가드.** `toggle_airplane_mode`(`adb.rs:82`)의 ON→OFF 시퀀스는 **중간에 절대 안 끊고 끝까지 실행**(폰이 항상 인터넷 복구 상태로 복귀)한 뒤 중지를 반영. 취소는 토글 전/후 경계에서만 검사. (로그인 IP회전 단계 한정, 게시 중엔 미발생.) 참고: 비행기 ON 동안엔 PC 인터넷(USB테더링)도 끊겨 **Admin 원격 중지 명령이 애초에 도착 못 함**(복구 후 도착) — 구조상 지연이며 정상.
4. **강제 에스컬레이션 = 협조정지 10초 후 taskkill**, 단 **add POST 임계구역(`in_critical`)이면 응답까지 대기**(상한 = CDP read/write 타임아웃 `naver_automation.rs:532`). hang까지 커버해 정지를 보장하되 이중게시·반쪽글은 방지.
5. **원격 중지 단위 = 큐별 + 디바이스 전체 둘 다.** → §10 "중지 명령" 페이지로 구현. 큐 옆 [중지](그 큐만), 디바이스 옆 [중지](그 디바이스 전 큐).

4. 하위가 여러 대여도 **하위별로 독립**(게시 명령과 동일 원칙, 절대 안 섞임).

### 10-2. 실시간 실행큐 인벤토리 (신규 데이터 흐름)
- 하위 에이전트가 **실행/대기 큐 스냅샷**을 (a) 주기적으로 + (b) 상태 변경 시 서버로 보고: `POST /agent/queue-state`(payload = `[{queue_id, kind(종토/카페/밴드/…), postTitle, targetLabel, loginId, state(Running/Waiting), progress:{done,total}}]`). 소스 = 로컬 `list_queue_now`(`queue.rs`)와 동일 데이터.
- 서버는 디바이스별 최신 스냅샷을 보관하고 `GET /devices/:id/queue-state` + **Admin SSE로 실시간 중계**(`hub` admin 스트림). Admin "중지 명령" 페이지가 구독.
- 오프라인/미연결이면 기존 Admin 패턴대로 더미 폴백(화면은 항상 뜸).

### 10-3. 결과보고 "중지" 항목 (`result-report`)
- 하위 **이번 배치** 요약의 성공/보류/대기초과/실패 옆에 **중지 (숫자)** 를 추가.
- **중지 (N)** 펼치면 계정별로: **ID · PW** + **사유** = "**N개 작업 중 M개 성공 후 중지**"(중지 시점까지 성공 개수/전체 개수 기준). 데이터는 에이전트 중지 결과 회신(§5 identity)에 담아 보고.

### 10-4. 원문 로그 (무필터 — 사용자 강조)
- **통신로그(§6)·서버 로그 파일·하위 앱 로그** 모두에, "내가 중지 명령을 내렸다"와 "하위가 실제로 어떻게 멈췄는가"가 **원문 그대로 전부** 남아야 한다. **발췌·필터·선별 금지.**
  - 서버: `POST /admin/kill` 수신 payload 원문 + 하위 회신 원문을 `st.audit`로 기록(감사로그 → Admin 통신로그 SSE + 서버 로그 파일).
  - 하위: **중지를 누른(또는 명령 수신한) 순간부터**의 전 과정(취소 신호 set → 루프 탈출 → `drop(chrome)`/`taskkill` 출력 → 다음 큐 승계)을 tracing에 원문 그대로 남기고, 기존 앱 로그 파이프라인(RingWriter→`/agent/log`→감사로그, #367)으로 서버·Admin 통신로그에 자동 전송.
- 이 원칙은 기존 "네이버 원문 그대로 로그"(#367) 규칙의 연장이다.

- **결과보고 날짜별 분류 ✅ 추가완료** (사용자 요청 2026-07-06) — 하위 이름·"등록 N건" 옆에 **날짜 선택 메뉴**(처음엔 "날짜를 선택하세요"). 서버가 로그인 4분류+중지를 그 날(KST=UTC+9) 버킷에 합산 보관(`AppState.daily`, 최근 90일) → `GET /admin/daily-results` → 날짜를 고르면 그 날의 성공/보류/대기초과/실패/중지만 표시(**절대 날짜 섞임 없음**). 미선택이면 기존 "최신 배치". `add_login_daily`/`add_stop_daily`(login_report·stop_report 핸들러에서 집계), `toDailyView` 단위테스트.
