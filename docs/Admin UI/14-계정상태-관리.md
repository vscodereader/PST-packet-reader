# 📐 설계서: 계정 상태 관리 (Admin) — 하위 계정의 플랫폼·상태 양방향 편집

> **신규 기능.** 파일: `docs/Admin UI/14-계정상태-관리.md`. 03-계정분배의 형제 페이지.
>
> **대원칙:** 계정의 상태(status)·플랫폼(platform) 데이터와 그 변경 로직은 **이미 하위(com
> pstmacro)에 전부 있습니다**(`ipc/accounts.rs`). 그러니 **기존 계정 모델·상태 enum·변경
> 함수를 한 줄도 고치지 않고 그대로 재사용**하고, Admin은 "이 하위의 이 계정을 이 플랫폼·이
> 상태로 바꿔라"는 **명령만** 내려보냅니다. **없는 배선(Admin UI + 명령 스키마 + 하위 조립)만
> 새로 만듭니다.** 코어(`src-tauri` 데스크톱 공용)는 건드리지 않습니다 — 전부 Admin 전용(324).

## 0. 한눈에

**왜 필요한가.** 종토 글쓰기에 성공하면 계정 상태가 **활성(Active) → 대기(Waiting)** 로 바뀝니다
(같은 계정이 연속 게시되지 않게, `accounts.rs:44`). 지금은 이 대기를 **하위 앱에서 사람이 직접**
다시 활성으로 돌려야 합니다. 캡차로 보류(OnHold)된 계정도 마찬가지입니다. 이걸 **Admin에서 원격으로**
하겠다는 것입니다. 더불어 계정의 **플랫폼**(종토였는데 블로그로, 클립이었는데 카페로)도 바꿀 수 있게
합니다.

**한 화면에서:**
- "계정 상태" 페이지(계정 분배 밑)에서 **하위 COM을 선택** → 그 하위에 분배된 **모든 계정**이 뜬다
  (loginId · 현재 플랫폼 · 현재 상태).
- 각 계정의 **플랫폼**과 **상태**를 드롭다운으로 바꾸고 **저장** → 하위 COM에 **똑같이 적용**된다.
- 반대로 **하위 COM에서 상태를 바꾸면 Admin에도 곧(≤4초) 반영**된다(양방향).

## 1. 재사용 지점 — 무엇을·어디서·어떻게 (한 줄도 새로 만들지 않음)

| 재사용 | 위치 | 어떻게 |
|---|---|---|
| 계정 목록(loginId·platform·status) 읽기 | `agent/mod.rs:344` `inventory_body` → `accountRows` | 하위가 이미 4초마다 전체 계정을 `accountRows`(loginId·platform·status)로 서버에 보고. Admin이 폴링해 그대로 표시. **읽기 배선 0.** |
| 상태 변경 로직 | `ipc/accounts.rs:125` `apply_status_by_login_id` | loginId로 매칭해 status 갱신. 하위 명령 핸들러가 그대로 호출(코어 무수정). |
| 상태 enum | `ipc/accounts.rs:40` `AccountStatus` | New/Active/Waiting/OnHold/TimedOut/BadCredentials/Challenge/Relogin/Blocked/Error. Admin은 이 중 **사람이 되돌릴 수 있는** 값만 노출. |
| 플랫폼 enum | `ipc/accounts.rs:71` `Account.platform`(PlatformId) | forum/naver/blog/clip/band. `platform_to_str`/`platform_from_str`(agent/mod.rs:75·88)로 문자열 왕복. |
| 계정 저장소 | `JsonStore<Account>` | 하위가 `store.mutate(...)`로 status·platform을 바꾸면 다음 `inventory_body` 보고에 자동 반영 → Admin에 돌아옴. |
| 서버 명령 릴레이 | `server/src/routes.rs:808` `distribute_accounts` 패턴 | `hub.device_push(uid, payload)`로 하위 SSE에 명령 전송(같은 패턴 복제). |
| 하위 명령 dispatch | `agent/mod.rs:546` `distribute_accounts` 패턴 | `match cmd.type { "update_account_meta" => ... }` 한 갈래 추가(같은 패턴). |

## 2. UI — "계정 상태" 페이지 (계정 분배 밑)

```
계정 상태
├─ [하위 COM 선택]  ← 03-계정분배와 동일한 기기 선택(온라인 하위)
└─ 선택 시: 그 하위의 계정 표 (accountRows 폴링)
   ┌──────────┬──────────────┬────────────┬─────────┐
   │ 계정(masked)│ 플랫폼(select) │ 상태(select) │         │
   ├──────────┼──────────────┼────────────┼─────────┤
   │ ab•••••  │ 종목토론방 ▼  │ 대기 ▼      │         │
   │ cd•••••  │ 네이버블로그 ▼│ 활성 ▼      │         │
   │ ...      │ ...          │ ...        │         │
   └──────────┴──────────────┴────────────┴─────────┘
   [저장]  ← 바뀐 행만 모아 하위에 명령 전송
```

- 계정 = 하위가 보고한 `accountRows` 전부(플랫폼·상태 무관 전체). masked loginId 표시(§10-4-1 `maskId`).
- **플랫폼 드롭다운**: 종목토론방(forum)·네이버카페(naver)·네이버블로그(blog)·네이버클립(clip)·밴드(band).
- **상태 드롭다운**: 활성(active)·대기(waiting)·보류(onHold) — 사람이 되돌릴 수 있는 3종만(하위 앱
  배지 순환 `STATUS_ACCOUNT_CYCLE`과 동일 취지). 나머지(badCredentials/blocked 등)는 로그인 워커가
  판정하는 값이라 **읽기 전용 표시**만 하고 드롭다운 선택지에서 제외.
- **저장**: 폴링본(원래 값) 대비 **바뀐 행만** 모아 하위에 한 번에 전송. 저장 후 폴링이 갱신본을
  다시 읽어 즉석 반영.

## 3. 데이터 흐름 (양방향)

**읽기 (하위 → Admin) — 이미 있음:**
```
하위 JsonStore<Account> → inventory_body(accountRows) → 서버 → Admin 4초 폴링 → 표
```
하위에서 상태를 바꾸면(앱 배지 클릭 등) 다음 보고(≤4초)에 Admin 표가 갱신된다. **신규 배선 0.**

**쓰기 (Admin → 하위) — 신규:**
```
Admin 저장 → POST /admin/accounts/update-meta {deviceId, updates:[{loginId,platform?,status?}]}
  → 서버 hub.device_push(SSE) → 하위 agent "update_account_meta" 핸들러
  → store.mutate: platform·status 갱신(apply_status_by_login_id 재사용 + platform 세팅)
  → 다음 inventory_body 보고에 반영 → Admin 폴링이 확인(왕복 닫힘)
```

## 4. 와이어 계약 (명령 스키마)

**Admin → 서버 (`POST /admin/accounts/update-meta`):**
```jsonc
{
  "deviceId": "…",
  "updates": [
    { "loginId": "ab1234", "platform": "blog", "status": "active" }, // 둘 다 바꿈
    { "loginId": "cd5678", "status": "active" },                     // 상태만
    { "loginId": "ef9012", "platform": "naver" }                     // 플랫폼만
  ]
}
```
`platform`/`status`는 **선택**(생략하면 그 필드는 안 바꿈). 값 도메인: platform ∈ {forum,naver,blog,clip,band}, status ∈ {active,waiting,onHold}.

**서버 → 하위 (SSE payload):** `distribute_accounts`와 동일 구조로 `{ "type":"update_account_meta", "commandId":…, "updates":[…] }`.

**하위 처리(agent):** 각 update에 대해 `store.mutate`로 해당 loginId 계정의 platform(있으면)·status(있으면)를 갱신. status는 `apply_status_by_login_id`(status_msg=None으로 "사람이 되돌림" 표시) 재사용. 통신로그에 "계정 N건 상태/플랫폼 변경(loginId·before→after)" 원문 기록(무필터, 기존 audit 패턴).

## 5. 상태·플랫폼 선택지 (와이어 문자열)

| 상태(라벨) | 와이어 | 비고 |
|---|---|---|
| 활성 | `active` | 정상 게시 가능 |
| 대기 | `waiting` | 게시 성공 후. 게시 목록에서 숨김 |
| 보류 | `onHold` | 캡차 미해결. 게시 목록에서 숨김 |
| (그 외) | 읽기전용 | badCredentials/blocked/… = 워커 판정, 드롭다운 제외 |

| 플랫폼(라벨) | 와이어 |
|---|---|
| 종목토론방 | `forum` |
| 네이버카페 | `naver` |
| 네이버블로그 | `blog` |
| 네이버클립 | `clip` |
| 밴드 | `band` |
