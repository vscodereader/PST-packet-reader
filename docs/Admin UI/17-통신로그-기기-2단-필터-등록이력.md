# 17. 통신로그 기기 2단 필터 — 하위com(machine_id 그룹) → 등록 이력 — #444

- 근거: 사용자 요청(2026-07-20). #441 하위 기기 안정 식별([[16-기기-안정-식별]]) 위에 얹음.
- 코드(예정): `src/admin/features/comm-log/comm-log.tsx`·`comm-log-filter.ts` · 서버 `device_registrations` 이력.

## 문제

재등록할 때마다 랜덤 이름(`ae62db4e`, `2bada9f6`…)의 기기가 쌓여 **어느 물리 컴퓨터인지 알 수 없다.**
통신로그 목록1이 이 랜덤 이름들의 평면 나열이라 식별 불가.

## 원하는 것 (사용자 명세)

- **목록1(컴퓨터)**: `Admin(전체)` · `하위com1` · `하위com2` … — 물리 컴퓨터 단위로 묶어서.
- **목록2(신규, 목록1 옆)**: 목록1에서 `하위com1`을 고르면 → **그 하위com1이 등록/재등록한 여러 컴퓨터
  이름**이 나온다.
- **정렬**: 등록 **날짜순** — 가장 **오래된** 등록이 **맨 위**, 가장 **최근** 등록이 **맨 아래**.

## 핵심 결정

### 무엇으로 "하위com"을 묶나 = machine_id (#441)

랜덤 등록들을 "같은 물리 컴퓨터"로 묶는 유일한 근거는 **machine_id**(#441, Windows MachineGuid).

- 같은 machine_id로 들어온 등록들 = 한 `하위com`.
- machine_id가 **없는**(옛 앱·#442 배포 전 등록) 것은 묶을 근거가 없으므로 **각각 개별 하위com**으로
  폴백(기존처럼 하나씩).
- **전제**: 실제 그룹핑은 #441/#442 **배포 + 하위앱 재설치** 후부터 채워진다. 그전 데이터는 개별로 뜬다.

### 이름 이력이 필요 → 등록 이력 테이블(신규)

#442의 `register_device`는 같은 machine_id면 **하나의 device row로 합친다(upsert)** — 이름은 최신으로
덮어써서 **과거 이름 이력이 안 남는다.** "다양한 이름을 날짜순으로" 보여주려면 **등록할 때마다
append하는 별도 이력**이 필요하다. (운영/결과보고/통신로그의 "기기 1개" 원칙은 그대로 유지 — 이력은
읽기 전용 별도 테이블.)

`device_registrations`

| 컬럼          | 타입        | 설명                                         |
| ------------- | ----------- | -------------------------------------------- |
| id            | UUID PK     |                                              |
| machine_id    | TEXT (null) | 기기 고유값(#441). NULL이면 개별 하위com     |
| device_id     | UUID        | 그 등록으로 매핑된 live device(upsert 후 id) |
| name          | TEXT        | 그 등록의 컴퓨터 이름(또는 하위-XXXX)        |
| registered_at | TIMESTAMPTZ | 등록 시각(정렬 기준)                         |

- `register_device`가 신규/재사용 **양쪽 경로에서** 이력 1건 append.
- 인덱스: `(machine_id)`, `(registered_at)`.

## API

`GET /admin/device-registrations` (운영자 인증) →

```jsonc
[
  {
    "machineId": "MID-1111",
    "deviceId": "ae62…",
    "name": "PC-사무실",
    "registeredAt": "2026-07-19T02:00:00Z",
  },
  {
    "machineId": "MID-1111",
    "deviceId": "ae62…",
    "name": "PC-사무실",
    "registeredAt": "2026-07-20T05:00:00Z",
  },
  {
    "machineId": null,
    "deviceId": "2bad…",
    "name": "하위-2bad",
    "registeredAt": "2026-07-18T09:00:00Z",
  },
]
```

프론트는 이걸 3초/5초 폴링(오프라인이면 빈 배열 → 기존 device 폴백).

## 그룹핑·라벨 로직 (순수 함수, comm-log-filter.ts)

- **하위com = device_id 단위.** #441 안정 식별로 같은 PC는 같은 device_id를 유지하므로(upsert가
  server-side에서 machine_id로 device_id를 고정), 프론트는 **device_id로 묶으면 곧 물리 컴퓨터 단위**가
  된다. (machine_id는 device_id를 고정시키는 근거일 뿐, 프론트 그룹핑엔 직접 안 쓴다.)
- **목록1 = 로그의 device_id들**(`deviceOptions`) + 시스템(있으면) + Admin. 하위com 번호는 `comOrder`로
  **등록이 이른 기기가 앞**(하위com1), 등록 이력 없는 기기는 로그 등장 순 뒤에.
- **목록2(등록 이력)**: `registrationsForDevice(regs, device_id)` = 그 기기의 등록들을 `registered_at`
  **오름차순**(오래된 위) → 라벨 `"{name} · M/D HH:mm"`(`regOptionLabel`). 같은 device_id에 귀속되므로
  **정보 표시용**(로그 필터는 목록1의 device_id + 목록3 날짜로 이미 결정됨).
- **필터**: `filterLines(lines, computer, date)` — computer=ADMIN→빈, 시스템/device_id→그 로그, date→그 날짜.

## 목록형 3단 최종 구조

1. **목록1 컴퓨터**: `Admin(전체)` · 하위com1..N.
2. **목록2 등록**: 목록1 = 하위comN 일 때 활성 → 그 그룹의 등록 이름들(등록일 오름차순) + (비우면 그 com 전체).
3. **목록3 날짜**: 현재 선택(하위com 전체 or 특정 등록)의 로그 날짜(KST, 최신순).

### 필터 결과

| 목록1    | 목록2(등록)     | 목록3       | 보이는 로그            |
| -------- | --------------- | ----------- | ---------------------- |
| Admin    | (비활성)        | (비활성)    | 아무것도(초기 빈 화면) |
| 시스템   | (비활성)        | (없음/날짜) | 시스템 로그 (+날짜)    |
| 하위comN | 정보(이름 이력) | (없음)      | 그 컴퓨터 전체         |
| 하위comN | 정보(이름 이력) | 날짜        | 그 컴퓨터의 그 날짜    |

- 목록2는 그 하위com이 등록/재등록한 **이름 이력을 날짜순으로 보여주는 정보용**(로그 필터는 목록1의
  device_id + 목록3 날짜로 결정). 목록1 바뀌면 목록2·3 초기화. [내보내기]는 현재 필터 로그만.

## 전제·한계 (다시)

- machine_id 그룹핑이므로 **#442 배포 + 하위앱 재설치 후** 실제 하위com 묶임이 생긴다. 그전엔 개별.
- 같은 PC 재등록 시 COMPUTERNAME이 안 바뀌면 목록2의 "여러 이름"은 같은 이름이 날짜만 다르게 반복될 수
  있다(랜덤 이름 시기의 흔적을 보는 용도가 큼).
