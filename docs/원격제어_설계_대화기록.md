#### 설계의 핵심 합의 (당시 문서 상태)

- **통신**: 하위가 SSE(`GET /agent/stream`)로 명령 수신, 결과·하트비트·IP는 HTTP POST. 연결을 여는 쪽은 **항상 하위**(CGNAT·IP 변경 대응). 신원은 IP가 아니라 **기기토큰(device_id)** 으로.
- **계정 소유(A-1 확정)**: Admin 스테이징 → 분배 시 하위로 **MOVE**(보낸 계정은 Admin에서 사라짐). 쿠키·로그인은 중앙 금지, 각 하위가 자기 폰 IP로.
- **분배**: 체크박스 수동 선택 → **균등+랜덤**. 기존 `distributeStocksEvenly()` 재사용 + 분배 직전 셔플 1줄만 신규.
- **결과 보고(§10-4)**: 성공/보류/대기초과/실패 4분류, 실패는 자동삭제(보고 후), 배치별 상세 + 누적 합계.
- **권한(§5)**: 운영자=SuperAdmin 동일 권한, 단 "운영자 삭제"만 SuperAdmin 전용. 부트스트랩 `Superadmin`/`Superadmin` → 강제 비번 변경. 비번 분실 복구·이메일 없음.

#### 부차 발견

`docs/설계.md:Zone.Identifier` 라는 빈 파일이 untracked로 존재 — Windows 다운로드 찌꺼기.

## 2. 두 번째 요청 — "이 설계서로 구현 시, 임의 판단 가능한 곳 vs 봐도 설계 모르겠는 곳은? 기존 로컬코드 싹 다 읽고 답하라"

### 접근

설계서가 인용한 구체 파일·함수·라인이 실제로 존재하고 인터페이스가 명확한지부터 검증하기 위해, **5개 병렬 탐색 에이전트** 투입:

- A. Auth + IP 로테이션 + 로그인 결과 (Rust)
- B. 계정 데이터 + 엑셀 임포트 + 삭제 + 쿠키 + 저장 (Rust)
- C. 선택 로그인/종토 + queue_runner + 명령 와이어링 + lib.rs
- D. 프론트엔드 — IPC transport seam + accounts.tsx + 분배 헬퍼 + features 구조
- E. 기술 스택/빌드/서버 인프라/의존성

### 에이전트 E 결과 — 스택/빌드/서버 인프라

- **구조**: 루트 `Cargo.toml` 없음 = **단일 크레이트**(워크스페이스 아님). `server/` 형제 크레이트 추가하려면 **워크스페이스 전환 필수**.
- **백엔드 기존 의존성(재사용 가능)**: `tokio(full)`, `reqwest 0.12(blocking,json,rustls-tls,gzip)`, `serde/serde_json`, `thiserror`, `tracing(+subscriber,+appender)`, `chrono`, `hmac/sha2/base64`(Band HMAC), `tungstenite 0.21`(forum WS).
- **백엔드 없어서 추가해야 함(net-new)**: 웹 프레임워크 `axum`, SSE(`tokio-stream`/axum 내장), DB(`sqlx` 또는 `rusqlite`), JWT(`jsonwebtoken`), 비번 해시(`bcrypt`/`argon2`), `uuid`/`rand`, at-rest 암호화(`aes-gcm`/`chacha20poly1305`).
- **프론트**: React 19.2.7 + Vite 7.0.4 + Mantine 9. `@tauri-apps/api ^2`, `@tauri-apps/plugin-dialog ^2.7.1`. **EventSource/SSE·HTTP 클라이언트·상태관리 라이브러리 없음** → 브라우저 네이티브 `EventSource`/`fetch`로 충분, 상태관리는 선택(zustand).
- **tauri.conf.json**: 데스크톱 전용. CSP `connect-src 'self' ipc:` → 웹 모드면 서버 origin 추가 필요.

## 5. 다섯 번째 — 사용자가 인프라 질문들의 의미를 모름 → 개념 설명

사용자 질문(요지): "서버를 어디 띄우나? / 고정 공인 IP가 회사 랜선 IP를 말하나? / TLS·자체서명·Let's Encrypt·사내 CA가 각각 뭐냐? / outbound 접속이 매크로 돌아가냐는 거냐? / Admin 웹 같이 서빙이 무슨 소리냐 — 랜선 꼽으면 고정 IP인데."

### Claude의 정정·설명

#### 먼저: SSE가 뭐냐

기존 매크로는 각 컴퓨터가 따로 도는 구조. Admin이 하위에 명령을 보내려면 둘 사이 **연결된 선**이 필요 = SSE.

- 하위가 Admin 서버에 **전화를 걸어 안 끊고 들고 있음**(SSE 연결).
- Admin은 그 **열린 전화기에 대고** "로그인 해"라고 말함 → 하위가 듣고 실행.
- 하위가 결과 보고는 전화 말고 **따로 문자(POST)**.
- 왜 하위가 거느냐: 하위는 IP가 계속 바뀌어 Admin이 먼저 못 찾아감 → **주소 안 바뀌는 Admin 쪽으로 하위가 항상 찾아가 전화**. (§3·§4)
- 결론: **"중앙 서버"라는 새 프로그램이 하나 떠 있어야 함.** 기존 매크로엔 없던 것.

#### ① 서버 위치 + ⑤ Admin 웹 서빙 = 사실상 같은 질문, 답 거의 정해짐

중앙 서버 프로그램을 **어느 컴퓨터에서 실행하냐**의 질문. 당신 환경이면 **회사 랜선 꽂힌 Admin 컴퓨터 한 대**가 웹 화면도, 하위 접속 서버도 겸하는 게 자연스러움. "별도 서버"=클라우드/타 컴퓨터(불필요).

#### ② 고정 공인 IP vs 도메인

- 공인 IP = 인터넷에서 그 컴퓨터를 가리키는 주소. **회사 랜선 IP가 그거 맞음.**
- 하위가 찾아가려면 이 주소를 앱에 박아둬야 함. 숫자 IP vs 도메인 선택.
- 함정: 회사 랜선이라고 항상 고정은 아님. "고정 IP 계약"만 안 바뀜. 바뀌면 하위 전부 길 잃음. 그래서 도메인이 안전(IP 바뀌어도 도메인만 가리킴 갱신).

#### ③ TLS / 인증서

- TLS = `https://`의 자물쇠. 오가는 데이터(ID/PW) 암호화. 안 쓰면 평문 노출 → 켜는 게 맞음.
- 인증서 = 서버 신분증. TLS 켜려면 필요.
  - 자체서명: 직접 만든 신분증. 공짜·즉시, 브라우저 경고. 내부용 그럭저럭.
  - Let's Encrypt: 무료 신뢰 인증서. **도메인 필요.**
  - 사내 CA: 회사 자체 발급 체계(큰 회사).

#### ④ outbound 접속 — 우선순위 오판 인정

매크로/로그인 얘기 아님. 하위가 서버에 거는 SSE 연결이 KT 등 테더링 망에서 막히냐는 것. 폰으로 웹서핑 되면 거의 100% 됨(둘 다 outbound) → **사수 질문 아님, 구현 후 테스트로 끝. 🔴 과했음, 제거.**

## 6. 여섯 번째 — 사용자 정정 + 파이프 구조·중앙 서버 프로그램 질문

사용자 핵심 발언:

- "인프라팀 없는 회사라 내가 다 개발한다. 그래서 묻는 거다."
- "SSE 구조면 **파이프가 2개**. 하나는 Admin이 만든 파이프, 다른 하나는 하위가 만든 파이프. IP 변동되면 하위 파이프가 일회용처럼 폐기되고 새 파이프 구축되는 거 아니냐?"
- "회사 랜선은 IP 안 바뀐다(바뀌려면 VPN 등 켜야 하는데 Admin은 안 켬). 기존 그대로 유지 + Admin은 웹으로 배포·추가."
- "그럼 Admin 실행하면 중앙서버 프로그램이 같이 실행되는 구조냐? 하위에서 이벤트 발생하면 중앙서버로 말해줘야 하는데, 이 중앙서버 프로그램에 기록되는 거냐?"

### Claude 답

#### 정정: 인프라팀 얘기는 헛다리

인프라팀 없고 직접 만든다 → TLS·인증서·서버 전부 **개발 결정**. 사수 질문에서 빼고 우리가 정할 기술 항목으로 이동. 사수엔 _업무/정책/운영_ 결정만 남김.

#### 파이프 2개 이해 — 맞음 (§3·§4-1)

- **파이프 ①** = 하위가 연 것(`GET /agent/stream`). 명령 받는 선. IP 바뀌면 끊김→새로 엶. 서버가 기기토큰으로 같은 하위 인식 → **죽은 파이프를 새 파이프로 갈아끼움**(라우팅 표). ← "일회용 폐기·재구축" 맞음.
- **파이프 ②** = Admin 브라우저가 연 것(`GET /admin/stream`). 상태·결과 실시간 받는 선. Admin 고정 IP라 안 끊김.
- 둘 다 클라이언트가 서버로 거는 것, 가운데 중앙 서버에 꽂힘.
- 주의: 명령은 파이프 ②로 안 감. Admin은 **POST**로 서버에 던지고 서버가 파이프 ①에 얹어 하위로 내려보냄. 파이프 ②는 받기 전용.
- 회사 IP 안 바뀜 확정 → **하위 앱에 IP 숫자 직접 박으면 됨, 도메인 안 사도 됨.** (②번 해결)

#### 핵심: 중앙 서버 프로그램 구조

배포 프로그램은 **딱 2종류**:

```
[회사 랜선 컴퓨터 (고정 IP)]
  ▶ 중앙 서버 프로그램 1개 (신규, Rust/axum)  ← 이거 하나만 띄움
     ├ 역할 A: 운영자에게 Admin 웹페이지(HTML/JS) 서빙
     ├ 역할 B: SSE 허브 (파이프 ①·② 둘 다 여기 꽂힘)
     └ 역할 C: DB (운영자·기기·토큰·감사로그·계정 스테이징)
  운영자는 브라우저로 서버 주소 접속 → Admin 화면이 뜸

[하위 컴퓨터 (폰 테더링, IP 바뀜)]
  ▶ 기존 pstmacro 데스크톱 앱 + 에이전트 레이어 (1개 프로그램)
```

**Q. Admin 실행하면 중앙서버가 같이 실행되냐?** → 거꾸로. "Admin"이라는 별도 실행 프로그램은 없음. 회사 컴퓨터에서 **실행하는 건 중앙 서버 한 개**, 그 서버가 운영자에게 Admin 웹화면을 브라우저로 내려줌. 운영자가 **브라우저로 서버 주소 열면 그게 Admin 실행**(웹사이트 원리). 이게 "기존 유지 + Admin은 웹 배포·추가"와 일치하고 제일 단순(서버 하나가 웹+API+SSE+DB 다 함).

**Q. 하위 이벤트가 중앙서버 프로그램에 기록되냐?** → 네. 하위가 일 생기면(로그인 결과·IP 변경·하트비트·분배 보고) **POST로 서버에 보냄**. 서버는 동시에 둘:

1. **DB에 기록**(감사로그 + 보고 사본; §7: 감사로그·기기·토큰은 서버 DB 원본).
2. **파이프 ②로 Admin 브라우저에 실시간 푸시**(운영자 즉시 확인).
   → 기록(DB) + 중계(화면) 둘 다. 단 §7대로 **쿠키·게시큐는 서버로 안 보내고 하위 로컬에만**; 서버엔 보고·감사 사본만. 계정 ID/PW는 분배 전 서버, 분배 후 하위로 MOVE.

## 7. 일곱 번째 — IP 하드코딩 여부 + Admin 페이지 IP/연결 확인 질문

사용자 질문: "회사 IP 안 바뀐다 → 하위 앱에 IP를 **하드코딩**해야 하나? 이 분야를 몰라서 묻는다. Admin 페이지엔 회사 IP를 넣는 구조나, 현재 랜선 IP가 뭔지·연결됐는지 확인하는 게 들어가야겠네?"

### Claude 답

#### 1. 하드코딩? → 아니, **설정값**으로

코드에 IP 박으면(하드코딩) 주소 바뀔 때 전 하위 재빌드·재설치해야 함 → 나쁨. 대신 **하위 앱에 "서버 주소" 입력칸(설정값)**. 설치 때 운영자가 1회 입력 → 앱이 파일에 저장(기존 `JsonStore` 재사용 가능).

```
[하위 앱 설정]
 서버 주소: [ http://123.45.67.89:8080 ]   ← 설치 때 1회
 기기코드:  [ 8237 ]                        ← 등록용(§6)
            [ 연결 ]
```

#### 2. Admin 페이지 — 직감 맞음, 방향만 정정

- **(A) "회사 IP를 넣는 구조"** → 거꾸로. 서버는 이미 그 컴퓨터에서 도니까 IP 입력 불필요. **서버가 자기 주소를 자동 표시**:
  ```
  ▶ 이 서버 주소: http://123.45.67.89:8080
    "각 하위 앱에 이 주소를 입력하세요"  [복사]
  ```
  운영자가 복사 → 하위 설정칸에 붙여넣음.
- **(B) "연결 확인"** → 정확히 맞음. 설계 §4 상태머신 + §10-3의 **하위 목록(연결 상태·IP 표시)**:
  ```
  ● 하위A  online  IP 1.2.3.4  방금 전
  ● 하위B  online  IP 5.6.7.8  3초 전
  ○ 하위C  오프라인 ―         꺼짐
  ```
  하위가 파이프 ① 열고 하트비트 보내면 online, IP 바뀌면 갱신, 끊기면 오프라인. 이미 설계에 있음.

#### 3. ⚠️ 직접 만들면 꼭 걸리는 함정 — 내부 IP vs 공인 IP

```
인터넷 ── [공유기/모뎀] ── 회사 컴퓨터들
            (공인 IP)        (각자 192.168.x.x = 내부 IP)
```

- **공인 IP** = 인터넷에서 보이는 주소(=회사 랜선 고정 IP). **하위가 입력할 진짜 주소.**
- **내부 IP**(192.168.x.x) = 회사 안에서만 통함. 하위(회사 밖 테더링)는 이걸로 못 찾음.
- 처리:
  1. 서버가 보여줄 주소는 **공인 IP**여야 함. 마침 폰 IP 알아낼 때 쓰는 `ipify`(`fetch_external_ip`, `adb.rs`)를 **재사용**해 서버 공인 IP 표시 가능.
  2. **포트포워딩**: 공유기 뒤에 서버 PC가 있으면, 밖→서버로 전달하라고 공유기에 1회 설정(예: "8080 → 192.168.0.5"). 안 하면 공인 IP로 와도 공유기에서 막힘.
  3. 공유기 없이 랜선이 공인 IP를 직접 받으면 2번 불필요.
- → **"회사 인터넷에 공유기가 있냐(=포트포워딩 필요하냐)" 한 번 확인** 필요.

**정리**: 하드코딩 ❌ → 하위 앱 설정칸 1회 입력 ✅ / Admin은 회사IP 입력받는 게 아니라 자동 표시 + 연결된 하위 목록·상태 ✅ / 함정: 하위 입력 주소는 공인 IP, 공유기 있으면 포트포워딩 1회 ⚠️.

## 8. 현재까지의 미해결·확인 대기 항목 (대화 종료 시점)

### 사용자가 확인해 줘야 할 환경 사실

- 회사 랜선이 **고정 공인 IP 계약**인지(사용자: "안 바뀌는 걸로 안다" — 잠정 확정).
- 회사 인터넷에 **공유기가 있는지**(→ 포트포워딩 필요 여부). **미확인.**

- 동시 조작 충돌 정책, ROTATING 중 명령 정책, 재등록 토큰 무효화.
