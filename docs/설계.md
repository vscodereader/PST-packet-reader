# Admin–하위 컴퓨터 원격제어 계획서 (SSE 기반)

- 작성일: 2026-06-26
- 작성자: vscodereader (Claude 협업)

- 관련 메모리: 원격제어=중앙서버+에이전트(CGNAT/USB테더링) 방향

---

## 1. 배경 / 목적

### 현재 구조

- pstmacro는 **1대의 컴퓨터에 설치되어 각 사람이 직접 실행**하는 Tauri(데스크톱) 앱이다.
- 각 컴퓨터는 **핸드폰 USB 테더링(모바일 데이터)** 으로 인터넷에 연결되며, ADB IP 로테이션으로 **공인 IP가 비주기적으로 바뀐다**.
- 네이버 로그인은 CDP(눈에 보이는 Chrome)로 수행하고, 게시(카페·블로그·밴드·종토방·클립)는 로컬에서 실행된다.

### 목표

- **Admin 컴퓨터 1대**에서 **여러 하위 컴퓨터**를 등록·모니터링·원격제어한다.
- Admin에서 명령을 보내면 하위가 실행하고 **결과를 그때그때 Admin으로 회신**한다.
- IP가 계속 바뀌는 환경에서 **연결 상태·IP 변경·재연결(retry)을 Admin에서 확인**할 수 있다.
- **계정 ID/PW를 서버에 중앙 집중 저장**하고 시스템이 **여러 하위에 자동 분배**한다(예: 1000개 → 10대 × 100개). 각 하위는 **할당받은 계정만 자기 폰 IP로 로컬 로그인**하고, **쿠키·게시큐는 하위 로컬에 그대로 유지**(서버 전송 안 함). (§7·§10-2)
- 사수 지시: **Admin은 웹으로 배포**하고, 기존 pstmacro 기능을 살린다. "SSE만 추가하는 느낌"으로 기존 코드 무손상.

### 비목표(이번 범위 아님)

- 하위 컴퓨터 자동 재부팅/원격 전원제어 (앱이 꺼지면 **사람이 직접 켜러 감**).
- **쿠키·게시큐**의 중앙 집중 저장 (쿠키 본문은 서버로 보내지 않고 하위 로컬 유지, 아래 §7). ※단 **계정 ID/PW 목록은 중앙 풀로 저장·분배** — 이번 범위에 포함(목표, §7·§10-2).
- **중앙(한 곳)에서 몰아서 로그인** 후 쿠키를 하위에 배달하는 방식 (네이버 쿠키는 로그인 당시 IP·기기에 묶여, 발급 IP ≠ 사용 IP면 안티봇에 차단됨 → 로그인은 반드시 각 하위가 자기 폰 IP로, §10-2).
- 기존 플랫폼 자동화 로직(카페/블로그/밴드/종토/클립) 변경.

## 2. 환경 / 네트워크 전제

| 항목           | 내용                                                                                                                                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin          | **랜선 + 고정 IP**, IP 안 바뀜. 서버 역할 가능. **웹으로 배포**.                                                                                                                                               |
| 하위           | 핸드폰 USB 테더링(모바일 데이터), 공인 IP 비주기적 변경. **outbound 접속만** 가능(CGNAT 무관).                                                                                                                 |
| 연결 방향      | **연결을 여는 쪽은 항상 하위.** 하위가 서버로 SSE 스트림을 열어두고(명령은 이 파이프로 내려옴) + 결과는 HTTP POST로 올림. 서버는 하위로 **새 연결을 먼저 열지 못함**(하위 IP가 계속 바뀌고 CGNAT라 도달 불가). |
| IP 변경 트리거 | 네이버 로그인 시 ADB 디바이스 off→on → 모바일 데이터 재할당 → 공인 IP 변경 → 연결 일시 단절.                                                                                                                   |

핵심: **하위는 항상 "찾아가는" 쪽**이므로 IP가 바뀌어도 outbound 재접속만 되면 복구된다. 서버(Admin)는 고정 주소라 하위가 언제든 다시 찾아올 수 있다.

> **"Admin이 하위를 직접 찌르지 않는다"의 정확한 의미** — Admin이 하위로 *새 TCP 연결을 새로 여는 것*이 불가능하다는 뜻이지, 명령을 안 보낸다는 뜻이 아니다. 명령은 분명히 Admin→하위로 가지만, **하위가 미리 열어둔 SSE 파이프를 타고** 내려간다. (서버는 그 파이프에 명령을 얹기만 함)

## 3. 통신 방식 — SSE(단방향) + HTTP POST(회신)

SSE는 **서버→클라이언트 단방향**이다. 양방향처럼 동작시키려면 **돌아오는 길을 일반 HTTP POST**로 구성한다(표준 패턴).

> **누가 서버이고 누가 연결을 여는가 (가장 헷갈리는 지점)**
>
> - **서버 = Admin**, **클라이언트 = 하위.** SSE의 데이터는 서버→클라이언트로 흐르지만, 그 **연결을 여는 쪽은 클라이언트(하위)** 다.
> - 하위가 먼저 `GET /agent/stream`으로 **연결을 열어두면**, Admin(서버)이 그 열린 파이프로 **명령을 흘려보낸다.** 즉 "로그인 해" 명령은 `Admin 웹 → Admin 서버 → (하위가 연 SSE 파이프) → 하위` 로 도착한다. 명령은 확실히 Admin→하위 방향이다.
> - 하위가 무언가 보낼 때(결과·하트비트·IP·기기등록)는 SSE가 아니라 **별도 HTTP POST** 를 쏜다. SSE 한 줄로는 못 올리기 때문.

```
                    ┌──────────────────────────────────────────┐
                    │        Admin 서버 (랜선·고정IP, 웹배포)         │
                    │   axum + SSE 허브 + 인증DB + 기기DB + 감사로그   │
                    └──────────────────────────────────────────┘
       SSE: 명령 수신 ▲│ POST: 결과·하트비트·IP   ▲│ SSE: 실시간 상태/결과
                    │▼                          │▼ POST: 명령 발행
       ┌──────────────────────┐        ┌──────────────────────────┐
       │   하위 컴퓨터 (에이전트)    │        │   Admin 웹 (운영자 브라우저)      │
       │ 기존 pstmacro 풀 UI +    │        │  기존 React UI 재사용 +         │
       │ 에이전트 레이어            │        │  관리화면(인증·기기·모니터링)       │
       │ 폰 USB테더링/모바일데이터    │        │                              │
       └──────────────────────┘        └──────────────────────────┘
```

### 3개의 통신 경로

1. **하위 → 명령 수신 (SSE)**: 하위가 `GET /agent/stream`으로 SSE 스트림을 열어둔다. Admin이 명령을 발행하면 서버가 **해당 하위의 스트림으로 push**한다.
2. **하위 → 결과 회신 (POST)**: 명령마다 `commandId` 부여. 하위가 진행률/최종결과/하트비트/현재 IP를 **POST**로 서버에 올린다. 서버는 이를 Admin 스트림으로 중계 → "결과를 그때그때 Admin으로" 충족.
3. **Admin → 명령 발행 (POST) + 상태 수신 (SSE)**: Admin 웹이 `POST /devices/{id}/commands`로 명령을 발행하고, `GET /admin/stream` SSE로 모든 하위의 상태·결과를 실시간 수신한다.

서버는 **허브**: Admin 명령을 대상 하위의 SSE로 라우팅하고, 하위 결과/상태를 구독 중인 Admin SSE로 중계한다.

## 4. 디바이스 상태 머신 (IP 변경·연결 핵심)

```
   [미등록]
      │ 기기코드 등록
      ▼
   [온라인/준비] ──명령 수신──▶ [실행중] ──완료/실패──▶ [온라인/준비]
      ▲   │
      │   │ 네이버 로그인 등 IP 로테이션 직전 (하위가 먼저 알림)
      │   ▼
      │ [IP변경중(ROTATING)]  ← 이 동안 Admin은 명령 버튼 비활성화
      │   │ ADB off→on, SSE 끊김, 백오프 재시도(retry)
      │   ▼
      └─[재연결] ──새 IP POST──▶ [온라인/준비] (Admin에 바뀐 IP 표시)

   하트비트 타임아웃 → [오프라인/꺼짐]  ← 사람이 직접 켜러 감
```

### 상태별 동작

| 상태          | 의미                      | Admin UI                       |
| ------------- | ------------------------- | ------------------------------ |
| 미등록        | 기기코드 미등록           | 목록에 없음                    |
| 온라인/준비   | SSE 연결됨, 하트비트 정상 | 명령 가능(버튼 활성)           |
| 실행중        | 명령 수행 중              | 진행률 표시, 중복 명령 차단    |
| **IP변경중**  | 하위가 로테이션 직전 통보 | **명령 버튼 비활성화**         |
| 재연결        | SSE 끊김, 재시도 중       | "재연결 중…" 표시, 명령 비활성 |
| 오프라인/꺼짐 | 하트비트 타임아웃         | "꺼짐" 표시, 직접 켜러 가야 함 |

### IP 변경 시나리오 (가장 중요한 요구)

> 대입한 현행 로그인 IP 변경 구조: **비행기모드 ON → `adb shell ping 8.8.8.8` 실패(끊김 확인) → 비행기모드 OFF → IP 확인 API로 공인 IP 변경 확인 → 안정화.** 이 구간 전체가 아래 3~5번이다.

1. 하위 online, **SSE 파이프 열려있음.** Admin이 **네이버 로그인** 명령 발행 → 파이프로 하위 도착.
2. 하위가 로그인 시작 → IP 로테이션 **직전(아직 인터넷 살아있을 때) `ROTATING` 상태를 POST** → 서버 → Admin push → **Admin UI에서 그 하위 명령 버튼 비활성화**.
3. 비행기모드 ON → 인터넷 끊김 → **SSE 파이프 끊김.** 이 동안 하위는 명령을 받지도 POST를 보내지도 못함.
4. 비행기모드 OFF → IP 확인 → 안정화. 하위 에이전트가 **백오프 재시도(retry)** 로 ★**다시 SSE 연결을 엶**(= "하위가 Admin을 직접 찾아감". 항상 연결을 여는 쪽은 하위).
5. 재연결 성공 → 하위가 **새 IP + `온라인` 상태를 POST** → Admin이 **바뀐 IP 표시 + 명령 버튼 재활성화**.
6. 로그인 결과(성공/캡차/실패)를 `commandId` 결과로 POST → Admin 표시.

> 하위는 IP 변경 중에는 명령을 받지 않으며(3번, SSE 끊긴 상태), Admin도 그 동안 명령 발행 UI가 비활성. 재연결(4번)이 완료된 뒤에만 명령 가능.

### 4-1. 재연결 메커니즘 — 핸드폰 IP가 바뀐 뒤 하위가 서버를 "어떻게 다시 찾아가는가"

> 핵심 한 줄: **하위의 IP는 바뀌어도 목적지(Admin 서버) 주소는 고정**이라, 하위는 *늘 같은 주소로 다시 접속*하고, 자기가 누구인지는 *IP가 아니라 기기토큰*으로 증명한다. 그래서 IP가 아무리 바뀌어도 "찾아가는 길"은 변하지 않는다.

**(1) 목적지는 고정값 — 하위 IP와 무관**

- 하위 설정에 **Admin 서버 주소를 사전에 박아둔다**(`ADMIN_SERVER_URL` = Admin의 고정 IP 또는 도메인. Admin은 랜선·고정 IP라 안 바뀜).
- 재연결이란 결국 **같은 URL로 다시** `GET {ADMIN_SERVER_URL}/agent/stream` 요청을 여는 것. 하위 자신의 IP가 1.2.3.4 → 5.6.7.8로 바뀌어도, "어디로 가야 하나"는 그대로다. (TCP 출발지 IP만 바뀔 뿐 목적지는 동일)

**(2) 신원은 IP가 아니라 기기토큰으로**

- 재연결 요청에 `Authorization: Bearer <device-token>`(§6 등록 때 받은 장기 토큰)을 실어 보낸다.
- 서버는 **토큰 → `device_id` 매핑**으로 "이 스트림이 어느 하위인지" 식별한다. **출발지 IP는 식별에 쓰지 않는다**(어차피 매번 바뀌므로). → 새 IP로 접속해도 서버는 같은 기기로 인식.

**(3) 언제 재연결을 시도하나 — 현행 로테이션 코드에 직접 물림**

현행 `toggle_airplane_mode()`(`src-tauri/src/auth/adb.rs`)가 이미 "네트워크 복구 + 새 IP 확정" 신호를 만든다:

```
toggle_airplane_mode():
  before = fetch_external_ip()          # api.ipify.org (현재 공인 IP)
  비행기모드 ON
  wait_until_phone_offline()            # ping 폴링으로 실제 끊김 확인
  비행기모드 OFF
  wait_for_internet_connection()        # 인터넷 복구 대기  ← 여기서부터 outbound 가능
  after = wait_for_ip_change(before)    # ipify 폴링으로 새 공인 IP 확정
  return IpRotation { before, after }   # ★ 이 반환 시점 = 재연결 트리거
```

→ 에이전트는 **`toggle_airplane_mode()`가 `after`(새 IP)를 반환한 직후** 재연결을 시작한다(이때 비로소 인터넷이 살아있고 IP도 확정됨). 곧바로 `GET /agent/stream` 재오픈 + `POST /agent/heartbeat { ip: after, state: "online" }`.

**(4) 안전망 — 백오프 재시도 루프**

- 위 트리거와 별개로, 에이전트는 **SSE 스트림이 끊긴 것을 감지하면 항상 재연결 루프**를 돈다: `1s → 2s → 4s → 8s → … → 최대 30s` 백오프로 **무한 재시도**.
- 아직 네트워크가 안 살아있으면 연결 실패 → 다음 백오프까지 대기 후 재시도. 살아나는 순간 성공. (서버가 잠깐 죽어도 동일하게 부활 시 자동 복구)

**(5) 서버측 재부착(re-attach)**

- 서버는 `device_id → 현재 활성 SSE 송신핸들`(채널) 맵(= **라우팅 표**)을 유지한다.
- 같은 토큰의 **새 스트림이 들어오면 옛 핸들을 폐기하고 새 핸들로 교체**한다(기기 신원은 그대로, 연결만 갈아끼움). 직후 Admin 스트림으로 `{device_id, 새 IP, online}` push → Admin UI가 바뀐 IP 표시 + 명령 버튼 재활성.
- 끊긴 동안 서버는 그 기기를 `재연결(RECONNECTING)`로 두고, **하트비트 타임아웃(예: N초)** 을 넘기면 `오프라인/꺼짐`으로 전환.

> **"새 파이프를 어떻게 찾아가는가" = IP가 아니라 `device_id`로 찾는다.** Admin은 IP를 몰라도 됨 — 항상 `device_id`로만 지목하고, "그 번호의 지금 파이프"는 서버 라우팅 표가 연결해 준다. 하위가 매 연결마다 기기토큰을 제시 → 서버가 표를 최신으로 덮어쓴다. (교환원 비유: Admin="철수한테 연결" → 서버가 *철수의 지금 번호*로 이어줌)
>
> ```
> 서버 라우팅 표 (device_id → 현재 살아있는 파이프)
> ─────────────────────────────────────────────
> 하위A (토큰 aaa) → 파이프#41  (지금 IP 5.6.7.8)   ← IP 바뀌며 #17에서 교체됨
> 하위B (토큰 bbb) → 파이프#23  (지금 IP 9.9.9.9)
> 하위C (토큰 ccc) → (없음, 재연결 중)
>
> IP 변경: 하위A #17 죽음 → 토큰 aaa로 #41 새로 옴 → 표를 #41로 덮어씀(헌 #17 폐기)
> 명령 발행: Admin "하위A 로그인" → 서버가 표에서 하위A 칸(#41)에 명령 흘려넣음
> ```

**(6) 명령 유실·중복 방지**

- ROTATING 구간엔 Admin 명령 발행 UI가 막혀 있어 그 사이 새 명령이 쌓일 일이 거의 없다.
- 그래도 끊긴 사이 발생한 이벤트를 놓치지 않도록 **SSE 표준 `Last-Event-ID`** 를 쓴다: 하위가 마지막으로 받은 이벤트 ID를 재연결 요청 헤더에 실으면, 서버가 그 이후 이벤트만 재전송.
- 모든 명령은 **`commandId` 멱등** 처리 → 혹시 중복 전달돼도 같은 명령은 한 번만 실행.

**(7) 엣지 케이스**

- 토큰 만료/무효 → 서버가 `401` → 하위는 SSE를 안 열고 **재등록(§6) 안내** 상태로 전환.
- 안정화가 끝났는데도 계속 실패 → 백오프 무한 재시도(루프 (4))로 버팀, 사람이 개입할 필요 없음. 단 앱 자체가 꺼지면 하트비트 타임아웃으로 Admin에 `꺼짐` 표시 → 사람이 직접 켜러 감.

```
[하위] toggle_airplane_mode() 반환(after IP 확정)
   │
   ├─▶ GET {ADMIN_SERVER_URL}/agent/stream     (Authorization: Bearer <device-token>,
   │                                             Last-Event-ID: <마지막 이벤트 ID>)
   │        │ 실패(아직 네트워크/서버 미복구)
   │        └─▶ 백오프(1→2→4→…→30s) 후 재시도 ──┐
   │                                            │
   │        성공 ◀───────────────────────────────┘
   ▼
[서버] 토큰→device_id 식별 → 옛 핸들 교체(re-attach) → Last-Event-ID 이후 이벤트 재송신
   │
   └─▶ Admin 스트림으로 {device_id, 새 IP, online} push → Admin UI 갱신·버튼 재활성
[하위] POST /agent/heartbeat { ip: after } + 직전 명령 결과 POST(commandId)
```

## 5. 인증 / 접근권한 (신규 — 서버 DB)

- **주체**: 운영자 다수.
- **흐름**: `회원가입 → 승인 → 로그인 → 모든 기능 사용(권한 차등 없음)`.
- **세션**: 로그인 시 토큰 발급(JWT 또는 서버 세션). Admin 웹 보호 라우트 게이트.

### 가입 승인 상태

`가입신청(대기) → 승인 → 활성` / `거절`. 미승인 계정은 로그인 불가. 승인은 **승인된 운영자 누구나** 할 수 있다(권한 동일).

### 권한 모델 — 운영자·최상위 관리자 권한 **동일** (차등 부여 없음)

> 사수 지시: 최상위 관리자가 운영자에게 권한을 골라 주던 모델은 **폐기**. 승인된 운영자는 **최상위 관리자(SuperAdmin)와 완전히 동일한 모든 기능**을 사용한다.

- **기능 단위(capability) 차등 부여·체크박스 권한 화면을 두지 않는다.** 기기코드 발급, 하위 제어, 엑셀 업로드/일괄등록·계정 풀 분배, 네이버 계정 삭제, 운영자 승인 등 **모든 동작을 승인된 운영자라면 누구나** 수행. **단 아래 "운영자 삭제" 하나만 SuperAdmin 전용.**
- **최상위 관리자(SuperAdmin)의 특수성** — 일반 운영자와 다른 점은 **딱 세 가지**:
  - **항상 1명 이상 존재**해야 한다. **삭제 불가**(누구도 SuperAdmin 계정을 지울 수 없음).
  - **SuperAdmin 비밀번호는 변경 가능**(본인이 로그인해 변경 — 아래 비밀번호 변경).
  - **다른 운영자(일반 운영자) 계정을 삭제할 수 있다 — SuperAdmin 전용 권한.** 일반 운영자는 다른 운영자를 삭제하지 못한다. (단 SuperAdmin은 삭제 대상이 될 수 없음 → 위 보호 규칙)
- **적용 지점**: 모든 Admin 동작은 호출 전 "**로그인·승인된 운영자인지**"만 서버에서 검사한다. **예외: "운영자 삭제"만 호출자가 SuperAdmin인지 추가 검사**(그 외 기능별 권한 비트 검사는 없음).

### 비밀번호 변경 (로그인 상태에서만)

- **ID/PW 찾기(분실 복구) 기능은 두지 않는다**(사수 지시로 제외). 따라서 가입 시 이메일·인증코드 발송 인프라도 불필요.
- 비밀번호 변경은 **로그인한 본인이 직접** 한다: 현재 비번 확인 → 새 비번 저장.
- **SuperAdmin도 동일하게 자기 비밀번호를 변경**할 수 있다(요구사항).
- 분실 시 복구 경로가 없으므로, 비번 분실 대응 정책(예: 다른 운영자가 재설정/재발급)은 §13에서 결정.

## 6. 기기코드 발급·등록 흐름

```
[Admin] 기기코드 발급 요청 ──▶ [서버] 단기 코드 생성·pending 저장 ──▶ Admin에 코드 표시
                                                                    │
[하위] 로컬 UI에 코드 입력 ──POST /device/register {code}──▶ [서버] 코드 검증
                                                                    │
                          ┌─────────────────────────────────────────┘
                          ▼
[서버] 기기↔운영자/조직 바인딩 + 장기 기기토큰 발급 ──▶ [하위] 토큰 저장 → SSE 연결 시작
                          │
                          └──▶ 등록 결과를 Admin에 push (요구: 등록 결과 회신)
```

- 단기 기기코드: 짧은 만료(예: 10분), 1회용.
- 장기 기기토큰: 하위 로컬에 안전 저장, SSE/POST 인증에 사용.

### 단기 기기코드 vs 장기 기기토큰 (역할이 다른 두 단계)

> **코드 = 처음 한 번 짝짓는 "입장권", 토큰 = 그 뒤로 계속 쓰는 "신분증".** 사람이 치는 짧은 코드를 영구 비밀로 쓰면 위험하므로, 한 번 써서 강한 토큰으로 바꿔 갖는 표준 페어링 방식.

| 구분    | 단기 기기코드                   | 장기 기기토큰                        |
| ------- | ------------------------------- | ------------------------------------ |
| 비유    | 일회용 초대코드 / 문자 인증번호 | 발급된 사원증                        |
| 형태    | 짧음(사람이 눈으로 읽고 입력)   | 긺·무작위(기계만 씀)                 |
| 발급    | Admin이 발급, 화면에 표시       | 등록 성공 직후 서버가 발급           |
| 수명    | 10분·1회용(쓰면 폐기)           | 계속 유효(취소 전까지)               |
| 쓰는 곳 | 등록(페어링) 단 한 번           | 매 SSE/POST 인증마다(`Bearer`)       |
| 왜      | 사람이 짝짓는 입장권            | IP 바뀌어도 신원 유지(재입력 불필요) |

- **등록(코드) = 새로 생성**: 그 하위의 첫 페어링이라 지울 "기존"이 없다 → 새 기기 레코드 + 새 토큰 생성, 코드는 '사용됨'으로 폐기.
- **재연결(토큰) = 파이프만 교체**: IP가 바뀌어도 _기기·토큰은 그대로_ 재사용. 서버가 갈아끼우는 건 §4-1처럼 죽은 **파이프 핸들뿐**(기기·토큰 삭제 아님).
- (선택) 같은 하위를 나중에 재등록(재설치 등)하면 옛 토큰 무효화 후 재발급 — 정책은 §13.

## 7. 데이터 소유 (계정 ID/PW만 중앙 풀 + 쿠키·큐는 하위 로컬)

| 데이터                   | 저장 위치            | Admin 접근 방식                                          |
| ------------------------ | -------------------- | -------------------------------------------------------- |
| **계정 ID/PW(자격증명)** | **서버 DB(중앙 풀)** | Admin이 업로드·분배·조회 (**at-rest 암호화**, 아래 주의) |
| **계정↔하위 할당표**     | **서버 DB**          | Admin이 조회(누가 어떤 계정을 맡는지 = 분배 결과)        |
| 쿠키(`cookies/*.json`)   | **하위 로컬**        | 명령으로 목록/상태 조회(**쿠키 본문은 서버 전송 안 함**) |
| 게시큐·게시물·통계       | **하위 로컬**        | 명령/이벤트로 상태 스냅샷 수신                           |
| 운영자 계정·역할         | **서버 DB**          | Admin이 직접 조회                                        |
| 기기 등록·토큰           | **서버 DB**          | Admin이 직접 조회                                        |
| 감사로그(명령/결과 이력) | **서버 DB**          | Admin이 직접 조회                                        |

근거(사수 지시 반영):

- **계정 ID/PW는 중앙 풀(서버 DB)** 로 올려, Admin이 한 번 업로드하면 시스템이 여러 하위에 **자동 분배**한다(컴퓨터마다 엑셀을 일일이 넣던 수동 작업 제거). 자격증명이 서버에 모이므로 **at-rest 암호화·접근통제·TLS 필수**(§12 리스크).
- **쿠키·게시큐는 하위 로컬에 그대로** 둔다(`store.rs`, `cookies/`). 이유 두 가지: (1) **쿠키 유출 위험·동기화 복잡도 회피**, (2) **로그인은 반드시 각 하위가 자기 폰 IP로** 해야 한다 — 네이버 쿠키는 로그인 당시 IP·기기에 묶여, 중앙 한 IP에서 몰아 로그인해 쿠키를 뿌리면 안티봇에 무더기 차단된다. → **분배되는 것은 자격증명(ID/PW)이지 쿠키가 아니다.**
- 즉 서버는 "**계정 풀 보관·분배 + 원격 뷰 + 명령 발행**", 하위는 "**할당받은 계정을 자기 IP로 로그인·쿠키 로컬 보관**" 으로 역할이 갈린다.

## 8. 기존 코드 재사용 — Transport 추상화 seam

현재 React UI는 `src/shared/ipc`에서 로컬 Tauri(`invoke`)를 호출한다. 여기에 **transport 인터페이스**를 도입한다.

```ts
// 개념도
interface Transport {
  invoke<T>(command: string, args: unknown): Promise<T>;
  subscribe(event: string, cb: (e) => void): Unsubscribe;
}
// 하위(데스크톱):     TauriTransport   → 로컬 invoke 그대로
// Admin 웹(브라우저):  HttpSseTransport → 선택된 하위로 명령 전달 + SSE 수신
```

- **같은 React 컴포넌트**(`features/{accounts,dashboard,posts,queue,notifications}`)를 하위/Admin이 공유. 호출 대상만 transport로 분기.
- 하위는 기존 동작 그대로(로컬). Admin 웹은 "현재 선택된 하위"를 대상으로 동일 화면을 원격 조작.
- 기존 백엔드·플랫폼 모듈(`naver_cafe/`, `naver_blog/`, `band_*`, `forum_stocks/`, `naver_clip/`)은 **무손상**.

## 10-1. 대표 명령 시나리오 — Admin 엑셀 → 하위 일괄등록 → 게이트 후 전체 선택 로그인

> 요구: Admin에서 ID/PW가 담긴 `.xlsx`를 하위로 보내면, 하위가 **기존 '엑셀 가져오기'와 똑같이** 계정을 등록하고, **모두 등록된 뒤에야** 전 계정을 선택해 **선택 로그인**까지 자동 수행.

### (1) 파일 전달 — 기존 import 로직 재사용이 핵심

현행 `import_accounts(path)`(`src-tauri/src/ipc/excel.rs:76`, calamine)는 **로컬 파일 경로**를 읽어 계정을 로컬 등록한다. Admin의 엑셀은 하위 디스크에 없으므로, **파일(또는 데이터)을 하위로 옮긴 뒤 이 함수를 그대로 호출**한다(신규 파싱 로직 안 만듦).

```
1. [Admin 웹]  .xlsx 선택 → POST /devices/{id}/files (multipart)  ※ ID/PW 포함 → TLS 필수
2. [서버]      파일 보관(또는 짧은 만료 URL) → 명령 push:
               { type:"import_accounts", file:<base64 인라인 또는 다운로드 ref> } → 하위 SSE
3. [하위]      파일 수신 → 로컬 임시파일로 저장 → import_accounts(임시경로) 호출(변경 없음)
               → 계정 로컬 등록(지금 '엑셀 가져오기' 버튼과 100% 동일 동작)
4. [하위]      결과 POST: { imported:N, skipped:M, loginIds:[...] } → Admin 표시, 임시파일 삭제
```

- 파일 전달 방식: ID/PW 엑셀은 보통 수 KB라 **명령 JSON에 base64 인라인**이 가장 단순(별도 다운로드 엔드포인트도 가능). **보안: 평문 금지(TLS), 서버 잔류 파일은 import 후 즉시 삭제.**

### (2) "모두 등록되면 → 전체 선택 → 선택 로그인" (하위에서 게이트)

게이트를 **하위 안의 순차 명령**으로 잡아 원자성을 보장한다(Admin이 두 명령 타이밍을 맞출 필요 없음):

```
명령: { type:"import_then_login_all" }
 하위 실행:
  단계1) import_accounts(임시파일) → 등록 완료까지 대기  ← 이게 게이트. 실패행은 결과에 표시
  단계2) ★등록이 끝난 뒤에만★ 방금 등록된 계정 전체를 '선택'으로 잡고
  단계3) 기존 선택 로그인 경로(buildLoginNowItem / isSelectiveLoginPlatform) 호출
  각 단계 진행률을 같은 commandId로 그때그때 POST → Admin 실시간 확인
```

- 자동/수동 선택: 단계1·단계2를 분리해 "등록 결과 확인 후 운영자가 로그인 버튼"식 **수동 게이트**도 가능(§13에서 확정).

### (3) ⚠️ 선택 로그인은 IP를 바꾼다 — §4-1과 직접 맞물림

단계3의 선택 로그인 = 네이버 로그인 = **ADB IP 로테이션 → SSE 끊김 → 재연결**. 따라서:

- 로그인 직전 하위가 `ROTATING` 통보 → Admin 버튼 비활성(§4).
- 재연결되면 하위가 **같은 `commandId`로 진행률/결과를 이어서 POST**(§4-1 (6) 멱등) → Admin이 끊김 없이 이어받음.
- 계정이 여러 개면 **로그인마다 IP가 바뀔 수 있으므로**, 진행률 보고가 재연결을 건너뛰어도 누락·중복 없이 이어지도록 설계.

### (4) 로그인 후 자동 정리 — 실패 계정 자동 삭제(보류·대기초과는 유지)

> 요구: 선택 로그인을 전부 돌린 뒤, **로그인이 안 되는(실패) 계정은 자동 삭제**한다. 단 **보류(OnHold)·대기초과(TimedOut)는 무조건 유지**(사람이 직접 인증·로그인하거나, Admin이 "그 계정만 로그인" 명령으로 처리).

로그인 결과 상태(`outcome.rs`)별 처리:

| 결과 상태                     | 처리     | 이유                                        |
| ----------------------------- | -------- | ------------------------------------------- |
| `Active`(성공)                | **유지** | 정상 로그인                                 |
| `OnHold`(보류: 캡차·본인인증) | **유지** | 사람이 직접 풀면 회복 — 절대 삭제 안 함     |
| `TimedOut`(대기초과)          | **유지** | 페이지 대기/500 등 일시적 — 절대 삭제 안 함 |
| `BadCredentials`(비번오류)    | **삭제** | 로그인 실패                                 |
| `Challenge`(추가인증 필요)    | **삭제** | 로그인 실패(사용자 지시로 삭제 포함)        |
| `Blocked`(차단/잠김)          | **삭제** | 로그인 실패(사용자 지시로 삭제 포함)        |
| `Error`(네트워크/환경)        | **삭제** | 로그인 실패                                 |

→ **규칙 한 줄: `Active`·`OnHold`·`TimedOut`이 아닌 모든 로그인 실패 = 자동 삭제.**

**메커니즘(기존 부품 재사용, 트리거만 신규)**

```
하위: 선택 로그인 전부 실행 → 각 계정 결과 상태 수집
  → 삭제 대상(위 표) loginId 모음 → 기존 delete_accounts(ids) 호출(로컬 레코드 제거)
  → 결과 POST: { logged_in:[...], kept_onhold:[...], kept_timedout:[...], deleted:[{id, 사유}...] }
     ← 어떤 계정이 왜 지워졌는지 Admin에 회신(감사로그). 삭제는 되돌리기 불가라 회신 필수.
```

- **이미 있는 코드**: 선택 로그인(종토·블로그, #228), 보류 재로그인 시 사람이 직접 인증(`login.rs` `manual_captcha`, 120초), 계정 삭제(`accounts.rs::delete_accounts`). → **"실패 시 자동 삭제" 트리거만 신규 추가.**
- **유지된 보류·대기초과 처리**: 사람이 직접 인증/로그인, 또는 Admin이 그 계정들만 지목해 선택 로그인 명령(기존 선택 로그인 + `manual_captcha` 재사용).
- ⚠️ **되돌리기 불가**: 삭제 전 대상 목록을 결과로 회신/감사로그 남김. 즉시삭제 vs "Admin 확인 후 삭제" 옵션은 §13.

## 10-2. 중앙 계정 풀 → 하위 자동 분배 → 각 하위 로컬 로그인 (사수 지시 반영)

> 사수 지시: 계정 ID/PW를 **서버에 중앙 집중 저장**하고, 시스템이 **여러 하위에 나눠 배분**한다(예: 1000개 → 10대 × 100개). §10-1이 "Admin이 하위 1대에 엑셀을 직접 배달"이라면, 여기는 "**서버 풀에 한 번 올리면 시스템이 알아서 갈라 뿌림**"이다.

### 핵심 — 무엇을 중앙저장하고 무엇을 안 하나

- **중앙저장(서버 DB)**: 계정 **ID/PW 목록**(자격증명) + **계정↔하위 할당표**.
- **중앙저장 안 함(하위 로컬 유지)**: **쿠키**·게시큐. **로그인도 각 하위가 자기 폰 IP로** 직접 수행.
- **왜 쿠키·로그인은 중앙에서 안 하나**: 네이버 쿠키는 **로그인 당시 IP·기기에 묶인다.** 중앙(Admin 한 IP)에서 1000개를 몰아 로그인해 쿠키를 뿌리면 "발급 IP ≠ 사용 IP"라 안티봇에 무더기 차단된다. 이 앱이 폰 테더링 + ADB IP 로테이션으로 IP를 흩뿌리는 이유가 바로 그것. → **분배되는 것은 자격증명(ID/PW)이지 쿠키가 아니다.**

### 흐름

```
1. [Admin 웹]  ID/PW 엑셀을 서버 풀에 업로드   POST /admin/accounts/import (multipart, TLS 필수)
2. [서버]      계정 풀 DB에 저장(at-rest 암호화)  ← 여기까지가 '중앙 집중 저장'
3. [Admin 웹]  분배 실행   POST /admin/accounts/distribute { 정책: 균등 N개 / 규칙 }
4. [서버]      온라인 하위에 계정을 갈라 할당표 생성
               (계정 1개 = 정확히 하위 1대, 중복 할당 금지)
               → 각 하위 SSE로 { type:"accounts_assigned" } push (또는 하위가 GET /agent/accounts)
5. [하위]      할당받은 ID/PW → import_accounts 로 로컬 등록(§10-1 (1) 재사용, 신규 파싱 없음)
               → 전체 선택 → 선택 로그인(자기 폰 IP) → 쿠키 로컬 저장 (지금 방식 그대로)
6. [하위]      각 계정 결과를 commandId로 POST → Admin 실시간 표시
               (로그인이 IP를 바꾸므로 §4-1 재연결·멱등 그대로 적용)
```

### 분배 규칙 (요지, 세부는 §13)

- **계정 1개 = 하위 1대에만** 할당. 같은 계정을 두 대가 동시 로그인하면 네이버가 세션 충돌·차단하므로 **중복 할당 절대 금지**(서버 할당표가 단일 출처).
- 기본 정책: **온라인 하위 수로 균등 분배**(1000 / 10 = 100). 하위가 오프라인이면 그 몫은 보류하거나 다른 하위로 재배분.
- 새 하위 등록·제거 시 **재배분(rebalance)** 정책 필요(§13).
- 등록·로그인 자체는 §10-1 (2)~(4)와 동일: 모두 등록 후 로그인하는 **게이트**, **실패 계정 자동 삭제**(`Active`·`OnHold`·`TimedOut` 외 삭제) 규칙 그대로.
- **삭제 시 중앙 동기화**: 하위가 실패 계정을 로컬 삭제하면 그 결과를 서버에 회신해 **풀/할당표에도 반영**(재배분 후보로 둘지·완전 제거할지는 §13).

## 10-3. Admin 분배 화면 (UI) — 체크박스로 계정·하위 선택 → 균등+랜덤 분배

> 요구(사수 지시 구체화): Admin "1페이지"에서 계정을 한곳에 다 넣어두고, 연결된 하위 컴퓨터를 체크박스로 골라 **분배하기**를 누르면, 선택한 계정이 선택한 컴퓨터 수에 맞게 **겹치지 않게·균등하게·랜덤으로** 나뉘어 전송된다. (예: 10개를 3대에 → 4·3·3, 남는 1개는 임의의 한 대로)

### 화면 레이아웃 (위/아래 절반)

```
┌──────────────────────────────────────────────┐
│ 상단 절반 — 계정 풀 (기존 '계정 추가' 화면 재사용)        │
│  [계정 추가] [엑셀 가져오기]         총 N개 계정         │
│  ┌──────────────────────────────────┐ ▲      │
│  │ ☐ id001 / ****                   │ │스크롤 │  ← 최대 8행만 보임
│  │ ☐ id002 / ****                   │ │       │     더 보려면 좌측 스크롤바
│  │ … (최대 8행) …                    │ ▼      │
│  └──────────────────────────────────┘        │
├──────────────────────────────────────────────┤
│ 하단 절반 — 하위 컴퓨터 목록 (등록+연결된 것만)          │
│  ☐ 하위A (online, IP …)                       │
│  ☐ 하위B (online, IP …)                       │
│  ☐ 하위C (online, IP …)                       │
│                                  [ 분배하기 ]  │  ← 계정·컴퓨터 둘 다 1개↑ 선택 시 활성
└──────────────────────────────────────────────┘
```

**상단 절반 — 계정 풀 (기존 계정 추가 화면 재사용)**

- [재사용] `src/features/accounts/accounts.tsx`의 계정 추가/엑셀 가져오기 UI(계정 추가 버튼 `:634`)를 **절반 높이**로 배치. Admin 웹에서는 §8 transport(HttpSse)로 동작 → 추가/가져오기가 **서버 계정 풀(§10-2)** 에 기록(로컬 대신).
- [재사용] 계정 개수 표시 `accounts.tsx:864`("총 N개 계정").
- [재사용] 행 체크박스 패턴 `accounts.tsx:737–780`(`sel` 배열, 헤더 전체선택 + 행별 체크).
- [수정(스타일만)] 목록을 **최대 8행 고정 높이 + 세로 스크롤(좌측 스크롤바)** 로. 기존 테이블에 컨테이너 높이/overflow 스타일만 추가 — **로직 무손상**.

**하단 절반 — 하위 컴퓨터 목록**

- [신규] **기기등록 완료 + 현재 연결(online)** 인 하위만 표시. §4 상태 머신에서 `온라인/준비`만 노출하고 `IP변경중`·`재연결`·`오프라인/꺼짐`은 제외. (`GET /devices` 결과를 online 필터)
- [재사용] 좌측 체크박스는 위 `accounts.tsx` 체크박스 패턴 그대로.

### "분배하기" 버튼 & 분배 규칙

- [신규] **분배하기 버튼**: 상단 계정 ≥1 **그리고** 하단 컴퓨터 ≥1 선택 시 활성화(둘 중 하나라도 0이면 비활성). 기존에 없으면 신규 생성.
- 누르면 선택 계정 N개를 선택 컴퓨터 M대에 분배:
  - [재사용] **균등 분배는 기존 `distributeStocksEvenly()`** (`src/features/posts/publish-helpers.ts:28–44`) 재사용 — 겹침 없이 N을 M으로 갈라 각 대 `⌊N/M⌋` 또는 +1(대별 차이 최대 1). (검증: 18개/4대 → `[5,5,4,4]`, `publish-helpers.test.ts`)
  - ⚠️ [신규(셔플 1줄만)] 기존 함수는 **나머지를 앞 버킷에 몰아주는 결정적(deterministic)** 방식이라 "랜덤"이 아니다. 요구의 _랜덤_ 충족을 위해 **분배 직전에 계정·컴퓨터 순서를 한 번 셔플**해서 넣는다. → 균등 로직은 그대로 재사용하고 **순수 함수 `distributeStocksEvenly`는 수정하지 않음**(앞에 셔플만 추가).
  - **나머지 처리**: 10 ÷ 3 = 3·3·3 + 남은 1 → 셔플된 순서상 맨 앞 1대가 +1(=4). 어느 대가 +1 받을지는 셔플 때문에 매번 달라짐 → "아무 데나 추가" 충족.
  - **겹침 없음**: 계정 1개 = 정확히 1대(§10-2 분배 규칙·할당표 단일 출처와 동일).

### 분배 후 흐름

```
[Admin] 분배하기 클릭
  → 계정·컴퓨터 셔플 → distributeStocksEvenly(계정, 선택 컴퓨터 수)로 대별 몫 산출
  → 대별로 명령 발행  POST /devices/{id}/commands { type:"import_accounts", accounts:[{id,pw}...] }
                     (명령은 §3대로 그 하위가 연 SSE 파이프로 내려감)
[하위] 명령 수신 → import_accounts(임시) 로컬 등록 (excel.rs:76–159 재사용, §10-1 (1))
  → 자기 몫 전부 등록 완료되면 결과 POST → ★자기 로컬 화면 1회 새로고침
  → Admin이 보낸 계정이 전부 추가됨 (★로그인은 안 된 상태)
```

- **이 화면은 "계정 등록까지만"**. 선택 로그인은 별도 트리거(§10-1 (2), §10-2 6단계)에서 수행 — 분배 ≠ 로그인.
- **새로고침 시점**: 하위가 "내 몫 전부 등록 완료" 결과를 보낸 직후 자기 UI를 1회 refresh.

| 부품                          | 처리               | 위치                                                  |

## 11. 단계별 로드맵 (개발 시)

> 사수 지시로 이번엔 **계획서까지**. 아래는 승인 후 진행 가정 순서.

1. **P0 — 서버 골격**: axum + SSE 허브 + 인증/기기 DB 스키마 + 기기 등록/토큰.
2. **P1 — 에이전트 골격**: 하위 SSE 구독 + 하트비트 + 재연결(retry) + 상태 전이 POST.
3. **P2 — 연결 모니터링**: Admin 기기 목록/상태/IP 실시간 표시, IP변경중 명령 비활성화.
4. **P3 — 명령 1종(네이버 로그인)** 엔드투엔드: 발행→실행→IP 로테이션→재연결→결과 회신.
5. **P4 — Transport 추상화 + Admin 웹 UI 재사용**: 기존 화면을 원격 조작으로.
6. **P4-A — 중앙 계정 풀·분배 화면**: 서버 계정 풀 DB(암호화) + 엑셀 업로드 + **Admin 분배 화면(체크박스로 계정·하위 선택 → 균등+랜덤 분배, §10-3)** + 하위가 할당받아 `import_accounts`→로컬 등록(로그인은 별도). 기존 `distributeStocksEvenly`·`accounts.tsx`·`import_accounts` 재사용, 분배 직전 셔플만 신규. 실패 계정 삭제를 풀/할당표에 동기화.
7. **P5 — 명령 전체 원격화**: 게시 시작/중지/재정렬, 계정 관리, IP 로테이션 등 전 기능.
8. **P6 — 인증 강화**: 역할/접근권한, 감사로그, 승인 워크플로 마감.

각 단계는 기존 워크플로(이슈→브랜치→PR, TDD, 카페/밴드 무손상) 준수.

## 12. 리스크 / 검토 포인트

- **재연결 신뢰성**: IP 변경 후 SSE 재연결 백오프·중복 명령 방지(멱등 `commandId`) 설계 필요.
- **명령 유실**: ROTATING 중 발행된 명령 처리 정책(거부 vs 큐잉 후 재연결 시 전달) 확정 필요. → 기본: **거부 + Admin UI 비활성화**.
- **보안**: 기기토큰/운영자 세션 보호, 서버 공개 노출 시 TLS·인증 필수. 쿠키 본문은 서버로 보내지 않음.
- **자격증명 중앙 저장 위험**: 계정 ID/PW가 서버 DB 풀에 모이므로 **at-rest 암호화·키 관리·접근통제·전송 TLS 필수**, 유출 시 영향 범위가 크다. 쿠키는 여전히 서버로 보내지 않으며, **중앙에서 몰아 로그인하지 않는다**(IP 묶임 → 안티봇 차단, §10-2).
- **분배 정합성**: 같은 계정이 두 하위에 중복 할당되면 네이버 세션 충돌·차단 → 할당표를 **단일 출처**로 두고 중복 금지를 서버에서 보장해야 함.
- **웹 배포 환경**: Admin 웹/서버 호스팅(같은 머신, 포트, TLS, 방화벽) 운영 정책 확정 필요.
- **하위 풀 UI 유지 + 원격 동시 조작**: 동시 조작 충돌(현장 사람 + Admin) 시 우선순위/락 정책 필요.
- **CI**: 기존 CI는 결제 미납으로 영구 빨강 — 머지 정책은 기존 합의(merge-commit) 따름.

## 13. 미해결/추후 결정 사항

- ROTATING 중 명령 정책(거부/큐잉) 최종 확정.
- 동시 조작(현장+Admin) 충돌 정책.
- Admin 웹 배포 토폴로지(서버와 동일 머신 여부, TLS 인증서, 포트/도메인).
- 비밀번호 분실 대응: ID/PW 찾기 기능을 두지 않으므로, 분실 시 복구 경로(예: 다른 운영자가 재설정/계정 재발급 허용 여부) 정책 결정.
- 인증 토큰 방식(JWT vs 서버 세션) 확정.
- 엑셀 일괄등록 후 선택 로그인 게이트: **자동 연속** vs **등록 결과 확인 후 수동 트리거**(§10-1 (2)).
- 같은 하위 재등록(재설치 등) 시 옛 기기토큰 무효화 후 재발급 정책(§6).
- 파일 전달 방식: base64 인라인 vs 다운로드 엔드포인트 + 서버 잔류 파일 보존/삭제 정책(§10-1 (1)).
- 로그인 실패 계정 자동 삭제(§10-1 (4)): **즉시 삭제** vs **Admin 확인 후 삭제**(되돌리기 불가라 회신/감사로그는 필수, 확인 단계는 선택).
- 계정 분배 정책(§10-2): **온라인 하위 수 균등 분배** vs 규칙 기반(하위별 상한 등), 오프라인 하위 몫 처리(보류 vs 다른 하위 재배분), 새 하위 등록·제거 시 **재배분(rebalance)** 트리거.
- 계정 중복 할당 금지 보장 방식(서버 할당표 단일 출처 + 동시성 제어).
- 실패 계정 로컬 삭제 시 **중앙 풀/할당표 동기화**: 풀에서 완전 제거할지, 보존하고 재배분 후보로 둘지.
- 서버 계정 풀 **자격증명 암호화 방식**(at-rest 암호화 알고리즘·키 저장/회전·접근통제).
