# Admin–하위 컴퓨터 원격제어 계획서 (SSE 기반)

- 작성일: 2026-06-26

- 관련 메모리: 원격제어=중앙서버+에이전트(CGNAT/USB테더링) 방향

---

## 1. 배경 / 목적

### 현재 구조

- pstmacro는 **1대의 컴퓨터에 설치되어 각 사람이 직접 실행**하는 Tauri(데스크톱) 앱이다.
- 각 컴퓨터는 **핸드폰 USB 테더링(모바일 데이터)** 으로 인터넷에 연결되며, ADB IP 로테이션으로 **공인 IP가 비주기적으로 바뀐다**.
- 네이버 로그인은 CDP(눈에 보이는 Chrome)로 수행하고, 게시(카페·블로그·밴드·종토방·클립)는 로컬에서 실행된다.

### 목표

- **Admin 컴퓨터 1대**에서 **여러 하위 컴퓨터**를 등록·모니터링·원격제어한다.
- Admin에서 명령을 보내면 하위가 실행하고 **결과를 그때그때 Admin으로 회신**한다.
- IP가 계속 바뀌는 환경에서 **연결 상태·IP 변경·재연결(retry)을 Admin에서 확인**할 수 있다.
- **계정 ID/PW를 Admin(서버)에 모아 두었다가**, 운영자가 **체크박스로 골라 여러 하위에 균등+랜덤 분배**한다(예: 10개 → 3대에 4·3·3). 분배는 **MOVE**(보낸 계정은 Admin에서 비워짐, §7). 각 하위는 **받은 계정을 자기 폰 IP로 로컬 로그인**하고, **쿠키·게시큐는 하위 로컬 유지**(서버 전송 안 함). (§7·§10-2~10-4)
- 사수 지시: **Admin은 웹으로 배포**하고, 기존 pstmacro 기능을 살린다. "SSE만 추가하는 느낌"으로 기존 코드 무손상.
- 기존 코드, UI 재사용하고 없는 것만 새로 만들어서 추가할 것. 수정이 반드시 필요한 부분만 찾아서 수정할 것.

> **역할 분리(사수 재확인) — "기존 기능 유지 + Admin/하위 추가"**
>
> 기존 pstmacro는 **그대로 둔다**(무손상, 지금처럼 사람이 직접 단독 실행도 가능). 그 위에 두 역할을 *추가*만 한다:
>
> - ① **하위 = 기존 pstmacro(Tauri 데스크톱) + 에이전트 레이어**. 기존 화면·기능 100% 그대로, 거기에 SSE 구독·결과 보고만 얹는다. Admin이 없어도 단독 동작.
> - ② **Admin = 신규 웹**. 핵심 범위는 **인증·기기 모니터링·계정 분배(§10-3)·결과 보고(§10-4)**. 하위의 모든 화면(큐·게시 등)을 원격 미러링하는 것은 **후순위(P5)** 이지 MVP가 아니다.

### 비목표(이번 범위 아님)

- 하위 컴퓨터 자동 재부팅/원격 전원제어 (앱이 꺼지면 **사람이 직접 켜러 감**).
- **쿠키·게시큐**의 중앙 집중 저장 (쿠키 본문은 서버로 보내지 않고 하위 로컬 유지, 아래 §7). ※단 **계정 ID/PW는 Admin 스테이징에 모았다가 분배(MOVE)** — 이번 범위 포함(목표, §7·§10-2).
- **중앙(한 곳)에서 몰아서 로그인** 후 쿠키를 하위에 배달하는 방식 (네이버 쿠키는 로그인 당시 IP·기기에 묶여, 발급 IP ≠ 사용 IP면 안티봇에 차단됨 → 로그인은 반드시 각 하위가 자기 폰 IP로, §10-2).
- 기존 플랫폼 자동화 로직(카페/블로그/밴드/종토/클립) 변경.

## 2. 환경 / 네트워크 전제

| 항목           | 내용                                                                                                                                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin          | **랜선 + 고정 IP**(고정 IP 사용으로 가정), IP 안 바뀜. **중앙 서버 + Admin 웹을 이 컴퓨터 1대에 함께** 둔다(별도 머신 분리 안 함, §13). **웹으로 배포**.                                                       |
| 하위           | 핸드폰 USB 테더링(모바일 데이터), 공인 IP 비주기적 변경. **outbound 접속만** 가능(CGNAT 무관).                                                                                                                 |
| 연결 방향      | **연결을 여는 쪽은 항상 하위.** 하위가 서버로 SSE 스트림을 열어두고(명령은 이 파이프로 내려옴) + 결과는 HTTP POST로 올림. 서버는 하위로 **새 연결을 먼저 열지 못함**(하위 IP가 계속 바뀌고 CGNAT라 도달 불가). |
| IP 변경 트리거 | 네이버 로그인 시 ADB 디바이스 off→on → 모바일 데이터 재할당 → 공인 IP 변경 → 연결 일시 단절.                                                                                                                   |

핵심: **하위는 항상 "찾아가는" 쪽**이므로 IP가 바뀌어도 outbound 재접속만 되면 복구된다. 서버(Admin)는 고정 주소라 하위가 언제든 다시 찾아올 수 있다.

> **"Admin이 하위를 직접 찌르지 않는다"의 정확한 의미** — Admin이 하위로 *새 TCP 연결을 새로 여는 것*이 불가능하다는 뜻이지, 명령을 안 보낸다는 뜻이 아니다. 명령은 분명히 Admin→하위로 가지만, **하위가 미리 열어둔 SSE 파이프를 타고** 내려간다. (서버는 그 파이프에 명령을 얹기만 함)

## 3. 통신 방식 — SSE(단방향) + HTTP POST(회신)

SSE는 **서버→클라이언트 단방향**이다. 양방향처럼 동작시키려면 **돌아오는 길을 일반 HTTP POST**로 구성한다(표준 패턴).

> **누가 서버이고 누가 연결을 여는가 (가장 헷갈리는 지점)**
>
> - **서버 = Admin**, **클라이언트 = 하위.** SSE의 데이터는 서버→클라이언트로 흐르지만, 그 **연결을 여는 쪽은 클라이언트(하위)** 다.
> - 하위가 먼저 `GET /agent/stream`으로 **연결을 열어두면**, Admin(서버)이 그 열린 파이프로 **명령을 흘려보낸다.** 즉 "로그인 해" 명령은 `Admin 웹 → Admin 서버 → (하위가 연 SSE 파이프) → 하위` 로 도착한다. 명령은 확실히 Admin→하위 방향이다.
> - 하위가 무언가 보낼 때(결과·하트비트·IP·기기등록)는 SSE가 아니라 **별도 HTTP POST** 를 쏜다. SSE 한 줄로는 못 올리기 때문.

```
                    ┌──────────────────────────────────────────┐
                    │        Admin 서버 (랜선·고정IP, 웹배포)         │
                    │   axum + SSE 허브 + 인증DB + 기기DB + 감사로그   │
                    └──────────────────────────────────────────┘
       SSE: 명령 수신 ▲│ POST: 결과·하트비트·IP   ▲│ SSE: 실시간 상태/결과
                    │▼                          │▼ POST: 명령 발행
       ┌──────────────────────┐        ┌──────────────────────────┐
       │   하위 컴퓨터 (에이전트)    │        │   Admin 웹 (운영자 브라우저)      │
       │ 기존 pstmacro 풀 UI +    │        │  기존 React UI 재사용 +         │
       │ 에이전트 레이어            │        │  관리화면(인증·기기·모니터링)       │
       │ 폰 USB테더링/모바일데이터    │        │                              │
       └──────────────────────┘        └──────────────────────────┘
```

### 3개의 통신 경로

1. **하위 → 명령 수신 (SSE)**: 하위가 `GET /agent/stream`으로 SSE 스트림을 열어둔다. Admin이 명령을 발행하면 서버가 **해당 하위의 스트림으로 push**한다.
2. **하위 → 결과 회신 (POST)**: 명령마다 `commandId` 부여. 하위가 진행률/최종결과/하트비트/현재 IP를 **POST**로 서버에 올린다. 서버는 이를 Admin 스트림으로 중계 → "결과를 그때그때 Admin으로" 충족.
3. **Admin → 명령 발행 (POST) + 상태 수신 (SSE)**: Admin 웹이 `POST /devices/{id}/commands`로 명령을 발행하고, `GET /admin/stream` SSE로 모든 하위의 상태·결과를 실시간 수신한다.

서버는 **허브**: Admin 명령을 대상 하위의 SSE로 라우팅하고, 하위 결과/상태를 구독 중인 Admin SSE로 중계한다.

## 4. 디바이스 상태 머신 (IP 변경·연결 핵심)

```
   [미등록]
      │ 기기코드 등록
      ▼
   [온라인/준비] ──명령 수신──▶ [실행중] ──완료/실패──▶ [온라인/준비]
      ▲   │
      │   │ 네이버 로그인 등 IP 로테이션 직전 (하위가 먼저 알림)
      │   ▼
      │ [IP변경중(ROTATING)]  ← 이 동안 Admin은 명령 버튼 비활성화
      │   │ ADB off→on, SSE 끊김, 백오프 재시도(retry)
      │   ▼
      └─[재연결] ──새 IP POST──▶ [온라인/준비] (Admin에 바뀐 IP 표시)

   하트비트 타임아웃 → [오프라인/꺼짐]  ← 사람이 직접 켜러 감
```

### 상태별 동작

| 상태          | 의미                      | Admin UI                       |
| ------------- | ------------------------- | ------------------------------ |
| 미등록        | 기기코드 미등록           | 목록에 없음                    |
| 온라인/준비   | SSE 연결됨, 하트비트 정상 | 명령 가능(버튼 활성)           |
| 실행중        | 명령 수행 중              | 진행률 표시, 중복 명령 차단    |
| **IP변경중**  | 하위가 로테이션 직전 통보 | **명령 버튼 비활성화**         |
| 재연결        | SSE 끊김, 재시도 중       | "재연결 중…" 표시, 명령 비활성 |
| 오프라인/꺼짐 | 하트비트 타임아웃         | "꺼짐" 표시, 직접 켜러 가야 함 |

### IP 변경 시나리오 (가장 중요한 요구)

> 대입한 현행 로그인 IP 변경 구조: **비행기모드 ON → `adb shell ping 8.8.8.8` 실패(끊김 확인) → 비행기모드 OFF → IP 확인 API로 공인 IP 변경 확인 → 안정화.** 이 구간 전체가 아래 3~5번이다.

1. 하위 online, **SSE 파이프 열려있음.** Admin이 **네이버 로그인** 명령 발행 → 파이프로 하위 도착.
2. 하위가 로그인 시작 → IP 로테이션 **직전(아직 인터넷 살아있을 때) `ROTATING` 상태를 POST** → 서버 → Admin push → **Admin UI에서 그 하위 명령 버튼 비활성화**.
3. 비행기모드 ON → 인터넷 끊김 → **SSE 파이프 끊김.** 이 동안 하위는 명령을 받지도 POST를 보내지도 못함.
4. 비행기모드 OFF → IP 확인 → 안정화. 하위 에이전트가 **백오프 재시도(retry)** 로 ★**다시 SSE 연결을 엶**(= "하위가 Admin을 직접 찾아감". 항상 연결을 여는 쪽은 하위).
5. 재연결 성공 → 하위가 **새 IP + `온라인` 상태를 POST** → Admin이 **바뀐 IP 표시 + 명령 버튼 재활성화**.
6. 로그인 결과(성공/캡차/실패)를 `commandId` 결과로 POST → Admin 표시.

> 하위는 IP 변경 중에는 명령을 받지 않으며(3번, SSE 끊긴 상태), Admin도 그 동안 명령 발행 UI가 비활성. 재연결(4번)이 완료된 뒤에만 명령 가능.

### 4-1. 재연결 메커니즘 — 핸드폰 IP가 바뀐 뒤 하위가 서버를 "어떻게 다시 찾아가는가"

> 핵심 한 줄: **하위의 IP는 바뀌어도 목적지(Admin 서버) 주소는 고정**이라, 하위는 *늘 같은 주소로 다시 접속*하고, 자기가 누구인지는 *IP가 아니라 기기토큰*으로 증명한다. 그래서 IP가 아무리 바뀌어도 "찾아가는 길"은 변하지 않는다.

**(1) 목적지는 고정값 — 하위 IP와 무관**

- 하위 설정에 **Admin 서버 주소를 사전에 박아둔다**(`ADMIN_SERVER_URL` = Admin의 고정 IP 또는 도메인. Admin은 랜선·고정 IP라 안 바뀜).
- 재연결이란 결국 **같은 URL로 다시** `GET {ADMIN_SERVER_URL}/agent/stream` 요청을 여는 것. 하위 자신의 IP가 1.2.3.4 → 5.6.7.8로 바뀌어도, "어디로 가야 하나"는 그대로다. (TCP 출발지 IP만 바뀔 뿐 목적지는 동일)

**(2) 신원은 IP가 아니라 기기토큰으로**

- 재연결 요청에 `Authorization: Bearer <device-token>`(§6 등록 때 받은 장기 토큰)을 실어 보낸다.
- 서버는 **토큰 → `device_id` 매핑**으로 "이 스트림이 어느 하위인지" 식별한다. **출발지 IP는 식별에 쓰지 않는다**(어차피 매번 바뀌므로). → 새 IP로 접속해도 서버는 같은 기기로 인식.

**(3) 언제 재연결을 시도하나 — 현행 로테이션 코드에 직접 물림**

현행 `toggle_airplane_mode()`(`src-tauri/src/auth/adb.rs`)가 이미 "네트워크 복구 + 새 IP 확정" 신호를 만든다:

```
toggle_airplane_mode():
  before = fetch_external_ip()          # api.ipify.org (현재 공인 IP)
  비행기모드 ON
  wait_until_phone_offline()            # ping 폴링으로 실제 끊김 확인
  비행기모드 OFF
  wait_for_internet_connection()        # 인터넷 복구 대기  ← 여기서부터 outbound 가능
  after = wait_for_ip_change(before)    # ipify 폴링으로 새 공인 IP 확정
  return IpRotation { before, after }   # ★ 이 반환 시점 = 재연결 트리거
```

→ 에이전트는 **`toggle_airplane_mode()`가 `after`(새 IP)를 반환한 직후** 재연결을 시작한다(이때 비로소 인터넷이 살아있고 IP도 확정됨). 곧바로 `GET /agent/stream` 재오픈 + `POST /agent/heartbeat { ip: after, state: "online" }`.

**(4) 안전망 — 백오프 재시도 루프**

- 위 트리거와 별개로, 에이전트는 **SSE 스트림이 끊긴 것을 감지하면 항상 재연결 루프**를 돈다: `1s → 2s → 4s → 8s → … → 최대 30s` 백오프로 **무한 재시도**.
- 아직 네트워크가 안 살아있으면 연결 실패 → 다음 백오프까지 대기 후 재시도. 살아나는 순간 성공. (서버가 잠깐 죽어도 동일하게 부활 시 자동 복구)

**(5) 서버측 재부착(re-attach)**

- 서버는 `device_id → 현재 활성 SSE 송신핸들`(채널) 맵(= **라우팅 표**)을 유지한다.
- 같은 토큰의 **새 스트림이 들어오면 옛 핸들을 폐기하고 새 핸들로 교체**한다(기기 신원은 그대로, 연결만 갈아끼움). 직후 Admin 스트림으로 `{device_id, 새 IP, online}` push → Admin UI가 바뀐 IP 표시 + 명령 버튼 재활성.
- 끊긴 동안 서버는 그 기기를 `재연결(RECONNECTING)`로 두고, **하트비트 타임아웃(예: N초)** 을 넘기면 `오프라인/꺼짐`으로 전환.

> **"새 파이프를 어떻게 찾아가는가" = IP가 아니라 `device_id`로 찾는다.** Admin은 IP를 몰라도 됨 — 항상 `device_id`로만 지목하고, "그 번호의 지금 파이프"는 서버 라우팅 표가 연결해 준다. 하위가 매 연결마다 기기토큰을 제시 → 서버가 표를 최신으로 덮어쓴다. (교환원 비유: Admin="철수한테 연결" → 서버가 *철수의 지금 번호*로 이어줌)
>
> ```
> 서버 라우팅 표 (device_id → 현재 살아있는 파이프)
> ─────────────────────────────────────────────
> 하위A (토큰 aaa) → 파이프#41  (지금 IP 5.6.7.8)   ← IP 바뀌며 #17에서 교체됨
> 하위B (토큰 bbb) → 파이프#23  (지금 IP 9.9.9.9)
> 하위C (토큰 ccc) → (없음, 재연결 중)
>
> IP 변경: 하위A #17 죽음 → 토큰 aaa로 #41 새로 옴 → 표를 #41로 덮어씀(헌 #17 폐기)
> 명령 발행: Admin "하위A 로그인" → 서버가 표에서 하위A 칸(#41)에 명령 흘려넣음
> ```

**(6) 명령 유실·중복 방지**

- ROTATING 구간엔 Admin 명령 발행 UI가 막혀 있어 그 사이 새 명령이 쌓일 일이 거의 없다.
- 그래도 끊긴 사이 발생한 이벤트를 놓치지 않도록 **SSE 표준 `Last-Event-ID`** 를 쓴다: 하위가 마지막으로 받은 이벤트 ID를 재연결 요청 헤더에 실으면, 서버가 그 이후 이벤트만 재전송.
- 모든 명령은 **`commandId` 멱등** 처리 → 혹시 중복 전달돼도 같은 명령은 한 번만 실행.

**(7) 엣지 케이스**

- 토큰 만료/무효 → 서버가 `401` → 하위는 SSE를 안 열고 **재등록(§6) 안내** 상태로 전환.
- 안정화가 끝났는데도 계속 실패 → 백오프 무한 재시도(루프 (4))로 버팀, 사람이 개입할 필요 없음. 단 앱 자체가 꺼지면 하트비트 타임아웃으로 Admin에 `꺼짐` 표시 → 사람이 직접 켜러 감.

```
[하위] toggle_airplane_mode() 반환(after IP 확정)
   │
   ├─▶ GET {ADMIN_SERVER_URL}/agent/stream     (Authorization: Bearer <device-token>,
   │                                             Last-Event-ID: <마지막 이벤트 ID>)
   │        │ 실패(아직 네트워크/서버 미복구)
   │        └─▶ 백오프(1→2→4→…→30s) 후 재시도 ──┐
   │                                            │
   │        성공 ◀───────────────────────────────┘
   ▼
[서버] 토큰→device_id 식별 → 옛 핸들 교체(re-attach) → Last-Event-ID 이후 이벤트 재송신
   │
   └─▶ Admin 스트림으로 {device_id, 새 IP, online} push → Admin UI 갱신·버튼 재활성
[하위] POST /agent/heartbeat { ip: after } + 직전 명령 결과 POST(commandId)
```

### 4-2. ROTATING(IP 변경) 중 도착한 명령 — 거부 + 거부 사실을 통신로그에 남김 (확정)

> 사용자 지시: ROTATING 동안 Admin UI 명령 버튼은 비활성이 **원칙**이지만, **혹시라도** 그 사이 명령이 서버에 도달하면(예: 두 운영자가 동시에 보거나, 비활성화 직전에 클릭이 들어온 경우) **그 명령을 실행하지 않고 거부**하고, **어떤 명령이 들어왔고 어떻게 거부했는지를 통신로그(§10-5)에 빠짐없이 남긴다.** "조용히 무시"가 아니라 "거부 사실을 기록"한다.

**규칙**

- **1차 방어(UI)**: 대상 하위가 `ROTATING`/`재연결` 상태면 Admin 화면에서 그 하위의 명령 버튼을 비활성화(§4) → 애초에 못 보냄.
- **2차 방어(서버)**: 그래도 명령이 도착하면 **서버가 거부**한다. 서버는 `device_id → 상태`를 알고 있으므로, 대상 하위가 `online/준비`가 아니면(`ROTATING`·`재연결`·`오프라인`) 해당 명령을 **실행 라우팅하지 않고 거부 응답**(예: HTTP `409 Conflict` + 사유)으로 돌려준다. 이 동안 하위는 어차피 SSE가 끊겨 있어 명령을 받지도 못한다.
- **거부 = 반드시 로그**: 거부할 때 다음을 **모두** 감사로그(서버 DB)에 기록하고 통신로그 화면(§10-5)에 띄운다.
  - **들어온 명령 전체**: `commandId`, 명령 타입(예: `import_then_login_all`), 대상 `device_id`, 발행한 운영자.
  - **거부 사유**: 대상 상태(예: `ROTATING`), 거부 코드(`409`), 시각.
  - 통신로그 태그 `[REJECT]`(빨강)로 한 줄, **무엇을·어디로·왜·누가·어느 코드**가 다 보이게:
    `시각 [REJECT] Admin → 하위-001  거부: device_name=하위-001 명령=import_then_login_all(전체로그인) commandId=c-92 사유=대상 컴퓨터 IP 변경 중(ROTATING·거부코드 409) operator=admin src=<명령 핸들러 절대경로:줄>`
  - 필드 의미: `device_name`=대상 컴퓨터 이름(=화살표의 그 기기), `명령`=거부된 명령 타입+한글 설명, `commandId`=명령 고유 추적번호(기기 이름 아님), `사유`=왜 거부(대상 상태 + 거부코드 409=서버 "지금 안 됨"), `operator`=명령 낸 운영자, `src`=그 명령 핸들러의 **소스 절대경로:줄**(구현되면 실제값. 서버/에이전트 미구현이라 현재는 예정 위치).
- **유실 아님**: 거부는 "삭제"가 아니라 "지금은 안 됨" 회신이다. 운영자는 재연결(§4-1) 뒤 버튼이 풀리면 다시 보낸다. (큐잉해서 자동 재전송하지 않음 — §12·§13 "거부" 정책 확정. 자동 큐잉은 중복·순서 꼬임 위험이 커 채택 안 함.)
- **멱등 안전망**: 만약 거부 타이밍이 어긋나 같은 명령이 중복 전달돼도 `commandId` 멱등(§4-1 (6))으로 한 번만 실행.

```
[Admin] 명령 발행 (실수로 ROTATING 중)
   │  POST /devices/{id}/commands { commandId, type:"import_then_login_all" }
   ▼
[서버] 대상 device 상태 확인 → ROTATING/재연결/오프라인 이면
   ├─▶ 실행 라우팅 안 함, 409 Conflict + { reason:"device_rotating" } 회신
   └─▶ 감사로그 기록 + Admin 스트림으로 [REJECT] 이벤트 push
[통신로그] 시각 [REJECT] Admin → 하위-001  거부: device_name=하위-001 명령=import_then_login_all(전체로그인) commandId=c-92 사유=대상 컴퓨터 IP 변경 중(ROTATING·거부코드 409) operator=admin src=<핸들러 절대경로:줄>
```

### 4-3. 동시 조작 충돌 정책 — 현장 사람 vs Admin (확정)

> 상황: 하위 컴퓨터 앞의 **현장 사람**과 원격의 **Admin**이 동시에 같은 하위를 조작할 수 있다. 누구 걸 먼저 실행할지 정한다.

**규칙 (확정)**

1. **기본은 Admin 명령 우선 실행** — Admin이 내린 명령을 하위가 받아 수행한다.
2. **단, 현장 사람이 직접 행동하면 그 행동을 우선**한다 — 사람이 하위 앞에서 직접 조작(버튼 클릭 등)하면 그게 먼저다.
3. **★진행 중인 작업은 절대 중간에 끊지 않는다(원자성 보장)** — 우선순위가 바뀌어도 **지금 실행 중인 단위는 끝까지 완료**하고, **그 다음 작업으로 넘어가기 직전**에 우선순위를 적용한다.
   - **단위 = 한 계정의 작업 묶음**(계정 경계). 글 1개 단위가 아니다(게시 큐 선점 규칙과 동일 — [[queue-priority-spec]]).

**예시 (사용자 지시 그대로)**

```
10개 계정 중 1번 계정이 글 5개를 게시하는 중에 현장 사람이 어떤 행동을 함
 → 게시를 중단하지 않는다. 1번 계정의 글 5개를 ★전부 올린다★.
 → 그 다음 계정(2번)으로 넘어가기 직전, 현장 사람이 한 행동을 먼저 실행.
 → 그 행동이 끝나면 다음 명령(2번 계정 게시)을 이어서 수행.
```

- 즉 **"실행 중인 명령은 모두 완료 → 계정 경계에서 끼어든 행동 처리 → 그 다음 명령"** 순서.
- 글 5개를 올리던 도중 끊으면 절반만 올라가 일관성이 깨지므로, **계정 단위가 끝나는 지점**을 안전한 양보 지점으로 삼는다(기존 게시 큐의 선점 경계와 동일 원칙).
- 통신 로그(§10-5)에는 "현장 행동으로 우선순위 전환" 사실도 기록해, 왜 명령 순서가 바뀌었는지 Admin이 알 수 있게 한다.

## 5. 인증 / 접근권한 (신규 — 서버 DB)

- **주체**: 운영자 다수.
- **흐름**: `회원가입 → 승인 → 로그인 → 모든 기능 사용(권한 차등 없음)`.
- **세션**: 로그인 시 토큰 발급(JWT 또는 서버 세션). Admin 웹 보호 라우트 게이트.

### 가입 승인 상태

`가입신청(대기) → 승인 → 활성` / `거절`. 미승인 계정은 로그인 불가. 승인은 **승인된 운영자 누구나** 할 수 있다(권한 동일).

### 권한 모델 — 운영자·최상위 관리자 권한 **동일** (차등 부여 없음)

> 사수 지시: 최상위 관리자가 운영자에게 권한을 골라 주던 모델은 **폐기**. 승인된 운영자는 **최상위 관리자(SuperAdmin)와 완전히 동일한 모든 기능**을 사용한다.

- **기능 단위(capability) 차등 부여·체크박스 권한 화면을 두지 않는다.** 기기코드 발급, 하위 제어, 엑셀 업로드/일괄등록·계정 풀 분배, 네이버 계정 삭제, 운영자 승인 등 **모든 동작을 승인된 운영자라면 누구나** 수행. **단 아래 "운영자 삭제" 하나만 SuperAdmin 전용.**
- **최상위 관리자(SuperAdmin)의 특수성** — 일반 운영자와 다른 점은 **딱 세 가지**:
  - **항상 1명 이상 존재**해야 한다. **삭제 불가**(누구도 SuperAdmin 계정을 지울 수 없음).
  - **SuperAdmin 비밀번호는 변경 가능**(본인이 로그인해 변경 — 아래 비밀번호 변경).
  - **다른 운영자(일반 운영자) 계정을 삭제할 수 있다 — SuperAdmin 전용 권한.** 일반 운영자는 다른 운영자를 삭제하지 못한다. (단 SuperAdmin은 삭제 대상이 될 수 없음 → 위 보호 규칙)
- **적용 지점**: 모든 Admin 동작은 호출 전 "**로그인·승인된 운영자인지**"만 서버에서 검사한다. **예외: "운영자 삭제"만 호출자가 SuperAdmin인지 추가 검사**(그 외 기능별 권한 비트 검사는 없음).

### 최상위 관리자(SuperAdmin) 부트스트랩

- 서버 최초 기동 시 **기본 SuperAdmin 계정을 시드**한다: **ID `Superadmin` / PW `Superadmin`**.
- 이 **기본 자격증명으로 로그인하면 곧바로 "비밀번호 변경" 화면으로 강제 이동**한다(기본 비번을 그대로 쓰지 못하게). 새 비번을 저장한 뒤에야 정상 화면 사용.
- **(확정) 강제 비번 변경 후에는 다시 로그인시킨다**: 새 비번 저장 → "변경되었습니다" 메시지 → **로그인 화면으로 복귀** → 운영자가 **바뀐 새 비번으로 다시 로그인**해야 메인 화면에 진입. (저장 직후 자동 통과시키지 않고 재로그인을 강제 — 더 명확·안전. DB엔 ID `Superadmin`은 그대로, 비번 해시만 새 값으로 덮어써짐.) 이 재로그인 패턴은 일반 운영자의 비밀번호 변경에도 동일 적용 가능.
- 이렇게 첫 SuperAdmin이 생기므로 "승인할 사람이 0인 닭-달걀 문제"가 없다. 이후 가입하는 운영자는 이 SuperAdmin(또는 승인된 운영자)이 승인한다.
- SuperAdmin은 항상 1명 이상(삭제 불가, 위 권한 모델).

### 비밀번호 변경 (로그인 상태에서만)

- **ID/PW 찾기(분실 복구) 기능은 두지 않는다**(사수 지시로 제외). 따라서 가입 시 이메일·인증코드 발송 인프라도 불필요.
- 비밀번호 변경은 **로그인한 본인이 직접** 한다: 현재 비번 확인 → 새 비번 저장.
- **입력 편의(확정)**: ① 로그인·비번변경 화면 모두 **Enter만 쳐도 제출**(버튼 클릭 불필요). ② 강제 변경 화면은 **현재 비번을 기본값(`Superadmin`)으로 미리 채워** 운영자가 새 비번만 입력하면 되게 한다. (코드: `login.tsx`·`change-password.tsx`)
- **SuperAdmin도 동일하게 자기 비밀번호를 변경**할 수 있다(요구사항).

#### 비밀번호 분실 복구 (사수 확정, PR #324) — SuperAdmin이 하위 운영자 비번 재설정

- **SuperAdmin 본인 비번**: 복구 경로 **없음**. 본인이 **종이에 적어 보관**한다(잊으면 복구 불가 — 그래서 SuperAdmin은 항상 1명 이상·삭제 불가, §5 권한 모델로 보호).
- **하위(일반) 운영자 비번**: 잊으면 **SuperAdmin이 새 비번으로 재설정**해 준다. (일반 운영자끼리는 서로 재설정 불가 — SuperAdmin 전용.)
  - 엔드포인트: `POST /admin/operators/{id}/reset-password`(호출자가 SuperAdmin인지 검사 — "운영자 삭제"와 같은 SuperAdmin 전용 게이트).
  - 재설정 시 그 운영자의 **토큰 버전 +1**(§5 인증) → 옛 토큰 즉시 무효 → 새 비번으로 재로그인.
  - UI: **운영자 관리 화면**(`operators.tsx`)에서 SuperAdmin에게만 각 하위 운영자 행에 **[비번 재설정]** 버튼 노출. (SuperAdmin 행에는 안 보임 — 본인은 로그인 상태에서 직접 변경.)

### 인증 방식 (확정) — JWT 통일, 단 **토큰 2종은 수명이 다르다**

> 사용자 결정: 운영자 로그인·기기 인증 **모두 JWT**로 통일한다. JWT는 서버가 토큰을 저장하지 않고 **서명만 검증**(상태 없음·가벼움)하므로, "강제 로그아웃·계정 삭제 시 옛 토큰 거부"는 **유저별 버전(token version) 한 칸**으로 처리한다.

> **두 토큰의 수명이 정반대다 (가장 헷갈리는 지점, 확정):**
>
> |                   | **운영자 토큰**                                    | **기기 토큰**                                      |
> | ----------------- | -------------------------------------------------- | -------------------------------------------------- |
> | 쓰는 주체         | 사람(운영자 브라우저)                              | 무인 하위 컴퓨터                                   |
> | 만료(exp)         | **8시간**(확정) → 지나면 **ID/PW 재로그인**        | **만료 없음(영구, 확정)** — 한 번 등록 = 계속 사용 |
> | 왜                | 사람이라 세션이 영원하면 위험(자리 비움·토큰 유출) | 무인이라 만료되면 사람이 가서 재등록해야 함 → 끔찍 |
> | 회수(즉시 무효화) | **유저 버전 +1**(§5)                               | **기기표 줄 삭제**(§6-4)                           |
>
> - 운영자 토큰이 만료되면 토큰을 **사람이 다시 입력하는 게 아니라**, ID/PW를 다시 치면 **새 토큰이 자동 발급**된다(부담 없음).
> - 기기 토큰은 IP가 바뀌어도 그대로(§6). 다시 등록해야 하는 경우는 재설치/강제 삭제뿐.
> - **만료(exp, 시계)와 회수(버전·줄삭제, 즉시 강제)는 다른 것**: 만료는 시간이 지나 자동으로 죽는 것, 회수는 시간과 무관하게 즉시 죽이는 것.

- **발급**: `POST /auth/login` 성공 → JWT 발급. 토큰에 담는 것 = `{ 운영자 ID(sub), 만료(exp), 현재 유저 버전(ver), 서명 }`.
- **검증(매 요청)**: 서명 확인 + 만료 확인 + **토큰의 `ver` == DB의 그 유저 `token_version`인지** 비교. 하나라도 어긋나면 `401`.
- **회수 = 버전 +1**: DB 유저표에 `token_version`(처음 1) 칸을 둔다. **운영자 삭제·비번 리셋·강제 로그아웃 시 이 숫자를 +1** → 그 유저가 전에 받은 **모든 토큰이 한 번에 무효**(옛 `ver`라 거부). 재로그인하면 새 토큰에 올라간 버전이 박혀 다시 통과.
  - 비유: 신분증 재발급 차수 — "지금은 N차 발급분만 인정". 서버는 토큰을 일일이 기억할 필요 없이 **유저당 숫자 1개**만 들고 있으면 됨.
- **유저 삭제 시**: 위 버전 불일치로도 막히고, 추가로 검증 때 "이 유저가 DB에 아직 있나"가 없으면 곧바로 `401`(삭제된 유저는 토큰의 sub가 가리킬 대상이 없음).
- **만료시간(exp) = 8시간(확정)**: 운영자 토큰은 8시간 후 만료 → ID/PW 재로그인(새 토큰 자동 발급). 기기 토큰은 만료 없음(§6, 위 표).
- 같은 JWT 인증 미들웨어를 기기 토큰에도 재사용(§6) — 단 기기는 ① 회수를 "버전"이 아니라 "기기표 줄 삭제"로, ② **만료 없음(영구)** 으로 한다(§6, 차이 주의).

## 6. 기기코드 발급·등록 흐름

```
[Admin] 기기코드 발급 요청 ──▶ [서버] 단기 코드 생성·pending 저장 ──▶ Admin에 코드 표시
                                                                    │
[하위] 로컬 UI에 코드 입력 ──POST /device/register {code}──▶ [서버] 코드 검증
                                                                    │
                          ┌─────────────────────────────────────────┘
                          ▼
[서버] 기기↔운영자/조직 바인딩 + 장기 기기토큰 발급 ──▶ [하위] 토큰 저장 → SSE 연결 시작
                          │
                          └──▶ 등록 결과를 Admin에 push (요구: 등록 결과 회신)
```

- 단기 기기코드: 짧은 만료(예: 10분), 1회용.
- 장기 기기토큰: 하위 로컬에 안전 저장, SSE/POST 인증에 사용. **형식 = JWT(확정)**. 토큰에 `{ device_id, 서명 }`을 담아 §5와 같은 JWT 미들웨어로 검증. **만료 없음(영구, 확정)** — 한 번 등록하면 IP가 바뀌어도 계속 사용(운영자 토큰의 8시간 만료와 다름, §5 표). **회수는 "버전"이 아니라 "기기표 줄 삭제"로 한다**(아래 §6-4).

### 단기 기기코드 vs 장기 기기토큰 (역할이 다른 두 단계)

> **코드 = 처음 한 번 짝짓는 "입장권", 토큰 = 그 뒤로 계속 쓰는 "신분증".** 사람이 치는 짧은 코드를 영구 비밀로 쓰면 위험하므로, 한 번 써서 강한 토큰으로 바꿔 갖는 표준 페어링 방식.

| 구분    | 단기 기기코드                   | 장기 기기토큰                        |
| ------- | ------------------------------- | ------------------------------------ |
| 비유    | 일회용 초대코드 / 문자 인증번호 | 발급된 사원증                        |
| 형태    | 짧음(사람이 눈으로 읽고 입력)   | 긺·무작위(기계만 씀)                 |
| 발급    | Admin이 발급, 화면에 표시       | 등록 성공 직후 서버가 발급           |
| 수명    | 10분·1회용(쓰면 폐기)           | 계속 유효(취소 전까지)               |
| 쓰는 곳 | 등록(페어링) 단 한 번           | 매 SSE/POST 인증마다(`Bearer`)       |
| 왜      | 사람이 짝짓는 입장권            | IP 바뀌어도 신원 유지(재입력 불필요) |

- **등록(코드) = 새로 생성**: 그 하위의 첫 페어링이라 지울 "기존"이 없다 → 새 기기 레코드 + 새 토큰 생성, 코드는 '사용됨'으로 폐기.
- **재연결(토큰) = 파이프만 교체**: IP가 바뀌어도 _기기·토큰은 그대로_ 재사용. 서버가 갈아끼우는 건 §4-1처럼 죽은 **파이프 핸들뿐**(기기·토큰 삭제 아님).
- (선택) 같은 하위를 나중에 재등록(재설치 등)하면 옛 토큰 무효화 후 재발급 — 정책은 §13.

### 6-1. 기기코드 발급 화면 (Admin UI) — 하위에 넣어줄 두 값을 한 화면에

> 운영자가 하위에 입력해야 하는 값은 **딱 두 개: ① 서버 주소 ② 단기 기기코드**(장기 토큰은 등록 성공 시 서버가 자동 발급·하위가 자동 저장, 사람이 입력 안 함). 그래서 발급 화면은 이 둘을 **함께** 보여주고 운영자가 복사해 하위에 옮기게 한다.

```
┌─────────────────────────────────────────────┐
│ 기기 등록                                       │
│                                               │
│  서버 주소 :  http://123.45.67.89:8080  [복사]   │  ← 항상 표시(서버 자기 주소 자동), 모든 하위 공통
│                                               │
│            [ 기기코드 발급 ]                     │  ← 누르면 아래 코드 생성
│                                               │
│  기기코드 :  8237          (09:42 남음)  [복사]   │  ← 버튼 누른 뒤 표시, 1회용·10분 만료, 하위마다 새로 발급
│                                               │
│  "각 하위 앱 설정에 위 두 값을 입력하세요"           │
└─────────────────────────────────────────────┘
```

- **서버 주소**: 서버가 자기 공인 주소를 **항상 표시**(버튼 누르기 전부터 화면에 떠 있음, 입력칸 아님 = 읽기 전용 라벨). **모든 하위에 동일한 값**이 들어감(설치 때 1회).
  - (공인 IP 표시는 기존 `fetch_external_ip`(ipify, `auth/adb.rs`) 재사용 가능. 공유기 뒤면 포트포워딩 필요 — §2·대화기록 §7.)
- **기기코드**: [기기코드 발급] 클릭 시 서버가 단기 코드 생성(`POST /admin/device-codes`, §10) → **서버 주소 줄 아래에** 표시 + 만료 카운트다운. **1회용·하위 1대당 1개**, 등록되면 폐기.
  - **하위가 여러 대면 발급도 대수만큼**: 하위 3대면 [기기코드 발급]을 (보통) **3번** 눌러 코드 3개를 만들어 각각 다른 하위에 입력한다. **한 코드로 여러 대를 붙이지 않는다**(대마다 새 코드). 단 **서버 주소는 3대 모두 같은 값**.
- **복사 버튼**: 서버 주소·기기코드 각각에 [복사] 하나씩, 또는 "둘 다 복사" 버튼 하나 — 구현 시 택일(사소).
- 운영자는 두 값을 복사해 **하위 앱 설정 화면**(아래)에 옮긴다.

### 6-2. 하위 앱 등록 화면 — 사람이 입력하는 칸은 두 개뿐

```
[하위 앱 설정]
 서버 주소 : [ http://123.45.67.89:8080 ]   ← ① 설치 때 1회(모든 하위 공통)
 기기코드  : [ 8237 ]                        ← ② Admin이 발급한 1회용 코드
            [ 등록하기 ]
```

- [등록하기] → `POST /device/register {code}` → 서버가 코드 검증 후 **장기 토큰 자동 발급**(사람이 입력하는 값 아님) → 하위가 저장 → 곧바로 `GET /agent/stream` SSE 연결 + 하트비트 → Admin 목록에 `online` 표시.
- 이 순간부터 Admin 명령이 그 하위에서 실행됨(네이버 로그인 명령만 IP 로테이션 동안 §4대로 잠깐 비활성·자동 재연결).
- (서버 주소 입력칸·기기코드 입력칸·연결 상태 표시는 신규 화면 `src/features/device-register/`, §9.)

### 6-3. 기기 연결 페이지 (Admin UI 통합 화면) — 위=발급, 아래=연결 현황

> 운영자가 보는 **하나의 "기기 연결" 페이지**. 화면을 **위/아래 절반**으로 나눠, 위에서 하위에 넣어줄 값을 발급·복사하고, 아래에서 연결된 하위들의 현황을 본다. (상세 목업·동작은 `docs/Admin UI/01-기기연결.md`)

```
┌──────────────────────────────────────────────┐
│ 상단 절반 — 기기코드·서버주소 발급/복사 (§6-1)         │
│  서버 주소 : http://123.45.67.89:8080   [복사]    │  ← 항상 표시(읽기전용)
│            [ 기기코드 발급 ]                       │
│  기기코드 : 8237        (09:42 남음)    [복사]    │  ← 발급 후 표시, 1회용
├──────────────────────────────────────────────┤
│ 하단 절반 — 연결된 컴퓨터 현황            [새로고침]   │
│  🖥  하위-001                                   │
│       ● connected                              │  ← 초록 원
│  🖥  하위-002                                   │
│       ○ disconnected                           │  ← 회색 원 + 빨간 글씨
└──────────────────────────────────────────────┘
```

**상단 절반 — 발급/복사 (§6-1 그대로)**: 서버 주소(항상 표시) + [기기코드 발급] → 기기코드·만료 카운트다운 + [복사].

**하단 절반 — 연결된 컴퓨터 현황**

- 각 기기 행: **좌측 컴퓨터 아이콘** + 우측에 **상단=기기 이름**, **그 밑=상태 텍스트(`connected`/`disconnected`)**, 상태 텍스트 옆 **상태 원**.
  - `connected`: 상태 원 **초록불**, 텍스트는 기본색.
  - `disconnected`: 상태 원 **회색불**, 텍스트는 **빨간색**.
- **[새로고침] 버튼**: 수동 갱신(`GET /devices` 재조회). "기기가 연결됐는데 화면이 안 바뀌는" 경우를 대비한 안전장치.
- **연결 시 자동 새로고침 + 토스트**: 새 하위가 연결(등록 성공 → SSE 연결)되면 **화면이 자동으로 갱신**되고, **토스트 메시지 "OOO 기기가 연결되었습니다."** 가 뜬다. (자동 갱신이 원칙, 수동 새로고침은 보조.)
  - 구현 시 자동 갱신 트리거 = Admin이 연 `GET /admin/stream` SSE로 `{device_id, online}` 이벤트 수신(§3·§4-1) → 목록 갱신 + 토스트. (UI 목업 단계에선 더미 데이터로 동작만 시연.)
- 표시 대상·상태 정의는 §4 상태 머신을 따른다(`온라인/준비`=connected, 그 외=disconnected 계열).
- **각 기기 행 우측에 [기기 삭제] 버튼(휴지통 아이콘)**: 그 기기의 등록을 해제(§6-4). 실제로는 `DELETE /devices/{id}`. (UI 미리보기에선 목록에서 제거 + 토스트.) 코드: `src/admin/features/device-connection/device-connection.tsx`.

### 6-4. 기기 삭제 → 재등록 (연결 안 되는 기기 정리) (확정)

> 시나리오: 어떤 하위가 연결이 안 돼서, **등록된 기기를 지우고 새 기기코드를 발급해 다시 등록**하려는 경우.

```
1. [Admin] 기기 목록에서 그 기기를 [기기 삭제] (DELETE /devices/{id})
2. [서버]  기기표에서 그 줄을 삭제 → 그 기기의 장기 토큰은 매칭되는 기기가 없어 자동 무효
3. [Admin] [기기코드 발급] 다시 → 새 코드(예: 5512)
4. [하위]  서버주소 + 새 코드 입력 → [등록하기]
5. [서버]  새 코드 검증 → 새 device_id + 새 기기토큰 발급 → 하위 저장 → SSE 재연결 → online
```

- **기기 토큰 회수 = "기기표 줄 삭제"로 끝**(확정). 서버는 `device_id → 토큰/상태` 표(§4-1 라우팅 표와 같은 곳)를 들고 있으므로, **그 줄을 지우면 옛 토큰이 들어와도 매칭되는 기기가 없어 거부**된다. 운영자(JWT) 쪽의 "버전 +1"과 달리, 기기는 별도 버전 칸 없이 삭제만으로 깔끔하게 무효화된다(§5 인증 방식 참고).
- **왜 기기는 버전이 필요 없나**: 재등록은 "같은 기기번호 유지"가 아니라 **새 device_id로 새로 페어링**이라, 옛 줄을 지우면 옛 토큰이 가리킬 대상 자체가 사라진다. (버전 방식은 "같은 신원 유지 + 옛 토큰만 무효"가 필요할 때 쓰는 것 — 기기 삭제엔 불필요.)
- 권한: 기기 삭제는 §5 권한 모델상 **승인된 운영자 누구나** 가능(운영자 삭제만 SuperAdmin 전용).
- 안전: 삭제는 되돌리기 불가(재등록하면 새 토큰). 삭제 사실은 감사로그/통신로그(§10-5)에 남긴다.

## 7. 데이터 소유 (계정은 "한 시점에 한 곳" — Admin 스테이징 → 분배 시 하위로 이전(MOVE))

> 핵심(A-1 확정): 계정 ID/PW는 **분배 전에는 Admin(서버)에 잠깐 머무는 스테이징**이고, **분배하면 하위로 옮겨가며(MOVE) Admin 계정 화면은 텅 빈다.** 같은 계정이 동시에 두 곳에 존재하지 않으므로 **동기화·정답 충돌이 원천적으로 없다.**

| 데이터                      | 저장 위치                                                                         | 정답본(source of truth)       |
| --------------------------- | --------------------------------------------------------------------------------- | ----------------------------- |
| 계정 ID/PW(자격증명)        | 분배 전: **Admin/서버 스테이징**(at-rest 암호화) → 분배 후: **하위 로컬**(이전됨) | 분배 전=Admin, 분배 후=하위   |
| 쿠키(`cookies/*.json`)      | 하위 로컬                                                                         | 하위 (서버 전송 안 함)        |
| 게시큐·게시물·통계          | 하위 로컬                                                                         | 하위                          |
| 계정 로그인 결과 이력(누적) | 하위 로컬 ledger → Admin에 보고(§10-4)                                            | 하위(원본) / Admin(보고 사본) |
| 운영자 계정·역할            | 서버 DB                                                                           | 서버                          |
| 기기 등록·토큰              | 서버 DB                                                                           | 서버                          |
| 감사로그(명령/결과 이력)    | 서버 DB                                                                           | 서버                          |

작동 모델(A-1 확정):

- **Admin = 입력+분배 창구(스테이징)**: 운영자가 계정을 추가하면 서버 스테이징에 쌓인다 → "분배하기"로 하위에 균등 전송 → **전송된 계정은 스테이징에서 제거되어 Admin 계정 화면이 텅 빈다** → 운영자는 다시 새 계정을 입력한다.
- **분배 후 정답은 하위**: 하위가 로그인하며 실패 계정 자동 삭제·보류/대기초과 유지 등 모든 변화의 정답을 가진다. Admin은 그 계정을 더는 들고 있지 않으므로 **죽은 계정을 다시 뿌릴 일이 없다.**
- **비번 수정 시나리오**: 분배 전이면 Admin에서 고쳐 보내면 된다. 이미 분배했으면 Admin은 비어 있으니, 계정 추가로 새 ID/PW를 넣고 대상 컴퓨터를 골라 다시 보낸다. 옛 비번 계정은 하위에서 **비번오류(실패)로 자동 삭제**되어 알아서 정리된다.
- **쿠키·로그인은 하위 자기 IP로**: 네이버 쿠키는 로그인 당시 IP·기기에 묶여, 중앙 한 IP에서 몰아 로그인하면 안티봇에 무더기 차단된다(§10-2). 쿠키 본문은 서버로 보내지 않는다.
- 자격증명이 스테이징 동안 서버에 있으므로 **at-rest 암호화·접근통제·TLS 필수**(§12 리스크).

> **계정 ID/PW 암호화 방식 = AES-256-GCM (at-rest, 확정)**
>
> - **at-rest** = "저장돼 가만히 있는 상태"(DB 파일에 저장될 때). 데이터 3상태 중 하나(at-rest 저장 / in-transit 전송=TLS / in-use 사용). 즉 **DB에 계정 ID/PW를 저장할 때 암호화해서 둔다** → DB 파일이 통째로 유출돼도 키 없이는 못 읽음.
> - **해시(argon2)가 아니라 암호화인 이유**: 계정 ID/PW는 하위에 보내 **실제 네이버 로그인에 써야** 하므로 원문 복원이 가능해야 한다(양방향 암호화). 반면 **운영자 로그인 비번은 복원할 필요가 없어 해시(argon2, 단방향)** 로 — 둘은 다루는 법이 정반대(§5).
> - **후보**: AES-256-GCM(업계 표준 대칭키, x86 CPU에 하드웨어 가속 AES-NI 내장) vs ChaCha20-Poly1305(하드웨어 가속 없이 SW로 빠름, 모바일/임베디드 유리). 둘 다 AEAD(암호화+변조감지)라 보안은 동급.
> - **선택 = AES-256-GCM**: 회사 PC(x86)는 AES-NI 가속이 있어 가장 빠르고, Rust 생태계에서 가장 표준적이라 **구현이 단순**(사수의 "복잡·무겁게 하지 말 것"에 부합). ※ 암복호화는 분배 때만 잠깐 도는 가벼운 연산이라 **서버 상시 부담과는 무관**(서버 부담은 DB·인증 방식이 좌우 — 둘 다 가벼운 쪽 채택).
> - 남는 세부(§13): 키 저장 위치·회전 정책.

## 8. 기존 코드 재사용 — Transport 추상화 seam

현재 React UI는 `src/shared/ipc`에서 로컬 Tauri(`invoke`)를 호출한다. 여기에 **transport 인터페이스**를 도입한다.

```ts
// 개념도
interface Transport {
  invoke<T>(command: string, args: unknown): Promise<T>;
  subscribe(event: string, cb: (e) => void): Unsubscribe;
}
// 하위(데스크톱):     TauriTransport   → 로컬 invoke 그대로
// Admin 웹(브라우저):  HttpSseTransport → 선택된 하위로 명령 전달 + SSE 수신
```

- **같은 React 컴포넌트**(`features/{accounts,dashboard,posts,queue,notifications}`)를 하위/Admin이 공유. 호출 대상만 transport로 분기.
- 하위는 기존 동작 그대로(로컬). Admin 웹은 "현재 선택된 하위"를 대상으로 동일 화면을 원격 조작.
- 기존 백엔드·플랫폼 모듈(`naver_cafe/`, `naver_blog/`, `band_*`, `forum_stocks/`, `naver_clip/`)은 **무손상**.

> **MVP 범위 주의**: 이 transport seam은 "하위 모든 화면 원격 미러링"을 위한 **장기 메커니즘**이다(P5). **MVP 단계의 Admin 웹은 자체 관리화면(인증·기기 모니터링·계정 분배·결과 보고)만** 만들면 되며, 큐·게시 등 전 화면을 웹에서 원격 조작하는 것은 그 다음 단계다. 데스크톱 전용 호출(파일 dialog 등)의 웹 대체는 transport 도입 시 함께 처리(§13).

## 10-1. 대표 명령 시나리오 — Admin 엑셀 → 하위 일괄등록 → 게이트 후 전체 선택 로그인

> 요구: Admin에서 ID/PW가 담긴 `.xlsx`를 하위로 보내면, 하위가 **기존 '엑셀 가져오기'와 똑같이** 계정을 등록하고, **모두 등록된 뒤에야** 전 계정을 선택해 **선택 로그인**까지 자동 수행.

### (1) 파일 전달 — 기존 import 로직 재사용이 핵심

현행 `import_accounts(path)`(`src-tauri/src/ipc/excel.rs:76`, calamine)는 **로컬 파일 경로**를 읽어 계정을 로컬 등록한다. Admin의 엑셀은 하위 디스크에 없으므로, **파일(또는 데이터)을 하위로 옮긴 뒤 이 함수를 그대로 호출**한다(신규 파싱 로직 안 만듦).

```
1. [Admin 웹]  .xlsx 선택 → POST /devices/{id}/files (multipart)  ※ ID/PW 포함 → TLS 필수
2. [서버]      파일 보관(또는 짧은 만료 URL) → 명령 push:
               { type:"import_accounts", file:<base64 인라인 또는 다운로드 ref> } → 하위 SSE
3. [하위]      파일 수신 → 로컬 임시파일로 저장 → import_accounts(임시경로) 호출(변경 없음)
               → 계정 로컬 등록(지금 '엑셀 가져오기' 버튼과 100% 동일 동작)
4. [하위]      결과 POST: { imported:N, skipped:M, loginIds:[...] } → Admin 표시, 임시파일 삭제
```

- 파일 전달 방식: ID/PW 엑셀은 보통 수 KB라 **명령 JSON에 base64 인라인**이 가장 단순(별도 다운로드 엔드포인트도 가능). **보안: 평문 금지(TLS), 서버 잔류 파일은 import 후 즉시 삭제.**

### (2) "모두 등록되면 → 전체 선택 → 선택 로그인" (하위에서 게이트)

게이트를 **하위 안의 순차 명령**으로 잡아 원자성을 보장한다(Admin이 두 명령 타이밍을 맞출 필요 없음):

```
명령: { type:"import_then_login_all" }
 하위 실행:
  단계1) import_accounts(임시파일) → 등록 완료까지 대기  ← 이게 게이트. 실패행은 결과에 표시
  단계2) ★등록이 끝난 뒤에만★ 방금 등록된 계정 전체를 '선택'으로 잡고
  단계3) 기존 선택 로그인 경로(buildLoginNowItem / isSelectiveLoginPlatform) 호출
  각 단계 진행률을 같은 commandId로 그때그때 POST → Admin 실시간 확인
```

- 자동/수동 선택: 단계1·단계2를 분리해 "등록 결과 확인 후 운영자가 로그인 버튼"식 **수동 게이트**도 가능(§13에서 확정).

### (3) ⚠️ 선택 로그인은 IP를 바꾼다 — §4-1과 직접 맞물림

단계3의 선택 로그인 = 네이버 로그인 = **ADB IP 로테이션 → SSE 끊김 → 재연결**. 따라서:

- 로그인 직전 하위가 `ROTATING` 통보 → Admin 버튼 비활성(§4).
- 재연결되면 하위가 **같은 `commandId`로 진행률/결과를 이어서 POST**(§4-1 (6) 멱등) → Admin이 끊김 없이 이어받음.
- 계정이 여러 개면 **로그인마다 IP가 바뀔 수 있으므로**, 진행률 보고가 재연결을 건너뛰어도 누락·중복 없이 이어지도록 설계.

### (4) 로그인 후 자동 정리 — 실패 계정 자동 삭제(보류·대기초과는 유지)

> 요구: 선택 로그인을 전부 돌린 뒤, **로그인이 안 되는(실패) 계정은 자동 삭제**한다. 단 **보류(OnHold)·대기초과(TimedOut)는 무조건 유지**(사람이 직접 인증·로그인하거나, Admin이 "그 계정만 로그인" 명령으로 처리).

로그인 결과 상태(`outcome.rs`)별 처리:

| 결과 상태                     | 처리     | 이유                                        |
| ----------------------------- | -------- | ------------------------------------------- |
| `Active`(성공)                | **유지** | 정상 로그인                                 |
| `OnHold`(보류: 캡차·본인인증) | **유지** | 사람이 직접 풀면 회복 — 절대 삭제 안 함     |
| `TimedOut`(대기초과)          | **유지** | 페이지 대기/500 등 일시적 — 절대 삭제 안 함 |
| `BadCredentials`(비번오류)    | **삭제** | 로그인 실패                                 |
| `Challenge`(추가인증 필요)    | **삭제** | 로그인 실패(사용자 지시로 삭제 포함)        |
| `Blocked`(차단/잠김)          | **삭제** | 로그인 실패(사용자 지시로 삭제 포함)        |
| `Error`(네트워크/환경)        | **삭제** | 로그인 실패                                 |

→ **규칙 한 줄: `Active`·`OnHold`·`TimedOut`이 아닌 모든 로그인 실패 = 자동 삭제.**

**메커니즘(기존 부품 재사용, 트리거만 신규)**

```
하위: 선택 로그인 전부 실행 → 각 계정 결과 상태 수집
  → 삭제 대상(위 표) loginId 모음 → 기존 delete_accounts(ids) 호출(로컬 레코드 제거)
  → 결과 POST: { logged_in:[...], kept_onhold:[...], kept_timedout:[...], deleted:[{id, 사유}...] }
     ← 어떤 계정이 왜 지워졌는지 Admin에 회신(감사로그). 삭제는 되돌리기 불가라 회신 필수.
```

- **이미 있는 코드**: 선택 로그인(종토·블로그, #228), 보류 재로그인 시 사람이 직접 인증(`login.rs` `manual_captcha`, 120초), 계정 삭제(`accounts.rs::delete_accounts`). → **"실패 시 자동 삭제" 트리거만 신규 추가.**
- **유지된 보류·대기초과 처리**: 사람이 직접 인증/로그인, 또는 Admin이 그 계정들만 지목해 선택 로그인 명령(기존 선택 로그인 + `manual_captcha` 재사용).
- ⚠️ **되돌리기 불가**: 삭제 전 대상 목록을 결과로 회신/감사로그 남김. 즉시삭제 vs "Admin 확인 후 삭제" 옵션은 §13.

## 10-2. Admin 스테이징 → 수동 분배(MOVE) → 하위 로컬 로그인 (사수 지시 반영)

> 사수 지시: 계정 ID/PW를 **Admin(서버)에 모아 두고**, **여러 하위에 나눠 배분**한다(예: 10개 → 3대에 4·3·3). §10-1이 "Admin이 하위 1대에 엑셀을 직접 배달"이라면, 여기는 "**Admin에 모아 두고 체크박스로 골라 하위에 갈라 뿌림(보낸 건 Admin에서 비워짐)**"이다.

### 핵심 — 무엇을 스테이징하고 무엇을 안 하나

- **스테이징 저장(서버 DB, 분배 전까지만)**: 계정 **ID/PW 목록**(자격증명). 분배하면 하위로 **MOVE**되어 스테이징에서 제거 + **분배 이력**(어느 계정을 어느 대에 보냈는지, 감사로그).
- **중앙저장 안 함(하위 로컬 유지)**: **쿠키**·게시큐. **로그인도 각 하위가 자기 폰 IP로** 직접 수행.
- **왜 쿠키·로그인은 중앙에서 안 하나**: 네이버 쿠키는 **로그인 당시 IP·기기에 묶인다.** 중앙(Admin 한 IP)에서 1000개를 몰아 로그인해 쿠키를 뿌리면 "발급 IP ≠ 사용 IP"라 안티봇에 무더기 차단된다. 이 앱이 폰 테더링 + ADB IP 로테이션으로 IP를 흩뿌리는 이유가 바로 그것. → **분배되는 것은 자격증명(ID/PW)이지 쿠키가 아니다.**

### 흐름

```
1. [Admin 웹]  계정 추가/엑셀 가져오기 → 서버 스테이징에 저장(at-rest 암호화)
2. [Admin 웹]  상단에서 뿌릴 계정 N개 + 하단에서 연결된 하위 M대 체크 → "분배하기"(§10-3)
3. [서버]      N개를 M대에 균등+랜덤 분배(겹침 없음) → 대별 명령 push
               → ★보낸 계정은 스테이징에서 제거(=Admin 계정 화면 텅 빔, MOVE, §7)
4. [하위]      받은 계정 import_accounts 로컬 등록 → ★전부 등록 확인(§10-3 등록완료 판정)
               → 계정 화면 1회 새로고침 → 전체 선택 → ★자동 전체 로그인(자기 폰 IP) → 쿠키 로컬 저장
5. [하위]      결과 분류(성공/보류/대기초과/실패)·실패 자동 삭제 → Admin에 보고(§10-4 형식)
6. (로그인이 IP를 바꾸므로 §4-1 재연결·멱등 그대로 적용)
```

### 분배 규칙 (확정)

- **계정 1개 = 하위 1대에만**(겹침 없음). 같은 계정을 두 대가 동시 로그인하면 네이버가 세션 충돌·차단하므로 절대 중복 금지.
- **분배는 운영자가 체크박스로 계정·하위를 직접 골라 수동 실행**(§10-3). "온라인 하위 전체 자동 분배"는 채택하지 않음. → 오프라인 하위는 애초에 목록에 안 떠 못 고르므로 "오프라인 몫·재배분" 문제도 사라짐.
- **분배 = MOVE**: 보낸 계정은 Admin 스테이징에서 제거되어 한 시점에 한 곳에만 존재(§7). 죽은 계정 재분배 문제 없음.
- 분배 직후 하위는 **등록 확인 → 자동 전체 로그인**까지 진행(§10-3), 결과는 **전부 Admin에 보고**(§10-4).
- **실패 계정 자동 삭제**(`Active`·`OnHold`·`TimedOut` 외 전부): 삭제 전 ID/PW·사유를 보고에 담은 뒤 로컬 삭제(§10-1 (4), §10-4).
- **(확정) 분배 대상 계정 = 종토(종토방) 가정**: 자동 전체 로그인은 기존 **종토 선택 로그인 경로**(`isSelectiveLoginPlatform`/`buildLoginNowItem`, 종토·#228 §10-1 (2))를 **그대로 재사용**한다. 블로그·카페·밴드·클립 등 타 플랫폼 확장은 추후(이번 구현 범위 아님).

## 10-3. Admin 분배 화면 (UI) — 체크박스로 계정·하위 선택 → 균등+랜덤 분배

> 요구(사수 지시 구체화): Admin "1페이지"에서 계정을 한곳에 다 넣어두고, 연결된 하위 컴퓨터를 체크박스로 골라 **분배하기**를 누르면, 선택한 계정이 선택한 컴퓨터 수에 맞게 **겹치지 않게·균등하게·랜덤으로** 나뉘어 전송된다. (예: 10개를 3대에 → 4·3·3, 남는 1개는 임의의 한 대로)

### 화면 레이아웃 (위/아래 절반)

```
┌──────────────────────────────────────────────┐
│ 상단 절반 — 계정 풀 (기존 '계정 추가' 화면 재사용)        │
│  [계정 추가] [엑셀 가져오기]         총 N개 계정         │
│  ┌──────────────────────────────────┐ ▲      │
│  │ ☐ id001 / ****                   │ │스크롤 │  ← 최대 8행만 보임
│  │ ☐ id002 / ****                   │ │       │     더 보려면 좌측 스크롤바
│  │ … (최대 8행) …                    │ ▼      │
│  └──────────────────────────────────┘        │
├──────────────────────────────────────────────┤
│ 하단 절반 — 하위 컴퓨터 목록 (등록+연결된 것만)          │
│  ☐ 하위A (online, IP …)                       │
│  ☐ 하위B (online, IP …)                       │
│  ☐ 하위C (online, IP …)                       │
│                                  [ 분배하기 ]  │  ← 계정·컴퓨터 둘 다 1개↑ 선택 시 활성

```

**상단 절반 — 계정 풀 (기존 계정 추가 화면 재사용)**

- [재사용 UI / 신규 저장경로] `src/features/accounts/accounts.tsx`의 계정 추가/엑셀 가져오기 **화면은 재사용**(계정 추가 버튼 `:634`)하되, Admin 웹에서는 §8 transport(HttpSse)로 동작해 **서버 스테이징(§7)** 에 기록한다. ⚠️ `import_accounts`(로컬 store 전용)로는 못 넣으므로 **서버 스테이징 저장 로직은 신규**(UI만 재사용, 백엔드 저장은 새로 만든다).
- [재사용] 계정 개수 표시 `accounts.tsx:864`("총 N개 계정").
- [재사용] 행 체크박스 패턴 `accounts.tsx:737–780`(`sel` 배열, 헤더 전체선택 + 행별 체크).
- [수정(스타일만)] 목록을 **최대 8행 고정 높이 + 세로 스크롤(좌측 스크롤바)** 로. 기존 테이블에 컨테이너 높이/overflow 스타일만 추가 — **로직 무손상**.

**하단 절반 — 하위 컴퓨터 목록**

- [신규] **기기등록 완료 + 현재 연결(online)** 인 하위만 표시. §4 상태 머신에서 `온라인/준비`만 노출하고 `IP변경중`·`재연결`·`오프라인/꺼짐`은 제외. (`GET /devices` 결과를 online 필터)
- [재사용] 좌측 체크박스는 위 `accounts.tsx` 체크박스 패턴 그대로.

### "분배하기" 버튼 & 분배 규칙

- [신규] **분배하기 버튼**: 상단 계정 ≥1 **그리고** 하단 컴퓨터 ≥1 선택 시 활성화(둘 중 하나라도 0이면 비활성). 기존에 없으면 신규 생성.
- 누르면 선택 계정 N개를 선택 컴퓨터 M대에 분배:
  - [재사용] **균등 분배는 기존 `distributeStocksEvenly()`** (`src/features/posts/publish-helpers.ts:28–44`) 재사용 — 겹침 없이 N을 M으로 갈라 각 대 `⌊N/M⌋` 또는 +1(대별 차이 최대 1). (검증: 18개/4대 → `[5,5,4,4]`, `publish-helpers.test.ts`)
  - ⚠️ [신규(셔플 1줄만)] 기존 함수는 **나머지를 앞 버킷에 몰아주는 결정적(deterministic)** 방식이라 "랜덤"이 아니다. 요구의 _랜덤_ 충족을 위해 **분배 직전에 계정·컴퓨터 순서를 한 번 셔플**해서 넣는다. → 균등 로직은 그대로 재사용하고 **순수 함수 `distributeStocksEvenly`는 수정하지 않음**(앞에 셔플만 추가).
  - **나머지 처리**: 10 ÷ 3 = 3·3·3 + 남은 1 → 셔플된 순서상 맨 앞 1대가 +1(=4). 어느 대가 +1 받을지는 셔플 때문에 매번 달라짐 → "아무 데나 추가" 충족.
  - **겹침 없음**: 계정 1개 = 정확히 1대(§10-2 분배 규칙과 동일, 서버가 분배 시 중복 금지 보장).

### 분배 후 흐름 (등록 확인 → 새로고침 → 자동 로그인)

```
[Admin] 분배하기 클릭
  → 계정·컴퓨터 셔플 → distributeStocksEvenly(계정, 선택 컴퓨터 수)로 대별 몫 산출
  → 대별로 명령 발행  POST /devices/{id}/commands { type:"distribute_accounts", accounts:[{id,pw}...] }
                     (명령은 §3대로 그 하위가 연 SSE 파이프로 내려감)
  → ★보낸 계정은 Admin 스테이징에서 제거 → Admin 계정 화면 텅 빔(MOVE, §7)
[하위] 명령 수신 → import_accounts 로컬 등록 (excel.rs:76–159 재사용, §10-1 (1))
  → ★등록완료 판정(아래) 통과까지 대기 → 계정 화면 1회 새로고침(등록됐는지 눈으로 확인)
  → ★전체 선택 → 자동 전체 로그인(자기 폰 IP, 종토 선택 로그인 경로 재사용) → 쿠키 로컬 저장
  → 결과 분류·실패 자동 삭제 → Admin에 보고(§10-4)
```

**등록완료 판정 방법** (요구: "다 등록된 것을 확인하는 방법"):

- 하위는 분배 명령에 담겨온 **계정 수 K**(= 받은 `loginId` 목록)를 안다.
- `import_accounts` 반환 후, 로컬 store에 **그 K개 `loginId`가 모두 존재**하면 등록완료로 본다.
  - 판정식: `import 결과의 imported + skipped(이미 존재) 합 == K`, 또는 store 재조회로 K개 `loginId` 전부 확인.
- 등록완료일 때만 **화면 1회 새로고침**(계정이 추가됐는지 확인용) → **전체 선택 → 자동 로그인**으로 진행.
- 새로고침은 분배 직후 "로그인 안 된 채로 추가된 상태"를 확인시키는 용도이며, 그 직후 자동 로그인이 이어진다.

### 분배 계정을 하위 로컬에 넣는 방식 = ② store 직접삽입 + import_accounts 검증 재사용 (확정)

> 결정(§13 B-4 확정): 분배된 계정은 네트워크를 타고 **JSON 데이터**로 하위에 도착한다(하위 디스크에 엑셀 파일이 없음). 이를 하위 로컬 store에 넣는 방식은 **② "임시 .xlsx 파일을 만들지 않고 store에 직접 삽입"** 으로 한다(비번 담긴 파일을 디스크에 떨구지 않아 더 안전). **단, 엑셀 가져오기(`import_accounts`)가 하던 검증·병합을 그대로 적용받는다.**

**어떻게 ②가 엑셀과 똑같은 검증을 받나 — 검증 로직을 함수로 추출해 두 경로가 공유**

현재 `import_accounts`(`excel.rs:76`)는 **(가) 엑셀 파싱**과 **(나) 검증·병합**이 한 함수에 붙어 있다. (나)만 떼어내 **순수 함수**로 만들고, 엑셀 경로와 분배(직접삽입) 경로가 **둘 다 그 함수를 호출**하게 한다. → 두 경로가 글자 그대로 같은 검증을 탄다.

```
// 신규(추출): 파싱된 계정 행들을 받아 검증·병합하는 공통 코어. 입력원(엑셀/JSON) 무관.
fn merge_account_rows(existing: Vec<Account>, rows: Vec<RawRow>) -> (Vec<Account>, ImportSummary)
   - 빈 loginId/pw/platform 행 → 건너뜀(skipped++) + "N행: 누락/오류" 기록   ← 빈줄 보강
   - 같은 배치 안 loginId 중복 → "중복 — 덮어씀" 기록                        ← 중복 감지
   - existing에 같은 login_id 있으면 → 기존 opaque id 보존하고 덮어씀          ← 중복 덮어쓰기
                          없으면     → 새 계정으로 추가
   - 반환: 병합된 목록 + ImportSummary{ imported, skipped, errors }

import_accounts(path):        엑셀 파싱 → rows → merge_account_rows(...)   // 엑셀 경로(기존과 동일 동작)
distribute_accounts(json):    JSON 파싱 → rows → merge_account_rows(...)   // 분배 경로(②) — 같은 검증 탐 ★
```

- **`import_accounts`의 겉 동작은 그대로**(엑셀 가져오기 버튼은 1도 안 변함). 내부에서 검증부만 `merge_account_rows`로 위임하도록 리팩터(로직 무손상, 기존 테스트 `import_accounts_*` 그대로 통과해야 함).
- **분배 경로(②)는 받은 JSON을 `RawRow`로 바꿔 같은 `merge_account_rows`에 넣는다** → 빈줄 건너뜀·중복 덮어쓰기·`ImportSummary` 집계까지 엑셀과 동일하게 적용. 등록완료 판정(위 `imported + skipped == K`)도 이 `ImportSummary`로 그대로 한다.
- 이 추출 리팩터는 서버·에이전트가 없어도 단독으로 가능한 **첫 안전한 구현 조각**이다(TDD: `merge_account_rows` 단위테스트 + 기존 `import_accounts` 테스트 회귀).

## 10-4. 하위 → Admin 로그인 결과 보고 형식 (배치별 상세 + 누적 합계)

> 대원칙: **하위에서 일어난 일은 전부 Admin으로 보고한다.** 분배받아 자동 로그인을 한 묶음(배치) 돌릴 때마다 ①이번 배치의 분류·상세 목록과 ②그 하위의 **누적 합계**를 함께 올린다. 보고는 로그인으로 IP가 바뀐 뒤 재연결되면 같은 `commandId`로 전송(§4-1).

### 상태 4분류 (outcome.rs 매핑)

| 보고 분류 | outcome.rs 상태                                              | 처리               |
| --------- | ------------------------------------------------------------ | ------------------ |
| 성공      | `Active`                                                     | 유지(로그인됨)     |
| 보류      | `OnHold` (캡차·전화번호 본인확인)                            | 유지 — 사람이 직접 |
| 대기초과  | `TimedOut`                                                   | 유지 — 성공 가능성 |
| 실패      | `BadCredentials`·`Challenge`·`Blocked`·`Error` 등 그 외 전부 | **자동 삭제**      |

→ 규칙 한 줄: **성공·보류·대기초과가 아니면 전부 실패 = 자동 삭제.** (비번오류·2차인증·보호조치·잠금·에러 모두 실패)

### 배치 보고 본문

예시 1 — 10개 중 `성공3 / 비번오류1 / 캡차1 / 전화번호1 / 보호조치1 / 대기초과3`
→ 분류하면 **성공3 / 보류2(캡차·전화번호) / 대기초과3 / 실패2(비번오류·보호조치)**.

```
성공 3 / 보류 2 / 대기초과 3 / 실패 2
보류 계정 2
  ID PW 보류사유 : (ex) 캡차
  ID PW 보류사유 : (ex) 전화번호 입력
대기초과 3
  ID PW
  ID PW
  ID PW
실패 2
  ID PW 실패사유 : (outcome.rs trace/메시지에 적힌 사유 그대로)
  ID PW 실패사유 :
총 받은 계정 10  성공 3 / 보류 2 / 대기초과 3 / 실패 2
```

- **성공 계정은 ID/PW를 적지 않는다(개수만).** 로그인돼 하위에 남아 있으니 따로 회신할 필요 없음.
- **보류·대기초과·실패만 ID·PW를 명시**한다. 보류엔 보류사유(캡차/전화번호 등), 실패엔 실패사유(trace/메시지), 대기초과는 사유 없이 ID·PW만.
- **실패 계정은 보고에 ID/PW·사유를 담은 뒤 로컬 삭제**(되돌리기 불가라 보고가 먼저 — §10-1 (4)).

### 누적 합계 (배치마다 갱신)

- 하위는 **자기가 지금까지 받은 모든 계정의 결과를 누적 집계(ledger)** 해서, 매 배치 보고 끝에 `총 받은 계정 X  성공 a / 보류 b / 대기초과 c / 실패 d`를 붙인다.
- 예시 2 — 같은 하위에 또 10개 분배(`성공3 / 비번오류2 / 캡차1 / 보호조치2 / 대기초과2` = 성공3·보류1·대기초과2·실패4):

```
성공 3 / 보류 1 / 대기초과 2 / 실패 4
보류 계정 1
  ID PW 보류사유 : (ex) 캡차
대기초과 2
  ID PW
  ID PW
실패 4
  ID PW 실패사유 :
  ID PW 실패사유 :
  ID PW 실패사유 :
  ID PW 실패사유 :
총 받은 계정 20  성공 6 / 보류 3 / 대기초과 5 / 실패 6
```

- 즉 **받을수록 누적이 쌓인다**(1차 10 + 2차 10 = 20, 성공 3+3=6, 보류 2+1=3, 대기초과 3+2=5, 실패 2+4=6).
- 누적 덕에 Admin은 **어느 컴퓨터(device_id)에 어떤 상태 계정이 얼마나 남았는지**를 항상 본다(특히 잔존하는 보류·대기초과 수량).

### 최종 잔량 & 보류 재로그인 (사람이 처리)

- 분배·로그인을 반복하면 실패는 모두 삭제되고 **하위엔 보류·대기초과만 남는다.** 이 잔량을 device별로 Admin에 보고.
- **보류 계정은 사람이 직접** 처리한다: 그 보류 계정만 선택해 **선택 로그인**하면, 첫 로그인과 달리 **`manual_captcha=true`로 동작**해 캡차·본인확인 창을 **사람이 풀 때까지 열어둔다**(`login.rs:23-24, 73-75`). (첫 로그인은 캡차가 뜨면 즉시 보류로 떨구지만, 보류 재로그인만 창을 열어 대기.)
- **대기초과 계정은 그대로 유지**(일시적 문제라 다음에 성공 가능). 필요 시 다시 선택 로그인.

### 10-4-1. 결과 보고 화면 표시 규칙 (마스킹·정렬·누적 스크롤)

> 사수/사용자 지시 반영. 보고 화면(`src/admin/features/result-report/`)에서 ID·PW를 보여줄 때의 표시 규칙.

- **마스킹 — ID·PW 모두 앞 2글자만 노출, 나머지는 `•`로 가린다.**
  - 예: `stock_id041` → `st•••••••••`, 비번 `ik7!naver22` → `ik•••••••••`.
  - 보류·대기초과·실패 행에 적는 ID·PW에 공통 적용(성공은 개수만이라 해당 없음).
  - 목적: 운영자가 어느 계정인지 식별은 되되(앞 2글자), 화면 노출로 비번 전체가 새지 않게.
- **열 정렬 — ID·PW 열을 고정폭으로 맞춰 세로 정렬.** (분류 섹션마다 표를 따로 그려 칸이 어긋나던 문제 해결: 보류=3열(ID·PW·사유), 대기초과=2열(ID·PW)이어도 ID·PW 열 위치는 동일.)
- **누적 스크롤 — 결과가 계속 쌓이므로** 한 device 카드의 상세 목록은 **일정 높이까지만 보여주고 나머지는 세로 스크롤(드래그바)** 로 내려서 확인한다(예: 최대 높이 약 260px, 초과분 스크롤). 누적 합계 줄은 카드 하단에 항상 고정 표시.
- (※ 계정 분배 화면(§10-3)은 운영자가 계정을 직접 골라야 하므로 **ID는 전체 표시**, PW만 마스킹 — 보고 화면과 다름. 분배 화면도 ID 마스킹할지는 추후 결정.)

### 10-4-2. 게시 결과 보고 — Admin이 "어디에·무엇을·왜 실패했는지"까지 본다 (기존 알림 모델 그대로)

> 사용자 지시: 결과 보고에 **로그인 결과만이 아니라 게시 결과도** 나와야 한다. 하위가 글을 **어디에** 게시했는지, **무엇을**(게시 내용·링크) 올렸는지, 실패면 **그 이유 + 자세히 보기(백트레이스)** 까지 — **데스크톱 앱 알림 화면(`notifications.tsx`)이 보여주던 그대로** Admin에서 본다.

**기존 부품 재사용(신규 모델 안 만듦)** — 데스크톱 앱이 이미 쓰는 게시 로그 모델을 그대로 가져온다:

- `LogBatch { items: BatchItem[] }`, `BatchItem { platform, target(어디에), loginId, status(success/fail/…), msg(친절한 사유), trace?(백트레이스), posted? }`, `PostedContent { title, body, comment?, url }` (`src/shared/data/types.ts`). 표시는 `notifications.tsx`의 `SubLog`와 동일한 UI(`src/admin/features/result-report/`).
- **성공**: `posted` → **[게시 내용]** 펼치면 실제 게시된 제목/본문/댓글 + **글 URL 링크**(클릭 시 열림). "글이 삭제돼도 무엇을 보냈는지" 보존(`PostedContent` 주석).
- **실패**: `trace` → **[자세히 보기]** 펼치면 **어두운 콘솔 박스에 백트레이스 그대로**.

**백트레이스가 어떻게 만들어지나 (코드 근거, `src-tauri/src/util.rs`)** — 게시/댓글 실패는 panic이 아니라 **에러 값**으로 흘러 자동 백트레이스가 없으므로, 실패 지점에서 직접 캡처한다:

- `backtrace_string()` = `Backtrace::force_capture()` — `RUST_BACKTRACE` 없이도 항상 스택 캡처.
- `here!()` 매크로 = **컴파일타임 `함수경로 (파일:줄)` 앵커** — 심볼이 `<unknown>`이어도 **실제 실패 지점의 file:line은 항상** 보임(`#[profile.release] debug=true`로 심볼 해석).
- `error_source_chain()`/`describe_reqwest_error()` = reqwest wrapper가 숨긴 **진짜 원인**(connection reset/timeout/DNS…)을 펼침.
- `transport_error_message!(prefix, e)` = `{prefix}: [분류] 원인체인` + `\n\nat {here!()}` + `\n\n{backtrace}` → 이 문자열이 곧 `BatchItem.trace`("자세히 보기" 본문).
- 분류(`queue_runner.rs`): 비번오류·차단·IP불일치 등 **정상 판정은 `trace: None`**(자동화 오류 아님), CDP/자동화/전송 오류만 `trace: Some(...)`. 메인 사유(`msg`)는 code 기반 한국어(`failure_reason`)로 분리.

**연결(하위 → Admin)**: 하위는 자기 로컬 게시 완료 로그(`LogBatch`)를 **이미 만든다**(데스크톱 앱과 동일). 에이전트가 그걸 Admin에 보고 → 결과 보고 화면이 같은 `SubLog` UI로 렌더. (미리보기는 더미 `LogBatch`.)

**마스킹**: 이 화면은 §10-4-1대로 **계정 ID 마스킹(앞 2글자)** 유지. 단 `posted`(게시 내용·URL)와 `trace`(백트레이스)는 자격증명이 아니므로 그대로 표시.

**표시 규칙 (사용자 지시)**:

- **컴퓨터(device)당 8곳까지만 보이고, 그 이상은 세로 스크롤(드래그바)** 로 내려서 확인(카드 본문 `ScrollArea`, `mah≈336px`). 게시 대상이 많아도 카드 길이가 폭주하지 않는다.
- **성공/실패 배지 = 클릭 필터**: 카드 헤더의 `성공 N`(초록)·`실패 N`(빨강) 배지를 누르면 **그 상태만** 보인다(성공만 / X 표시된 실패만). **다시 누르면 전체**로 복귀(옆 `전체 보기` 버튼으로도 해제). 활성 배지는 채워진(filled) 스타일로 강조. 필터는 카드(컴퓨터)마다 독립.

## 10-5. 통신 로그 화면 (Admin) — 감사로그 콘솔 + 내보내기

> 사용자 지시: 사이드바 "비밀번호 변경" 아래에 **통신 로그** 화면을 둔다. **모든 컴퓨터(하위)의 통신 내용**을 한 곳에서 보고, 위쪽 **[내보내기]** 버튼으로 전체를 **`.txt` 로그 파일**로 저장한다. 윈도우 PowerShell/명령창처럼 **콘솔(모노스페이스·어두운 배경)** 로 보여준다. 이 화면이 §7 **감사로그(명령/결과 이력)** 의 조회 창구다.

### 무엇이 보이나 (Admin↔하위 모든 통신)

- **Admin → 하위 명령** (`[CMD]`): 운영자가 발행한 명령 + **무엇을 보냈는지 인자까지** (distribute_accounts면 몇 건·어느 계정(ID/PW 평문), delete_accounts면 어느 ID/PW·사유) + `commandId` + 발행 operator.
- **하위 → Admin 결과** (`[RESULT]`): **계정별로 한 줄씩** — 어느 계정(ID/PW 평문)이 성공/보류/실패인지 + 사유. 끝에 배치 집계(성공/보류/대기초과/실패) 한 줄. (※ "3/10" 같은 **집계만 찍지 않는다** — 계정별 결과를 다 남긴다.)
- **하위 → 서버 하트비트/상태** (`[HEARTBEAT]`/`[STATE]`): 하트비트=주기적 "살아있음 + 현재 IP" 보고. `[STATE]`=`ROTATING` 등 §4 상태 전이(IP 회전 시작 시 기존 IP 명시).
- **연결/등록** (`[SSE]`/`[REGISTER]`): 스트림 연결·끊김·재연결, 기기코드 등록·토큰 발급. 재연결은 **`기존 IP → 바뀐 IP`** 를 모두 적는다(`adb.rs`의 IP 회전 로그와 동일).
- **거부된 명령** (`[REJECT]`): ROTATING/재연결/오프라인 하위로 명령이 들어와 서버가 거부한 경우 — `device_name`(대상 컴퓨터)·`명령`(타입+한글)·`commandId`·`사유`(대상 상태+거부코드 409)·`operator`·`src`(핸들러 절대경로:줄)를 남긴다(§4-2).
- **명령 줄의 공통 필드**: 모든 `[CMD]`/`[REJECT]` 줄은 명령 타입에 **한글 설명**(`import_then_login_all(전체로그인)`, `distribute_accounts(계정 분배)`, `delete_accounts(계정 삭제)`)과, 가능하면 그 명령 핸들러의 **소스 절대경로:줄(`src=`)** 을 함께 적어, 로그만 보고 무슨 명령인지·코드 어디인지 알 수 있게 한다.

### 표시 형식 (기존 tracing 컨벤션 재사용)

- 한 줄 = `시각  [태그]  방향(Admin → 하위-001)  메시지`. 모노스페이스 콘솔.
- 태그별 색: `[CMD]` 파랑 / `[RESULT]`·성공 청록 / 실패·`[REJECT]` 빨강 / `[STATE]`·경고 노랑 / `[HEARTBEAT]`·정보 회색.
- **표시 정책(운영자 결정) — 통신 로그에 한해 ID·PW를 마스킹 없이 그대로 표시**: 운영자가 "어느 ID/PW로 로그인했고 결과가 뭔지"를 로그만으로 추적할 수 있게, **이 통신 로그 화면에서는 ID·PW를 평문으로** 보여준다(계정별 로그인 결과·분배·삭제 줄 모두). **단 통신 로그 한정** — 결과 보고 화면(§10-4-1)·다른 화면은 마스킹(앞 2글자+`•`) 유지.
  - ⚠️ **보안 영향(반드시 인지)**: 이 결정은 기존 "PW 미로깅" 규칙(`auth/util.rs::mask_id` 주석 + `logging.rs` 테스트)을 **통신 로그 채널에 한해 의도적으로 푸는 것**이다. PW가 **서버 감사 DB·Admin 화면·내보낸 `.txt`** 에 평문으로 남으므로, 그 채널의 at-rest 암호화·접근통제·내보내기 파일 취급에 주의(§12). 구현 시 통신 로그용 데이터 경로는 `mask_id`를 거치지 않도록 별도 처리하고, `logging.rs`의 로컬 tracing(하위 로그 파일) 규칙은 그대로 둔다(로컬 tracing엔 여전히 PW 안 찍음).
- 컴퓨터 필터(전체/특정 하위)로 좁혀 보기 가능.

### 로그 상세 규칙 (사용자 지시 — "함축하지 말고 세세하게")

> 핵심: 운영자가 로그만 보고도 **어느 컴퓨터가 / 어느 계정으로 / 무엇을 했고 / 결과가 무엇인지**를 알 수 있어야 한다. 집계로 뭉뚱그리지 않는다.

- **계정별 로그인 결과**: 분배받아 자동 로그인할 때, **계정 하나당 결과 한 줄**(`c-1001 로그인 chol_invest / ch0lInvest! → 성공(Active) ✅` / `… viptrade77 / vipTrade@77 → 캡차 → 보류(OnHold)` / `… dki_master / dkiMaster12 → 비번오류(BadCredentials) → 실패`). ID·PW 평문(통신 로그 한정). 배치 끝에 집계 한 줄.
- **IP 변경**: `[STATE] ROTATING — IP 회전 시작 (기존 IP …)` → 재연결 시 `[SSE] 재연결 성공 · 기존 IP … → 바뀐 IP … (✓ IP 변경됨, 토큰 동일)`. **기존/바뀐 IP를 둘 다** 남긴다(`adb.rs` 회전 로그와 일치).
- **비행기모드 동안은 대기**: IP 회전 중(SSE 끊김)에는 보고를 못 보내므로, **재연결된 뒤 밀린 결과를 같은 `commandId`로 몰아서** 올린다(§4-1 멱등).
- **분배 명령**: `distribute_accounts 4건 → chol_invest/ch0lInvest!, moa_stock7/moaStock#22, … (commandId=…, operator=…)` — 건수와 대상 계정(ID/PW 평문)을 적는다.
- **삭제 명령**: `delete_accounts 1건 → dki_master / dkiMaster12 (사유: 비번오류)` — **어느 ID/PW를 왜 지웠는지** 명시(되돌리기 불가라 회신 필수, §10-1 (4)). 결과 줄엔 유지된 보류·대기초과도 표기.
- **명령 거부**: `[REJECT] 거부: device_name=하위-002 명령=import_then_login_all(전체로그인) commandId=c-1003 사유=대상 컴퓨터 꺼짐(offline·거부코드 409) operator=admin src=<핸들러 절대경로:줄>` — **무슨 명령을(타입+한글)·어느 컴퓨터로(device_name)·왜(사유+409)·누가(operator)·코드 어디서(src)** 거부됐는지 전부. `commandId`는 명령 추적번호(기기 이름 아님), `409`=서버 "지금 안 됨" 거부코드. **`src`는 그 명령 핸들러의 절대경로:줄** — 서버/에이전트 미구현이라 지금은 예정 위치, 구현되면 실제값이 찍힌다.

### 내보내기

- 화면 위 **[내보내기]** 버튼 → 현재 보이는(또는 전체) 로그를 **`.txt`** 파일로 저장.

## 12. 리스크 / 검토 포인트

- **재연결 신뢰성**: IP 변경 후 SSE 재연결 백오프·중복 명령 방지(멱등 `commandId`) 설계 필요.
- **명령 유실**: ROTATING 중 발행된 명령 처리 정책(거부 vs 큐잉 후 재연결 시 전달) 확정 필요. → 기본: **거부 + Admin UI 비활성화**.
- **보안**: 기기토큰/운영자 세션 보호, 서버 공개 노출 시 TLS·인증 필수. 쿠키 본문은 서버로 보내지 않음.
- **통신 로그 평문 PW(운영자 결정, §10-5)**: 통신 로그에 한해 계정 ID/PW를 평문 표시 → PW가 서버 감사 DB·Admin 화면·내보낸 `.txt`에 평문 잔류. at-rest 암호화·접근통제·`.txt` 내보내기 파일 취급(저장 위치·공유)에 각별히 주의. (로컬 tracing은 여전히 PW 미로깅.)
- **자격증명 중앙 저장 위험**: 계정 ID/PW가 서버 DB 풀에 모이므로 **at-rest 암호화·키 관리·접근통제·전송 TLS 필수**, 유출 시 영향 범위가 크다. 쿠키는 여전히 서버로 보내지 않으며, **중앙에서 몰아 로그인하지 않는다**(IP 묶임 → 안티봇 차단, §10-2).
- **분배 정합성**: 같은 계정이 두 하위에 가면 네이버 세션 충돌·차단 → 서버가 **분배 시 한 계정 = 한 대(MOVE)** 로 중복 금지를 보장해야 함.
- **웹 배포 환경**: Admin 웹/서버 호스팅(같은 머신, 포트, TLS, 방화벽) 운영 정책 확정 필요.
- **하위 풀 UI 유지 + 원격 동시 조작**: 충돌 정책 확정(§4-3) — Admin 우선이되 현장 사람 행동 우선, 진행 중 작업(계정 단위)은 완료 후 양보. 글 도중 끊김 없음.
- **CI**: 기존 CI는 결제 미납으로 영구 빨강 — 머지 정책은 기존 합의(merge-commit) 따름.

### 이번에 확정됨 (반영 완료)

- **계정 source-of-truth(A-1)**: Admin 스테이징 → 분배 시 하위로 **MOVE**, Admin 계정 화면 비워짐(§7). 중복·동기화 문제 원천 제거.
- **분배 방식**: 운영자가 **체크박스로 수동 분배**, **균등+랜덤**(§10-3). 자동 전체 분배·재배분·오프라인 몫 문제 해소(오프라인은 목록에 안 떠 못 고름).
- **분배 후 동작**: 등록완료 판정 → 화면 새로고침 → **자동 전체 로그인**(§10-3). 결과는 **§10-4 형식으로 전부 Admin 보고**(배치 상세 + 누적 합계).
- **자동 로그인 플랫폼 = 종토(종토방) 확정**: 분배 대상 계정은 종토로 가정, 기존 **종토 선택 로그인 경로 재사용**(§10-2). 타 플랫폼(블로그·카페·밴드·클립) 확장은 추후.
- **실패 계정 자동 삭제**: 보고에 ID/PW·사유를 담은 뒤 **즉시 삭제**(§10-4). 보류·대기초과는 유지.
- **SuperAdmin 부트스트랩**: 기본 `Superadmin`/`Superadmin` 로그인 → **강제 비번 변경**(§5).
- **ROTATING 중 명령 정책 = 거부(큐잉 안 함) + 거부 사실을 통신로그에 기록**(§4-2). 1차 UI 비활성, 2차 서버가 `409`로 거부하며 들어온 명령·사유를 `[REJECT]`로 감사로그/통신로그에 남김.
- **분배 계정 전달 형식(B-4) = ② store 직접삽입 + 검증 재사용**(§10-3). 임시 xlsx를 만들지 않고 받은 JSON을 store에 직접 넣되, `import_accounts`의 검증·병합을 `merge_account_rows`로 추출해 엑셀·분배가 공유 → 빈줄 건너뜀·중복 덮어쓰기 동일 적용.
- **인증 토큰 방식 = JWT 통일**(§5·§6). 운영자 로그인·기기 토큰 **모두 JWT**. 회수는 운영자=**유저 버전 +1**(옛 토큰 일괄 무효), 기기=**기기표 줄 삭제**(옛 토큰 매칭 대상 소멸).
- **토큰 수명(확정)**: 운영자 토큰 = **exp 8시간**(만료 시 ID/PW 재로그인) / 기기 토큰 = **만료 없음(영구)** — 한 번 등록하면 계속 사용(§5 표·§6).
- **계정 ID/PW 암호화 = AES-256-GCM**(at-rest, §7). 계정 자격증명은 복원 가능해야 해(하위가 실제 로그인) 암호화; 운영자 비번은 복원 불필요라 해시(argon2). x86 하드웨어 가속+표준이라 단순·경량.
- **동시 조작 충돌 정책(§4-3)**: 기본 Admin 명령 우선, **현장 사람이 직접 행동하면 그 행동 우선**. 단 **진행 중 작업은 끊지 않고 완료**(단위=계정 경계) → 다음 계정 넘어가기 직전에 끼어든 행동 처리 → 그 다음 명령. (예: 1계정 글 5개 게시 중이면 5개 다 올리고 → 사람 행동 → 다음 계정.)
- **서버 배포 토폴로지(부분 확정)**: 중앙 서버 + Admin 웹을 **회사 랜선 고정 IP 컴퓨터 1대에 함께** 둔다(별도 머신 분리 안 함). 그 컴퓨터는 **고정 IP 사용으로 가정**(§2). 서버 스펙(CPU/메모리/OS)은 설계 무관이라 기록 안 함. (주소 형식·TLS·포트는 사수 방침 후 — 아래 남은 결정.)
- **기기 재등록 정책 = 삭제 후 새 코드로 재페어링**(§6-4). [기기 삭제] 버튼(`DELETE /devices/{id}`) 신설 → 줄 삭제로 옛 토큰 무효 → 새 기기코드 발급·재등록. UI 삭제 버튼은 `device-connection.tsx`에 추가 완료.
- **서버 DB = PostgreSQL (사수 확정, PR #324)**. `server/` 크레이트는 sqlx + PostgreSQL. (개발/오프라인 미리보기는 `DATABASE_URL` 미설정 시 in-memory 저장소로 동작, 운영은 PostgreSQL.) `server/migrations/`에 스키마.
- **비밀번호 분실 복구 = SuperAdmin이 하위 운영자 비번 재설정 (사수 확정, PR #324)**. SuperAdmin 본인 비번은 복구 경로 없음(종이에 적어 보관). 하위 운영자가 비번을 잊으면 SuperAdmin이 새 비번으로 재설정 → 그 운영자는 새 비번으로 로그인(재설정 시 그 운영자의 토큰 버전 +1로 옛 토큰 무효, §5). 엔드포인트 `POST /admin/operators/{id}/reset-password`, UI는 운영자 관리 화면(SuperAdmin에게만 [비번 재설정] 노출).
- **서버 주소·TLS·포트 = 배포 전 결정 (사수)**. `server/src/config.rs`에 자리만 두고 값은 비워둠(`배포 전 결정` 주석).
