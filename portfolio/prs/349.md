## 배경 (fix_and_add 6번)
"나눠서 즉시 게시"로 7계정/22종목을 올렸는데 **6계정만 배치를 받고 1계정이 post 0으로 증발**했다. 같은 증상이 ⒜ 자세히보기 누르면 선택 안 한 큐("준비하고 있어요" 상태)도 펼쳐짐 ⒝ 완료 토스트/알림이 한참 뒤에 나옴 으로도 나타났다.

## 근본 원인
큐 아이템 ID가 `"qn" + Date.now()`(밀리초 해상도)인데, 나눠서 게시는 계정별 아이템을 **같은 동기 tick**에 만들어 **전부 같은 ID**가 됐다. 백엔드는 ID로 일괄 처리한다 — `mark_running`/`apply_cancel_now`가 그 ID와 일치하는 **모든** 아이템에 적용. 그래서 충돌 그룹 k개 중 1개만 실행되고, 나머지 k−1개는 실행도 못 한 채 형제의 완료 시 함께 삭제(post 0 증발). 자세히보기도 같은 ID로 키잉돼 쌍둥이가 다 펼쳐지고, 증발한 쌍둥이는 자기 알림을 못 내 "한참 뒤에" 다른 아이템 알림만 보였다.

## 수정
- **프론트(핵심):** `freshIdSuffix`(모듈 카운터 + 시간 + 랜덤)로 같은 tick에도 ID가 반드시 고유. `newNowId`/`newScheduledId` 둘 다 적용.
- **프론트 진단:** `dispatchSplitNow`에 `[SPLIT]` 로그(선택 계정 수·계정별 종목 분배·생성 ID) — 재발 시 원인(중복 ID/빈 버킷) 즉시 식별.
- **백엔드 방어+진단:** `add_queue_now`가 중복 ID 감지 시 새 ID 부여+경고; `apply_cancel_now`가 한 ID로 2개↑ 지우면 경고(충돌 결정적 흔적); `finish_item`이 완료/양보를 ID로 로깅.
- **회귀 테스트:** 프론트(나눠서 게시 큐 ID 고유성), 백엔드(중복 ID가 쌍둥이를 함께 지움 문서화).
