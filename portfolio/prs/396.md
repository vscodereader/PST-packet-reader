## 배경 — 무엇이 캡차를 가르나 (실측)

성공 로그인 vs 캡차 로그인 패킷을 **전 호스트 전량 1:1 대조**(어제 0707·오늘 0708 두 캡처)한 결과:
- 요청·순서·헤더·쿠키·호출 API·**기기지문(🕵 로그)** 전부 동일. 차이는 랜덤 토큰 + 크롬 내부 텔레메트리뿐.
- **성공↔캡차를 가르는 건 패킷 내용이 아니라 "세션 내 로그인 시도 누적"**: 3회 재현(집2·원격1)에서 **19판까지 성공 → 20판째부터 캡차**. PC·크롬버전·IP대역·계정이 전부 달라도 동일.

## WASM 엔진(`353dfc…wasm`)에서 확인한 것

봇탐지 엔진은 매판 지문을 모아 `fpHash`(SHA-256) → 암호화(cipherText) → `/v2/tokens` 제출한다. 엔진 자체엔 **저장/카운터가 없어**(fresh 프로필·stateless) 채점·카운팅은 서버. 같은 PC면 매판 **동일 fpHash**가 나가 서버가 "한 기기"로 묶는 것으로 보인다. UA(`_setUserAgent`)도 그 입력 중 하나 — 그래서 **UA 를 판마다 다르게** 흘려 묶음이 흩어지는지 실험한다.

⚠️ 엔진엔 UA 교차검증기(`_setUserAgent`+swUserAgent, `NCAPTCHA_UA_DETECTION_RESULT` iframe↔sw, `_setHighEntropy`=Client Hints, `_setHasLiedBrowser/OS`)가 있어 **UA 문자열만 바꾸면 sec-ch-ua·서비스워커·iframe UA 와 어긋나 역효과**. 반드시 문자열+Client Hints 를 세트로 일관되게 바꿔야 한다.

## 이 PR이 바꾼 것

- **`ua.rs`(신규)**: 구글 **버전 히스토리 API**(공개·무인증, `versionhistory.googleapis.com/.../win64/stable/versions`)에서 **최신 실존 크롬 버전** 목록을 프로세스당 1회 받아 캐시(4초 타임아웃, 실패 시 **실측 폴백** 149.0.7827.201/150.0.7871.47). **설치 크롬 버전 이하**만 후보로 판마다 랜덤(상위버전 주장=기능탐지 회피). **지어낸 빌드는 절대 안 씀.** 순수 선택함수 + 테스트 7개.
- **`chrome.rs`**: **`launch_for_login`(로그인 전용)** 에서만 `--user-agent` 로 브라우저 전역 UA 문자열 통일(페이지·iframe·**서비스워커**·헤더). 게시/밴드용 `launch` 는 **네이티브 UA 유지**(packet_client UA 로직 무손상). 설치 버전은 Windows=레지스트리 BLBeacon, 개발=`--version` 으로 읽어 상한.
- **`login.rs`**: `enable_page_only` 직후(navigate 전) `Emulation.setUserAgentOverride` 로 페이지 UA + `userAgentMetadata`(Client Hints)를 같은 버전으로 맞춤. `ua`가 Some(로그인)일 때만.

## 정직한 한계 (기대치)

UA 는 fpHash 의 **작은 조각**이다(canvas/webgl/audio/CPU/폰트는 그대로 동일·변경불가 — 랜덤화하면 `_detectFixedCanvas`에 걸림). 그래서 **UA 로테이션만으로 20 벽이 밀릴지는 미지수**다. 이 PR은 **"버전 축이 앵커인지"를 싸게 확인하는 실험**이다:
- 캡차 벽이 뒤로 밀리면 → 지문 축 기여 확인.
- 안 밀리면 → 앵커는 하드웨어 지문/네트워크 → 다음은 **velocity 끊기(<19판+쿨다운)·기기 분산**.
