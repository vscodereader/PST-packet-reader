## 원인 (cap10 RabbitWrite 실측 대조 확정)
사진/링크/스티커/파일이 섞인 글이 발행 시 `{"isSuccess":false,"errorCode":"not acceptable"}`로 거부(순수 텍스트 글은 정상).
- **근본 원인**: 툴바 `text_component`가 **최상위 `align`** + 각 문단에 **직접 `align` 문자열**을 넣었음. 실제 SmartEditor 스키마는 top-level align이 **없고**, 정렬은 문단의 `style:{align,@ctype:paragraphStyle}`에 들어가며 **기본(left)이면 style 키 자체를 생략**함. 미디어 글엔 항상 텍스트 블록이 껴서 이 잘못된 형식에 걸렸다(순수 텍스트 경로 `build_document_model`은 align을 안 넣어 계속 정상 발행).
- 실측 확인: 실제 text 컴포넌트 keys=`[id,layout,value,@ctype]`(align 없음), left 문단 keys=`[id,nodes,@ctype]`(style 없음).
- oglink/sticker/file/code/schedule 컴포넌트는 실제 패킷과 필드 단위로 일치(oglinkSign도 올바른 경로) — 변경 없음.

## 사진(본문 이미지) 실제 구현 (photo.pcapng 실측)
`/v2/upload/file`은 파일첨부 메타(fileId)만 줘서 image 컴포넌트를 못 채움 → 별도 2단계:
1. `GET .../photo-uploader/session-key` → sessionKey
2. `POST blog.upphoto.naver.com/{sessionKey}/simpleUpload/0?userId=..&extractExif=true&...` (multipart `image` 파트, sessionKey가 URL로 인증하므로 se-auth 없음) → **XML** 응답
- XML 파싱: `src = blogfiles.pstatic.net{url}?type=w1`, `path = {url}`, width/height/fileSize/fileName. (실제 image 컴포넌트와 일치.)
- `upload_file`(파일)은 `/v2/upload/file` 그대로.

fix(blog): media documentModel text-align schema + real photo upload

RabbitWrite rejected any post with 사진/링크/스티커/파일 blocks with
`{"isSuccess":false,"errorCode":"not acceptable"}` while text-only posts
published fine.

Root cause (verified vs cap10 decrypted RabbitWrite packets): the toolbar
`text_component()` emitted a top-level `align` on the text component and a
direct `align` field on each paragraph. The real SmartEditor schema has NO
top-level align and carries alignment in the paragraph's nested
`style:{align,@ctype:paragraphStyle}` (omitted entirely when left/default).
Every failing media post also contained a text block, so it always hit this
malformed shape; the pure-text path (`build_document_model`) never sets align
and so kept working. Fixed `text_component()` to match the real schema and
locked the shape with assertions.

Verified the other media components (oglink/sticker/file/code/schedule)
byte-match the real packet field-by-field, and `parse_oglink` reads
`oglinkSign` from the correct top-level path (confirmed by decompressing the
real /api/blogpc001/v1/oglink response) — no change needed.

Photos: implement the real 2-step photo-uploader flow (photo.pcapng).
`/api/blogpc001/v2/upload/file` only returns file-attachment metadata, so it
can never populate a body-image component. Body photos upload to
`blog.upphoto.naver.com/{sessionKey}/simpleUpload/0?...` (multipart `image`
part, sessionKey authorizes via URL so no se-authorization header) and return
XML. Added UPPHOTO_HOST + injectable upphoto base, rewrote `upload_photo` to
the upphoto endpoint, replaced the JSON `parse_uploaded_image` with an XML
parser that builds src=blogfiles+<url>?type=w1 / path=<url>, and wired
`upload_blog_photo_for_account` to fetch the session key first. `upload_file`
(파일) stays on /v2/upload/file, untouched.

Note: real posts also carry `document.di` (typing-time/keystroke anti-bot
telemetry) and `populationParams.editorSource` (per-session opaque token).
Both are absent from the working text-only path, proving them optional for
acceptance, and their values can't be derived from the packet, so they are
intentionally not fabricated.
