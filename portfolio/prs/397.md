## 무엇을 / 왜

로그인 캡차 규명 실험에서 나온 두 로그인 경로 개선을 master 에 반영한다. 전부 로그인
경로 한정이며, wasm 관련은 **환경변수 옵트인(기본 OFF)** 이라 평소 로그인·게시·밴드
동작은 바이트 단위로 무변경이다.

### 1) UA·Client Hints 로테이션 (`ua.rs` 신규 + `chrome.rs`/`login.rs`)
- 구글 버전 히스토리 API에서 최신 실존 크롬 버전을 받아(실패 시 실측 폴백) 각 메이저의
  최신 빌드 1개씩 최근 6개 메이저를 후보로, **설치 크롬 버전 이하**만 판마다 라운드로빈.
- `--user-agent`(브라우저 전역) + `Emulation.setUserAgentOverride`(페이지 UA·Client Hints)를
  같은 버전으로 일관 적용(불일치 봇신호 방지). 게시/밴드는 네이티브 UA 유지.

### 2) wasm 차단 실험 스위치 (`chrome.rs`/`login_flow.rs`) — 옵트인 기본 OFF
- `PSTMACRO_BLOCK_WASM` 설정 시, 로그인 Chrome 이 봇탐지 WASM 엔진 호스트
  `wtm.pstatic.net` 을 `--host-resolver-rules` 로 DNS 차단 → ncaptcha SDK 단독 경로 강제.
  (CDP `Network.enable` 은 봇탐지 표면을 늘려 결과를 오염시키므로 실행 플래그를 씀.)
- 차단 시 SDK 토큰 생성기(`wtmncapt`) 준비가 늦어 error 토큰→폴백 캡차가 나던 레이스를,
  제출 직전 wtmncapt 준비 대기(최대 10초)로 제거 → 진짜 SDK 토큰이 나가게 한다.

### 실측 근거 (2026-07-08, IP 회전·다계정 상수 고정)
- wasm ON: 캡차 6/65(~9%) · wasm OFF+진짜토큰: 캡차 0/24 → 지문(wasm) 축을 가리킴(추가 표본 필요).

feat(auth): 로그인 UA·Client Hints 를 판마다 최신 실존 크롬으로 일관 로테이션

같은 PC 로 로그인하면 매판 UA·지문이 동일해 서버가 '한 기기'로 묶어 시도를
누적(≈19판 통과→20판째 캡차)하는 것으로 관측됨(2026-07-08, 집2·원격1 재현).
UA 를 판마다 다르게 흘려 그 묶음이 흩어지는지 실험한다.

- ua.rs(신규): 구글 버전 히스토리 API(공개·무인증)에서 최신 실존 크롬(win64) 목록을
  프로세스당 1회 받아 캐시(4초 타임아웃, 실패 시 실측 폴백 149/150). 설치 크롬 버전
  '이하'만 후보로 판마다 랜덤(상위버전 주장=기능탐지 회피). 지어낸 빌드는 안 씀.
  순수 선택함수 pick_capped + 테스트 7개.
- chrome.rs: launch_for_login(로그인 전용)에서만 --user-agent 로 브라우저 전역 UA
  문자열 통일(페이지·iframe·서비스워커·헤더). 게시/밴드용 launch 는 네이티브 UA 유지
  (packet_client UA 로직 무손상). 설치 버전은 BLBeacon(win)/--version 으로 읽어 상한.
- login.rs: enable_page_only 직후(navigate 전) Emulation.setUserAgentOverride 로 페이지
  UA + userAgentMetadata(Client Hints)를 같은 버전으로 맞춤 — 문자열만 바꾸면 sec-ch-ua/
  sw/iframe UA 와 어긋나 _setHasLiedBrowser/NCAPTCHA_UA_DETECTION(WASM 교차검증)에 걸려
  역효과라, 문자열+Client Hints 를 세트로 일관되게 바꾼다.

### 43d84ad1ccc971f1a9b8ae1c4d2573c2b0aa048c

feat(auth): 로그인 WASM 엔진(wtm) DNS 차단 실험 스위치 추가

PSTMACRO_BLOCK_WASM 옵트인(기본 OFF) 시, 로그인 Chrome 이 네이버 봇탐지 WASM
엔진 호스트 wtm.pstatic.net 을 --host-resolver-rules=MAP ... ~NOTFOUND 로 DNS
해석 실패시킨다. wtm 로더(3e66f2f…js)·엔진(353dfc…wasm)이 로드되지 않아 ncaptcha
SDK(ncpt.naver.com) 단독 경로로 강제된다.

목적: "기기지문(fpHash)이 캡차 누적의 앵커인가"를 wasm-off 20판 버스트로 규명.
실측(2026-07-08, 재시도.pcapng)에서 wtm SNI/DNS 0 이어도 SDK 혼자 cipherText 를
POST(/v2/tokens)하고 진짜 wtoken(MnZLZ65q…=)을 nidlogin.login 에 실어 통과함을
확인 — SDK 단독 토큰 생성이 가능하므로 이 조건을 재현해 20판 누적을 관찰한다.

- Network.setBlockedURLs(→Network.enable 필요) 대신 Chrome 실행 플래그 사용:
  Network.enable 은 봇탐지 표면을 늘려(enable_page_only 주석) 결과를 오염시킴.
  host-resolver-rules 는 CDP 표면 0 추가, 사용자가 수동 재현한 조건과 동일.
- 로그인 경로(ua=Some)에만 적용 — 게시/밴드(ua=None)는 무영향.
- wtm.pstatic.net 만 대상, ncpt(SDK)·ssl.pstatic.net(폰트/이미지)은 무손상.
- 단위테스트 1개 추가(대상 호스트 정확성 검증).

### 1216d254b3b24ec5978c56968844bf68b302fd95

fix(auth): wasm 차단 실험 시 제출 전 wtmncapt 준비 대기

wasm 엔진 호스트(wtm)를 DNS로 막으면 ncaptcha SDK 가 엔진 로드를 재시도하느라
window.wtmncapt(토큰 생성기) 생성이 늦다. 매크로가 폼 로딩 ~1초 만에 제출하면
default_ecc.js 가 error1|ReferenceError|wtmncapt is not defined 를 실어 티켓 없이
폴백 캡차로 떨어진다(실측 wasm 완전통제: /v2/tokens 0, wtoken=error1…, 영수증 캡차).

제출 직전 wtmncapt 준비를 최대 10초 폴링(200ms)해, 재시도.pcapng 처럼 진짜 SDK
토큰이 나가게 한다 — 그래야 캡차가 떠도 우리가 쫓는 누적 캡차지 토큰-없음 폴백이
아니게 된다. 스위치 OFF 면 즉시 반환 → 기존 로그인 타이밍 바이트 무변경. best-effort:
준비 못 해도 경고만 남기고 제출은 계속(실험자가 로그로 원인 파악).
