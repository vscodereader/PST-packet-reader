- 취소 원시primitive가 **아예 없음**: `RunnerInner`는 `is_running`·`active_forum`·`active_comment` 정수 3개만 보유(`queue_runner.rs:55-66`). `CancellationToken`/`AtomicBool`/`AbortHandle` 전무.

- **쿠키 파일 손상은 구조적으로 불가**: 게시 경로는 쿠키를 읽기만 함(`cookie_bridge.rs`). 쓰기는 로그인 finalize에서만, 원자적 temp+rename(`login.rs:238`).
- **절대 끊으면 안 되는 창**: add POST 전송(`packet_client.rs:862`) 후 ~ outcome 기록(`queue_runner.rs:876`) 전 = 글은 올라갔는데 기록 없는 구간 → 수동 재큐잉 시 이중게시. (영속 dedup 대장이 없음)

때문 — 종토/밴드처럼 분배 직후 자동 로그인하는 흐름과 다르다). 그래서 두 화면을 손본다:

1. **계정 분배** — 계정 풀에 **플랫폼 열**(플랫폼·아이디·비밀번호·휴지통) 추가. 플랫폼을
   `네이버 카페`로 골라 분배하면 그 계정은 하위에 **등록만** 되고 로그인은 건너뛴다.
2. **게시 명령** — 글/댓글/글+댓글 어느 것이든 **카페**를 고르면 **게시판 링크** 입력칸이
   뜬다. 링크를 추가하면 목록(select)에 쌓이고, 고른 게시판이 아래 **동그라미 배지**로 뜬다.
   여러 링크 → 여러 게시판 선택. 카페일 때는 **로그인 성공/실패 무관 카페 계정 전부**를
   보여주고, `지금 게시`/`예약 게시`를 누르면 그 명령이 하위로 내려간다(하위가 게시 시점에
   로그인해서 올린다).

## 2. 계정 분배 — 플랫폼 열 + 카페=등록만

- **UI**(`src/admin/features/account-distribute/account-distribute.tsx`): 인라인 추가 행에
  **플랫폼 Select**(좌측 첫 열) → 아이디 → 비밀번호 → 휴지통. 기존 풀 계정도 플랫폼 배지 표시.
  기본 플랫폼 = `종목토론방`(기존 동작 유지).
- **명령 경로**: `import`(계정 스테이징)에 `platform`을 실어 보낸다 → 서버 `StagedAccount.platform`
  → 분배 payload `{loginId, pw, platform}` → 하위 `AccountIn.platform`.
- **하위 등록/로그인 분기**(`src-tauri/src/agent/mod.rs` `distribute_accounts`): 등록은 전부
  하되(IPC 스토어 + `accounts.json` — 카페도 게시 시점 로그인에 id/pw 필요),
  **로그인 큐(enqueue_login)는 카페(`naver`)가 아닌 계정만** 태운다. 카페는 등록만 하고
  로그인은 게시 순간 엔진이 한다. 종토·밴드는 종전대로 분배 직후 로그인.

## 3. 게시 명령 — 카페 게시판 링크

- **UI**(`src/admin/features/publish-command/publish-command.tsx`): `DeviceBlock`의 대상에서
  `카페(naver)`를 활성화하고 새 `CafeConfig`를 렌더한다(글/댓글/글+댓글 **모두**):
  - `게시판 링크` 입력 + `추가` → `parseCafeBoardLink`로 `{cafeId,menuId}` 파싱해 목록에 누적.
  - Select(placeholder "게시판 링크를 추가하면 여기 표시됩니다") → 고르면 아래 **동그라미 배지**
    (제거 X 포함). 여러 링크 → 여러 게시판 다중 선택. **데스크톱 publish-modal 카페 카드와 동일.**
  - 계정 = **이 하위의 카페(`naver`) 계정 전부**(로그인 성공/실패 무관). `지금 게시`/`예약 게시`는
    글·게시판·계정만 있으면 활성(로그인 상태 안 봄 — 카페는 게시 때 재로그인).
- **명령 경로**: `publish.send`/`scheduled.create`에 `target:"cafe"` + `cafeBoards:[{cafeId,menuId,link}]`
  추가 → 서버 `PublishSpec.target`/`cafe_boards` → payload → 하위 `PublishCmd`.
- **하위 조립**(`build_publish_items`): `target=="cafe"`면 `plan.forum` 대신 **`plan.naver`**를
  계정×게시판으로 조립한다. 각 `NaverTarget{account_id, cafe:cafeId, cafe_name, menu_id, board_type:""}`
  (`board_type`은 게시 시점 백엔드가 `menu_id`로 해석 — 데스크톱과 동일). 댓글/글+댓글은 글에
  동결된 `comment_target`/`comment_count`를 실어 엔진이 처리(글=None, 댓글=글의 대상, 글+댓글=자기 글).

## 4. 카페 계정을 로그인 무관 전부 보여주기

- 인벤토리 보고(`inventory_body`)에 **`accountRows:[{loginId,platform,status}]`**(계정 전체)를
  추가한다. 기존 `accounts`(로그인 성공만)는 그대로 둬 종토 화면 동작 불변.
- 서버 `DeviceInventory.account_rows`(신규) 저장·전달. Admin `accountsFor`는 **종토=Active만
  (`accounts`), 카페=`accountRows`에서 platform==naver 전부**.

## 5. 범위·비범위

- **이번 범위**: 카페(종토처럼 실동작). 글=게시판에 글, 글+댓글=글 게시 후 자기 글에 댓글,
  댓글=글에 동결된 대상(특정글/최신/인기)로 엔진 처리.
- **비범위(추후)**: 블로그·밴드 게시명령 상세(요구서 도입부 언급 — 이 문서는 카페만). 카페
  게시판명/카페명 실시간 조회(쿠키 필수라 게시 시점 백엔드가 해석; 목록 라벨은 `카페 {id}·게시판 {id}`).
- **실기기/실서버 검증은 사수/사용자 몫**(이 환경엔 폰·카페 로그인 불가).

## 0. 한눈에

**블로그는 댓글 전용**이다(글쓰기 없음 — `naver_blog/mod.rs` 머리말: "블로그는 댓글 전용").
별도 로그인 흐름이 없고 **저장된 네이버 쿠키**(`cookies/{loginId}.json`)를 그대로 재사용해

게시(댓글) 시점엔 그 쿠키로 바로 댓글을 단다.

댓글 대상은 **두 가지 모드**뿐이다(데스크톱과 동일):

| 모드 | 입력(링크) | 동작 |
|---|---|---|
| **특정 게시글** | 글 URL (`blog.naver.com/{blogId}/{logNo}`) | 그 글 하나에 댓글 |
| **최신글 / 인기글** | 블로그 홈 URL (`blog.naver.com/{blogId}`) | 그 블로그 **최신 N개** 글에 댓글 |

> ⚠️ **"최신글"과 "인기글"은 동일 동작**이다 — 데스크톱(`publish-modal.tsx:269·446`)에서 둘 다
> `blogIsListTarget=true`로, 블로그 홈 링크에서 `blogId`를 뽑아 **최신 N개**를 조회해 댓글을 단다.
> 블로그 백엔드에는 별도 "인기 정렬" 조회가 없다(`post_list.rs`=`fetch_latest_posts` 한 종류).
> UI 라벨만 "최신/인기"로 나뉘고 실동작은 같다(사용자 확인 완료).

Admin은 카페와 **동일한 UX**(링크 입력 → 목록 → 선택 배지)를 이식하고, `지금 게시`/`예약 게시`를
누르면 그 명령이 하위로 내려가 하위 큐 러너가 저장 쿠키로 댓글을 단다.

## 2. 계정 분배 — 플랫폼 열 + 블로그=로그인해서 등록

  Select**에 `네이버 블로그`(`blog`)를 노출한다(이미 `PlatformId::Blog` 존재). 아이디/비밀번호/휴지통.
- **명령 경로**: `import`(스테이징)에 `platform:"blog"`를 실어 보낸다 → 서버 `StagedAccount.platform`

## 🗄️ DB(PostgreSQL) 연결 — 정리

쿠키를 확보해 두고(종토·블로그와 동일), 게시(댓글) 시점엔 그 쿠키로 바로 댓글을 답니다.

댓글 대상은 **한 가지 모드**뿐입니다 — **창작자(@handle)의 최신 미디어 N개**:

| 입력(링크) | 동작 |
|---|---|
| 창작자 링크 `https://clip.naver.com/@<handle>` | 그 창작자의 **최신 미디어 N개**에 각각 댓글 1개 |
| `…/@<handle>?tab=video` | **영상만** 대상(그 외/`?tab=all`=전체) |

> ℹ️ 클립은 "특정 영상 1건"이나 "인기 정렬" 모드가 없습니다(엔진에 없음). 항상 **창작자 최신 N개**입니다.
> N은 데스크톱에선 글(댓글 템플릿)의 `commentCount`로 동결되며(`publish-modal.tsx:595`),
> Admin은 블로그와 동일하게 **"개수 N" 입력칸(이미 존재)** 을 재사용해 운영자가 지정합니다.

> ⚠️ **본인인증**: 클립 댓글은 계정이 **본인인증(실명·연령)** 을 마쳐야 합니다. 미인증 계정은 프로필
> 생성 단계에서 **`SignUp code=-7020`** 으로 실패합니다(`naver_clip/profile.rs:166`, "코드로 우회
> 불가"). 이는 **런타임 계정 속성**이라 Admin 배선의 대상이 아니며, 결과보고에 실패로 그대로 뜹니다(§6).

Admin은 블로그와 **동일한 UX**(창작자 링크 입력 → 칩 목록)를 이식하고, `지금 게시`/`예약 게시`를
누르면 그 명령이 하위로 내려가 하위 큐 러너가 저장 쿠키로 최신 N개에 댓글을 답니다.

## 2. 계정 분배 — 플랫폼 열 + 밴드 = band.us 로그인해서 등록

- **UI**(`account-distribute.tsx`): 카페·블로그와 **동일한 플랫폼 Select**에 `밴드`(`band`)를 노출
  (이미 `PlatformId::Band`·`platform_from_str("band")` 존재). — **새 옵션 추가 불필요.**
- **명령 경로**: `import`에 `platform:"band"` → 서버 `StagedAccount.platform` → 분배 payload
  `{loginId, pw, platform:"band"}` → 하위 `AccountIn.platform`.
- **하위 등록/로그인 분기**(`agent/mod.rs distribute_accounts`:487): 밴드는 **카페가 아님**
  (`is_cafe_platform("band")==false`)이라 **분배 직후 자동 로그인**(`enqueue_login`)합니다(종토·블로그와 동일).

> ⚠️ **여기 하나가 "없는 배선"입니다(밴드만의 유일한 실질 작업).** 현재 `enqueue_login`은 모든 로그인
> 대상을 `platform: PlatformId::Naver`로 하드코딩합니다(`agent/mod.rs:1244`). 클립/블로그/종토는
> 네이버 로그인이라 이대로 맞지만, **밴드는 band.us 로그인이라 `PlatformId::Band`가 필요**합니다
> (러너가 :1814·:2534에서 `Band`일 때만 `process_band_account`로 분기하기 때문). 따라서
> `enqueue_login`(또는 `distribute_accounts`의 로그인 적재부)을 **계정 플랫폼에 따라 `platform`을
> 정하도록** 바꿔야 합니다(밴드=`Band`, 그 외=`Naver`). **엔진은 무손상 — 로그인 대상 조립만 고칩니다.**

## 3. 게시 명령 — 밴드 링크(글/댓글/글+댓글)

- **UI**(`publish-command.tsx`): 현재 밴드는 `TARGETS`에서 `{ key:"band", label:"네이버밴드", soon:true }`
  (:69)로 **버튼만 있고 비활성**입니다. 작업 = **`soon:false`로 열고 `BandConfig` 렌더**(카페 `CafeConfig`:1235 형제).
  - `밴드 링크` 입력 + `추가` → **`bandNoFromLink` 미러(순수)** 로 파싱해 목록(select)에 누적. 카페가
    게시판 링크(menu)와 특정 글 링크(article)를 함께 받듯, 밴드도 **밴드 홈 링크**(글/최신/인기용)와
    **특정 글 URL**(url 댓글용, band_no+post_no)을 함께 받습니다 — url 댓글은 `t.link`에 그 글 URL을 실어야 함.
  - Select → 고른 밴드가 아래 **동그라미 칩**(제거 X 포함). 여러 링크 → 여러 밴드 다중 선택.
    **데스크톱 밴드 카드(:695 드롭다운·:711 칩)와 동일.**
  - **글 종류 3가지 공통**(카페와 동일): 글/글+댓글=밴드에 새 글, 댓글=**최신/인기/특정 글 URL**. 댓글
    대상 모드(latest/popular/url)/개수는 글(`commentTarget`/`commentCount`)에 **동결**된 값 사용(카페와 동일 — 여기서 안 고름).
  - 계정 = **이 하위의 밴드(`band`) 계정 중 로그인 성공(active)**.
- **명령 경로**: `publish.send`/`scheduled.create`에 `target:"band"` + `bandTargets:[{bandNo, link}]`
  추가 → 서버 `PublishSpec.target`/`band_targets`(신규, `PublishCafeBoard`:66 형제) → payload → 하위 `PublishCmd`.

> ℹ️ **밴드명 실시간 조회는 하지 않습니다(안 함).** 데스크톱은 저장 시 밴드명을 조회하지만
> (`publish-modal.tsx:684` `bandResolving`) 그건 **band.us 세션이 있는 하위**라서 가능합니다. Admin
> 웹엔 밴드 쿠키가 없으므로, 카페가 게시판명을 게시 시점 백엔드가 해석하듯 **Admin은 `band_no`만
> 파싱해 라벨(`밴드 {bandNo}`)로 쓰고, 실제 게시는 하위가 밴드 쿠키로 수행**합니다(band_publish가

# 네이버 종목토론방 글 신고하기 — 설계서

> 상태: **설계 확정 / 구현 착수**
> 브랜치: `feat/naver-report` (base=`master`)
> 대상: pstmacro(하위 COM 데스크톱 앱). e2e 검증 후 Admin 원격제어(#324)에 배선 예정.
> 근거: `신고하기 패킷.pcapng` + `글 신고 + 링크.pcapng` 2세트 TLS 복호화 실측(2026-07-14).

---

## 1. 목적

글 관리 화면에서 **"신고하기"** 버튼으로, 네이버 종목토론방 글을 **API로 직접 신고**한다.
링크 n개 + 하위 계정 m개를 골라 **n×m 건**을 신고하되, 화면은 막히지 않고(비차단)
백그라운드로 진행한다. 브라우저 UI를 자동 클릭하는 방식이 아니라 `POST /api/report`를
직접 쏘는 방식이다(단 봇탐지 토큰만 브라우저로 생성 — §4).

---

## 2. 신고 API 완전 스펙 (패킷 실측)

### 2.1 엔드포인트 (전부 `srp2.naver.com` = 네이버 신고센터)

| 순서 | 메서드 | URL | 용도 |
|---|---|---|---|
| 1 | GET | `stock.naver.com/api/community/discussion/posts/by-item?...&itemCode={code}` | 글 목록 → `writer.profileId` |
| 2 | GET | `stock.naver.com/api/community/profile/users/{profileId}` | → `encryptedUserId` (=cwriterenc) |
| 3 | GET | `srp2.naver.com/api/reason?serviceCode=FIN&virtualServiceCode=FIN&reportLanguageCode=ko` | 신고 사유 목록 |
| 4 | POST | `ncpt.naver.com/v2/tokens?q={ts}&tid={id}` | **ncaptcha 토큰**(브라우저 WASM만 생성) |
| 5 | POST | `srp2.naver.com/api/report` | 신고 제출 → `{"success":true}` |

### 2.2 링크 → 신고 파라미터 체인

```
링크 예: https://stock.naver.com/domestic/stock/000660/discussion/425406371
  → itemCode = 000660,  postId = 425406371
  → [GET by-item(itemCode)] 에서 id==postId 인 글 찾아 writer.profileId
  → [GET profile/users/{profileId}] → encryptedUserId  (실측: "vAOdyIfnpaqA...=")
  → contentId = "FIN_001;item;board;" + postId
```

### 2.3 POST `/api/report` 요청 (application/json, `x-requested-with: XMLHttpRequest`)

```json
{
  "serviceCode": "FIN",
  "virtualServiceCode": "FIN",
  "contentTypeCode": "AC01",
  "contentId": "FIN_001;item;board;425406371",
  "contentWriterId": "",
  "contentWriterIdEncrypted": "<encryptedUserId>",
  "reportCountryCode": "",
  "reportLanguageCode": "",
  "environment": "pc",
  "reportReasonCode": "<사유코드>",
  "addInformation": {},
  "ncaptchaTokenId": "<브라우저가 생성한 토큰>",
  "reportSystemId": ""
}
```
성공 응답: `{"success":true}`

### 2.4 신고 사유 7개 (`/api/reason`, service=FIN 실측)

| 코드 | 문구 |
|---|---|
| `AA01` | 혐오/차별적/생명경시/욕설 표현입니다 |
| `AA29` | 스팸홍보/도배입니다 |
| `AA14` | 음란물입니다 |
| `AA68` | 불법정보를 포함하고 있습니다 |
| `AA33` | 청소년에게 유해한 내용입니다 |
| `AA24` | 개인정보가 노출되었습니다 |
| `AB28` | 불쾌한 표현이 있습니다 (클린봇 학습) |

> 사유 목록은 상수로 내장하되, 첫 호출 시 `/api/reason`로 검증(문구/코드 변동 감지).

### 2.5 인증

`POST /api/report`에 **`NID_AUT`·`NID_SES` 로그인 쿠키가 필요**(패킷 실측).
pstmacro가 이미 보유한 `cookies/{loginId}.json`을 재사용한다. 신고 사이클 전체에
재로그인 요청은 없음 — 이미 로그인된 세션의 쿠키만 쓴다.

---

## 3. 근본 제약 — 왜 순수 HTTP만으로 안 되는가

`ncaptchaTokenId`는 `POST ncpt/v2/tokens`가 반환하는 `cipherText`를 **네이버 봇탐지
WASM(`ncaptcha-api.js`, 극도로 난독화된 안티봇 JS)**이 브라우저 안에서 처리해 만든다.
`cipherText`는 WASM 내부 랜덤키로 암호화되어 **Rust로 복제 불가**(프로젝트가 로그인
캡차에서 이미 확인한 벽 — `auth/chrome.rs`·캡차 포렌식 기록).

→ 조회(1·2)·사유(3)·신고 제출(5)은 순수 HTTP지만, **토큰(4)만은 브라우저가 필요**하다.
이 캡차는 **위험점수 문턱효과**라, 정상 계정·낮은 빈도면 조용히(퍼즐 없이) 토큰이 나오고,
같은 IP로 다계정 도배 시 위험점수가 올라 퍼즐이 뜬다.

---

## 4. 아키텍처 — 하이브리드

**실제 신고 POST는 Rust에서 직접, ncaptcha 토큰만 기존 CDP 인프라로 생성.**
(실제 브라우저가 토큰을 넣어 신고한 동작을 그대로 재현)

### 4.1 크롬 생명주기 (핵심)

- 크롬은 **토큰 생성이 필요한 그 순간에만** 켜고, 그 외에는 **확실히 종료**한다.
- 종료는 기존 `auth/chrome.rs`의 프로세스 트리 종료(`taskkill /T /F`, 자식 헬퍼 포함)를
  재사용 — 잔존 프로세스 0 보장.
- 크롬은 **보이는(visible) 모드**(로그인과 동일 — headless는 봇탐지에 더 잘 걸림).

### 4.2 계정 1개당 크롬 1회

계정마다 로그인 쿠키/세션이 다르므로 크롬 세션을 공유할 수 없다.
계정 하나가 크롬 열려 있는 동안 그 계정의 **링크 n개를 모두 처리**하고 닫는다.

---

## 5. 실행 흐름 — n×m 루프

```
입력: 링크 n개, 선택 계정 m개(체크박스 재사용), IP회전 on/off
"신고하기" → 모달 닫힘 → 백그라운드 async 시작(화면 안 막힘)

for 계정 in 선택 m개:                       # 계정 바깥루프
    if IP회전 ON and 앞 계정 완전 종료:
        ADB toggle_airplane_mode()  → 새 IP  # auth::adb 재사용
        새 IP에서 그 계정 재로그인(§6)         # 세션 IP 일관성
    else:
        저장 쿠키 주입(재로그인 없음)

    🟢 크롬 열기(계정 세션)
    for 링크 in n개:                          # 링크 안쪽루프
        1. 링크 → postId, itemCode
        2. GET by-item → profileId
        3. GET profile/users → encryptedUserId
        4. srp2 report 페이지 로드 → ncaptcha 토큰 획득(CDP)
        5. POST /api/report(쿠키+토큰+사유)  → 결과 수집
        [사람같은 간격 딜레이]
        (퍼즐 캡차 뜨면 보류→수동해결, 게시 흐름 재사용)
    🔴 크롬 종료(taskkill 트리)

알림: "총 n×m건 중 ○건 완료" (링크·계정별 성공/실패)
```

- 조회(1·2·3)·제출(5)은 크롬 없이 Rust HTTP. 4번만 크롬.
- 편의상 계정당 크롬을 한 번 열어 그 계정의 링크 토큰을 이어서 생성(창 여닫이·IP회전 최소).
  단 배치가 봇탐지를 낮추지는 않음 — 완화는 IP회전+간격이 담당.

---

## 6. IP 회전과 재로그인 규칙

모달의 **`IP 회전` 체크박스**(계정 선택 아래):

| 상태 | 동작 | 재로그인 |
|---|---|---|
| **OFF** | 전 계정 동일 IP에서 신고 | ❌ 저장 쿠키 재사용 |
| **ON** | 앞 계정 완전 종료 후 IP 회전 → 다음 계정 | ✅ 새 IP에서 계정 재로그인 |

**왜 IP 회전 시 재로그인인가:** 네이버 세션 쿠키는 만든 IP와 묶여 위험판정된다.
IP를 바꾼 뒤 옛 IP 쿠키를 새 IP에 주입하면 "세션 IP 점프"라는 봇 신호가 오히려 강해져
회전 의미가 사라진다. 새 IP에서 로그인해 세션 전체를 그 IP로 일관시킨다
(기존 로그인+ADB 흐름 `회전→로그인`을 그대로 재사용).

ADB가 없으면 회전을 건너뛰고 현재 IP로 진행(사수 지시, 기존 로그인과 동일).

---

## 7. 봇탐지·위험 고려 (정직)

- **같은 IP로 다계정이 같은 글 신고 = 고위험**: 위험점수 급상승 → 퍼즐 캡차 확률↑,
  네이버가 조직적 신고로 탐지해 무효처리 가능.
- 완화책: **IP 회전(ADB) + 계정 사이 간격 + 퍼즐 시 보류/수동해결**.
- 배치(크롬 한 번에 여러 토큰)는 창 여닫이 UX만 줄일 뿐 탐지 완화 아님 — 간격 필수.
